---
title: Engine/client protocol 0.2
---

An external client plays the game over newline-delimited JSON-RPC 2.0 on the stdio of `cataclysm-bn-tiles --client=mcp`. The values are defined by the [Draft 2020-12 schema](../../../schema/engine-client/0.2.schema.json), and every example below is checked against it in the [examples files](../../../schema/engine-client/0.2.examples/). The legacy MCP tools (`bn.observe`, `bn.press`, ...) are a separate, unchanged surface; once a client says `bn.hello`, they refuse input.

## A session

```text
-> {"jsonrpc":"2.0","id":1,"method":"bn.hello","params":{"versions":["0.2"],"client":{"name":"my-client","version":"1"},"schema":"sha256:0123456789abcdef"}}
<- {"jsonrpc":"2.0","id":1,"result":{"version":"0.2","epoch":"epoch:e7f3","engine":{"build":"...","mods":["bn"],"display":{"tiles":true,"tileset":"UNDEAD_PEOPLE_BASE"},"sound":{"soundpack":"/opt/bn/data/sound/Basic"}},"limits":{"frame_bytes":1048576,"cells_per_part":512,"cells_per_query":4096,"screen_queue":8},"schema":"sha256:0123456789abcdef","locale":"en","engine_locale":"en","role":"controller"}}
-> {"jsonrpc":"2.0","id":2,"method":"bn.subscribe","params":{}}
<- {"jsonrpc":"2.0","id":2,"result":{"at":{"epoch":"epoch:e7f3","sequence":"40","revision":"31"},"interaction":{...},"entities":[],"parts":1}}
<- {"jsonrpc":"2.0","method":"bn.snapshot.part","params":{"epoch":"epoch:e7f3","at":{...},"index":0,"last":true,"cells":[...]}}
-> {"jsonrpc":"2.0","id":3,"method":"bn.command.submit","params":{"epoch":"epoch:e7f3","expect":{"revision":"31","boundary_id":"boundary:90","schema_id":null},"operation":{"kind":"action","action_id":"RIGHT"}}}
<- {"jsonrpc":"2.0","id":3,"result":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"received"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"validated"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"executing"}}
<- {"jsonrpc":"2.0","method":"bn.events","params":{"epoch":"epoch:e7f3","events":[{"sequence":"41","revision":"32","type":"interaction.changed","command":"c:5","changes":{...}}]}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"completed","at":{"epoch":"epoch:e7f3","sequence":"41","revision":"32"}}}
```

Collect the `parts` snapshot parts, then apply `bn.events` in order. A gap, an epoch mismatch or `bn.resync` means: call `bn.subscribe` again. A new snapshot restores state only; transient events after `lost_after` are lost, never replayed. The engine keeps no event history: after `bn.unsubscribe`, or after falling behind, `bn.subscribe` is the only way back, and its snapshot (never a replay) supersedes the last seen `(epoch, sequence)`. A `bn.resync` stops only the events: the `bn.command` stages keep coming, since no snapshot carries them, and a stage may follow a newer snapshot than its `at`. Stages are pushed from `bn.subscribe` until `bn.unsubscribe` or `bn.hello`; read the outcome of a command outside that span with `bn.command.result`. Any request that names a stale `epoch` fails with `stale_epoch` and `action: "subscribe"`.

## Methods

| ------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |

| `bn.viewport`            | `cols`, `rows`                                             | none                                                                                                                                          |
| `bn.interrupt`           | none                                                       | none                                                                                                                                          |
| `bn.hold`                | `epoch`, `screen_id`, `affordance_id`                      | none                                                                                                                                          |
| `bn.release`             | none                                                       | none                                                                                                                                          |
| `bn.subscribe`           | none                                                       | snapshot header; parts and events follow                                                                                                      |
| `bn.unsubscribe`         | none                                                       | none                                                                                                                                          |
| `bn.interaction.choices` | `epoch`, `boundary_id`, `offset`, `limit`                  | `boundary_id`, `total`, `choices` (reads only)                                                                                                |
| `bn.world.describe`      | `epoch`, `boundary_id`, `pos`                              | `lines` (reads only)                                                                                                                          |
| `bn.world.cells`         | `epoch`, `min`, `max`                                      | `at`, `cells`, `forgotten` (reads only)                                                                                                       |
| `bn.overmap.cells`       | `epoch`, `min`, `max`                                      | `overmap` squares of an overmap level, whatever the cursor (reads only)                                                                       |
| `bn.panel.view`          | `epoch`, `panel` (`character` or `inventory`), `row?`      | the `screen` as it opens on the avatar, `row` (a row or tab id) focused, every list row while it fits a frame, nothing to invoke (reads only) |
| `bn.command.submit`      | `epoch`, `expect`, `operation`                             | `command_id`, `stage: "received"`                                                                                                             |
| `bn.command.result`      | `epoch`, `command_id`                                      | latest stage, for recovering a lost notification                                                                                              |
| `bn.credit`              | `frames`                                                   | `credits` held after the grant                                                                                                                |

Notifications from the engine: `bn.snapshot.part`, `bn.events`, `bn.command`, `bn.resync`, `bn.loading`, `bn.progress`. All but `bn.loading` and `bn.progress` are sent at input boundaries to a subscribed client. `bn.progress` (`{epoch}`) is a heartbeat, sent every 2 seconds to a client that said `bn.hello` while a wait or other activity runs without reaching an input boundary, so silence on the wire means the engine is not working. `bn.loading` plays the same role while the world loads.

Errors use code `1000` with `error.data = {kind, action?, at?}`; `action` says what to do next (`hello`, `subscribe`, `retry`).

## Hello and the stack

The engine serves `"0.2"` only, on every transport. A hello that does not list `"0.2"` fails with `negotiation_failed` and `action: "hello"`. The hello must carry:

- `schema`: `sha256:` and the first 16 hex digits of the SHA-256 of the raw bytes of [`0.2.schema.json`](../../../schema/engine-client/0.2.schema.json). A different hash fails with `negotiation_failed`, `action: "hello"` and `error.data.schema = {engine, client}`. The engine takes its hash from the schema file when CMake configures.
- optional `locale` and `capabilities` (`tiles`, `tint_ids`, `viewport`, `delivery`; the members may also stand loose in the hello, but not both forms). The result adds `schema`, `locale` (the language of the connection's text), `engine_locale` and `role`. A `locale` the engine has no catalogue for fails with `unavailable_locale` and `action: "hello"`.

Every interaction boundary (snapshot header and events) carries `stack`, next to `interaction`. The stack is the open screens, outermost first; only the last has affordances. A screen's `kind` names what screen it is (`map`, `crafting`, `uilist`, ...), the same at every opening and in every language, so a client keys what it keeps per screen, such as a window's place, on it; a screen without `kind` is one the engine does not name yet. `bn.interaction.choices` with `component_id` reads that list of the top screen (`rows`, `total`).

`bn.command.submit` takes `operation: {kind: "invoke", affordance_id, args?}`. Its `expect` is the affordance's `expect` scope:

- `screen`: `{screen_id}`, valid while that screen is on top, else the command is rejected with `stale_screen`. The engine keeps up to 8 of these waiting (`limits.screen_queue` in the hello result) while a command runs and validates each when it takes its turn, so a held key keeps moving and keys aimed at a popup that has closed are rejected.
- `boundary`: `{boundary_id, revision}`, as before. While a command runs the submit fails with `command_busy`.

A form that does not match the affordance is `invalid_arguments`.

An affordance, row, tab or grid cell that is off and can be picked always carries a `denial`: the screen's reason in the player's language, else that it is not available now. A client shows it as the reason and adds none of its own.

A text with the `role` `prompt` is the question the parts after it in its split answer (a popup's or a menu's message), which a client shows above them. A row's `affordance` names the affordance of the screen that does what the row does (a popup's `YES`), present only while the screen offers it, so a client offers that action on the row and not again as a button. A panel never repeats its screen's `title`: where it would, its `title` is empty.

A grid that a client can draw with sprites carries `looks`, each look once, and each of its cells `looks`, indexes into them from the bottom up: what the square shows, as the world map's cells name it. The cell's `glyph` stands for them in text. The map editor's canvas and preview and the vehicle window's grid carry them. A grid of squares the player draws on has the role `canvas` and takes whatever room a client has; a grid that only shows or picks squares has none.

## Held keys

A step of the map carries `holdable`. A client sends `bn.hold` once when its key goes down and `bn.release` when it comes up, and never invokes it for key repeats. While a hold stands, the map is the screen on top and input is awaited, the engine gives the game one step of that action at each input prompt, as if the native key were pressed once more, and reads the requests the client has sent before each step. A tap owes one step even if released first. A popup or other screen on top, a step that changes neither the avatar's square nor the turn, a new `bn.hello` and a disconnect end the hold. `bn.hold` fails with `not_ready` during an activity, `stale_screen` for a screen that is not on top, `unknown_affordance` and `invalid_arguments` for an affordance that is missing or not holdable. Screen-scoped invokes still queue (a held arrow in a list).

## Delivery credits

Opt in with `bn.hello` `delivery = {credits, max_hz?}` (`credits` 1 to 256, optional `max_hz` 1 to 240). The result then carries `delivery = {credits, held_frames, held_bytes, max_hz?}`, `max_hz` echoed when asked for. Without `delivery` nothing below applies: pushed frames are written at once, at input boundaries and auto-move steps, as before.

- A pushed `bn.events` or `bn.command` frame costs one credit. With none left the engine keeps the frame, in order, and writes it when `bn.credit {frames}` grants more (the result is the credits held, capped at 256; the held frames follow the response). Snapshot parts, `bn.resync`, `bn.loading` and `bn.progress` cost nothing.
- The engine holds at most `held_frames` frames and `held_bytes` bytes for a client. Past either bound it drops the held `bn.events`, sends `bn.resync` with reason `backpressure` (`lost_after` is the newest sequence it wrote) and stops pushing events until the client calls `bn.subscribe`, whose snapshot replaces what was dropped. The held `bn.command` frames stay and follow the `bn.resync` as credits pay for them, and `bn.subscribe` drops only held events too, so the end of a command is never lost; only a client that leaves more stages unpaid than the bounds hold loses the oldest of them.
- A client with credits also receives frames while an activity runs (a wait, a craft), before the command completes. Capturing the world costs far more than a turn, so the engine publishes a running activity only as often as publishing takes a fifth of the activity's time, not after every turn; with `max_hz` it also publishes at most once per 1/`max_hz` seconds of wall time, whichever is sparser: a frame carries what changed since the previous one, state changes merged and every message and presentation fact in order, and the boundary where the activity ends carries the rest. `bn.command` `completed` still comes at that input boundary. The stream never waits for the client: a client that stops granting credits costs the engine at most the held bound, and the game, its RNG and its saves are the same as for a client that reads everything or none.
- Credits never make an activity wait: stdout is served like a socket, as the controller (see Sockets and spectators), so a credited frame goes to a buffer that is written without blocking, and the engine keeps reading stdin while stdout is full. A frame larger than the pipe waits at most 10 ms for the client to read it, so a client that reads it at once gets it whole; one that takes nothing in that time is not waited for again until it reads. A client that reads more slowly than the activity publishes runs out of credits and is resynced as above; one that leaves more than 16 MiB unread is dropped, as a socket is. Stdio has no next controller, so the engine then saves the game being played and exits. On Windows stdio is not served this way: a write returns only when the pipe has taken it, so an activity waits for a client that does not read what it has credits for.

## Framing and failure

- A frame is one JSON value on one line, at most `limits.frame_bytes` long in either direction. Frames are written whole by a single writer and never interleave; the engine reads one frame at a time and holds no more than that.
- A line that is not JSON is answered with `-32700`, JSON of the wrong shape with `-32600`, an unknown `bn.` method with `-32601` and bad params with `-32602`; the `id` is `null` when none could be read, and a notification gets no reply. Such a frame changes neither the game nor the held frames, and the connection stays open, also while an activity runs.
- A frame longer than the maximum, or one cut off by the end of stdin, cannot be answered: the engine reads no further, writes the reason on stderr and exits with code 1 (on a socket, only that connection ends).
- While an activity runs, requests are answered but start nothing. `bn.command.submit` fails with `not_ready` until the next input boundary, `bn.interrupt` is the one control the activity accepts, and `bn.viewport`, `bn.subscribe` and `bn.credit` change only what is delivered: the command stays open until the boundary where the activity ends. A repeated `bn.hello` renegotiates delivery, drops the held frames and unsubscribes, so the stream restarts at the next `bn.subscribe`.
- At shutdown (stdin ends, the game exits) the engine writes the held frames that credits pay for, in order, and drops the rest; the `interrupted` stage of an unfinished command is among them. `SIGTERM` and `SIGINT` end the engine at once, after naming the signal on stderr. A client that stops reading and closes its end ends the engine through the failed write.

## Sockets and spectators

`--client=mcp --listen <path>` serves the same protocol on a local stream socket instead of stdio: a Unix domain socket, and `AF_UNIX` on Windows 10 and later. Without the option nothing changes. The engine creates the file readable by its user only, replaces a stale file nothing answers on and refuses a path in use. Frames are the same lines, with the same limits. At most 8 connections are served; more are closed at once. A client can connect while the world loads and receives `bn.loading`.

- **Roles.** The first connection, and any connection made while there is none, is the controller: it alone may command the game. Every other connection is a spectator with its own `bn.hello`, credits, held frames (256 frames, 1 MiB) and subscription. A spectator reads everything the controller can, including the command stages and events of the controller's commands, but `bn.command.submit`, `bn.interrupt`, `bn.viewport` and the legacy `bn.press` and `bn.interact` fail with `read_only`, and its `bn.hello` leaves the controller's viewport and tile settings alone. A role never changes while connected; a spectator that wants control reconnects after the controller left.
- **No blocking.** Output goes to a buffer of the connection that is written without blocking (the controller's frame waits at most 10 ms for its reader, as on stdio), and a connection that leaves more than 16 MiB unsent is closed, unless credits stopped its stream earlier. The game waits only for the controller's input, as it does on stdio, and serves the spectators meanwhile, so a spectator that reads slowly or not at all never slows the game or the controller. Credits never make an activity wait on a socket.
- **Disconnect.** Closing a connection frees everything held for it, and nothing is kept for a reconnect: a client that comes back says `bn.hello` and `bn.subscribe` and continues from that snapshot, as after a `bn.resync`. A frame that is not JSON is answered as above and the connection stays open; a frame past the limit, or cut off by the close, ends that connection only, where on stdio it ends the engine.
- **The controller leaves.** Its open command is `interrupted`. A running activity goes on to its end, and then the game waits at its input boundary, as for a player who has not pressed a key, until a connection arrives; the next connection becomes the controller. Spectators stay connected and are told where the game stands. A closing socket never ends the engine: it ends as the game does, or by `SIGTERM` and `SIGINT`.

## One clock

- `epoch` changes when the process starts or the world is replaced, never on reads.
- `sequence` counts published events (decimal string, contiguous, starting at `"1"`). `revision` counts events that change state. `at = {epoch, sequence, revision}` means "includes every event up to sequence".
- A command carries `expect = {revision, boundary_id, schema_id}`. A stale value is rejected, so a client never acts on a screen it has not seen. `schema_id` is `null` exactly when the boundary has no interaction.

## Commands

`operation.kind` is one of `choose`, `fill`, `set_count`, `set_target`, `cancel` (semantic menus) `action` (a registered action such as a movement key), `travel` (a map click) or `tile_action` (an action on a map square, below).

```json
{ "kind": "choose", "choice_id": "tab:new_game" }
{ "kind": "set_target", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
{ "kind": "action", "action_id": "RIGHT" }
{ "kind": "travel", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
```

Every boundary action lists `keys`, the portable names (`ESC`, `SPACE`, `RETURN`, `UP`, `>`, ...) of the single keyboard keys the active input context binds to it; `action` runs an action by its id, also one without keys (such as `open_options` while unbound). A client that wants to act on a pressed key finds the action whose `keys` contain it instead of guessing from the key settings files.

`travel` is the left click of Tiles and curses on an absolute map square in view, at a boundary without interaction. The first click publishes the engine's own route as `route`; clicking the same square again starts native auto-move. The avatar then walks one step at a time, each step publishing ordinary events attached to that command, and stops where the engine stops (arrival, a monster coming into view, ...). The command is `completed` when the walk ends and input is awaited again. Any other command or a click elsewhere replaces or clears the plan. A client never computes routes.

The engine also decides what a click or a chore does with the squares and items it names. A left `travel` onto a closed door beside the avatar that the avatar can open is the move into it (native movement opens the door) instead of a route click. `pickup` and `drop` take `{ "kind": "pickup" | "drop", "item_id", "count" }`: `item_id` is the `id` of a row of `avatar.ground` (pickup) or `avatar.inventory` (drop), `count` how much of the row in its native units (charges of a charges item such as nails, else items), and the engine starts the native pickup or drop activity as the menus would after marking and confirming. A row id stays while the stack stays what it is; the command is rejected with `validation_failed` when the row is gone or holds less than `count`. A command that fails carries `error_text` (a command result or `bn.command`) or `message` (a JSON-RPC error `data`): the localized reason, more specific than `error` where the engine knows it (a travel target outside the map window, a count past the stack). The aiming screen (kind `target`: firing, throwing, reach attacks, spells and turrets), titled as the native one, is the `target` panel, whose stats are `range` (against the maximum, `bad` out of range), `elevation`, `targets` and the gun, aim, throw, spell or turret figures, over the `target:map` map. Its `target` carries `distance` (how far `current` is from `source` by `distance_metric`, the vertical axis included), `status` (`good`, `bad_target`, `out_of_ammo` or `out_of_range`), `status_text` (the localized range and readiness line), the `candidates` the cursor can jump to and the `parts` of the cursor square. `target:move` with a `pos` puts the cursor on that square; firing, the aim modes and the cursor keys are the registered actions. A popup that any key acknowledges and binds no key for names the choice to take in `interaction.any_key_choice_id`.

`context` is the right click (SEC_SELECT) on the same square: the native action examines an adjacent square, closes an adjacent door, picks up at the avatar, fires at a seen monster, or first cancels a planned route. `bn.world.describe` returns the text the native mouse view prints for a hovered square in the terrain window (`validation_failed` outside it); it selects and plans nothing. `bn.world.cells` returns what the avatar knows in a box of one level (`min` and `max` inclusive, same `dim` and `z`, at most `limits.cells_per_query` squares), the cells exactly as the snapshot holds them; `forgotten` lists the squares of the box inside the coverage that nothing is known about. An inverted box or one across levels is `validation_failed`, an oversized one `resource_limit`, and another `epoch` `stale_epoch`. A wheel step in a menu is the registered action `SCROLL_UP` or `SCROLL_DOWN` (the engine moves the native cursor by three rows).

`tile_action` takes one of the `actions` that `bn.world.describe` lists for a square, with `action_id` and `pos`, and does what the native action does on that square. The list holds only what applies now, in menu order, each with the native `label` and the player's `keys` (none for `attack`, `talk` and `travel`): `attack` (a seen creature beside the avatar that is not a friend), `fire` (a seen monster, with a ranged weapon wielded), `talk` (a seen character), `open`, `close`, `pickup` and `examine` (the avatar's square and the eight around it, where the native action finds something to do), `travel` (a square the avatar knows; it plans the route and starts walking it in one command) and `look` (always; it opens the look view on that square). An action the square does not list now is `validation_failed`. A client shows the list as the right-click menu of the square.

The map screen also carries `shortcuts`, the buttons of a shortcut bar. They are data (`client_shortcut` in the game's JSON: `id`, `action`, `icon`, `glyph`, `order`; a mod adds a button with a new id and replaces one by reusing its id): each names a registered action of the map's input context, and the engine publishes it with that context's `label` and `keys`, the data's `icon` (an opaque sprite id) and `glyph` (what to draw without art for it), and `enabled` while the map is on top and offers the action. A button the context names no action for is left out. The `editor` action opens the map editor; without the `DEBUG_EDITOR` trait it carries the `denial` `You need the Debug Editor trait.` The world map component also carries `item_lists`, the avatar's item lists a client shows beside the map in order, also while the map is covered: per list the avatar member holding its rows as `id` (`avatar.ground`, `avatar.inventory`), its heading as `label` and what moving a row out of it does as `verb` (pick up, drop), both localized. Its click is an `invoke` of the affordance named by `affordance_id`. A screen's affordances may carry the `role`s `navigate` (cursor, page, tab and scroll actions, which a client already reaches with keys, the wheel and clicks), `help` (the keybindings menu), `digit` (a typed digit of a counting list's count, read before any action bound to the key: as in the native list, it goes into the count the next mark takes, or opens the count prompt with it; a client need not draw it) and `layout` (an action that only resizes or rearranges the native window, which changes nothing the screen publishes: `TOGGLE_WIDE_DISPLAY` and `TOGGLE_FULL_HEIGHT_DISPLAY` of the message log, `TOGGLE_ITEM_INFO` of the trade window, `TOGGLE_EXPANDED` of the Lua console, `toggle_fullscreen` of the map; a client that lays out its own windows need not draw it) next to `confirm` and `cancel`.

Stages: `received`, `validated`, `executing`, `completed`; or `rejected`; or `interrupted`, whose `error` says why (`stale_epoch` when the world was replaced, `validation_failed` when the game refused the input, `not_ready` otherwise). Every stage comes with `stage_text`, its localized words (`Received.`, `Under way.`, `Refused.`, ...) for the player; `stage` stays the id to act on. `completed` means input is awaited again: a wait or other activity first runs to its end, or until the game asks something (a pop-up, an interruption); its `at` is the endpoint of that boundary. A prompt the input opens (a text field, an amount) is therefore in the state when `completed` arrives, since the events that carry it come first (after a `bn.resync`, the snapshot that follows carries it): a client that finds no prompt then knows none opened. One command is outstanding at a time (`command_busy`). While a wait or other activity runs, requests are still answered; `bn.interrupt` presses the native interrupt key, so the activity asks whether to stop as in Tiles, and that question is the next boundary. Outside an activity it fails with `not_ready`.

## Loading

While the world loads, the game thread is busy and reaches no input boundary, so a client that said `bn.hello` gets `bn.loading` instead, written at each step of the native loading screen (subscribed or not). Progress is the screen the native client shows: `title` is the current context (for example "Loading files"), `entries` its list, `index` the entry in progress (earlier ones are done) and `image` the loading image, chosen like the native client does. `image.path` is relative to the game's base path, `author` is omitted when the file name has none. `done` is sent once when the loading screen ends; after it the usual `bn.resync` or `bn.events` follow. `epoch` is the epoch in force when the step was sent.

```text
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","title":"Loading files","entries":["Terrain","Items"],"index":1,"image":{"path":"data/json/loading/Ada_dawn.webp","author":"Ada"}}}
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","done":true}}
```

## Values

- `pos = {dim, x, y, z}` is an absolute map square; `dim` is the game dimension, `""` for the primary one. Reality-bubble coordinates never appear on the wire.
- `look = {kind, id, glyph, color}` carries appearance from game data, so text clients need no tileset. Auto-wall terrain carries the line glyph for the connections the avatar knows, as the native text view draws it; a remembered cell keeps `memory.overlay` (furniture, trap or vehicle part) over `memory.terrain`.
- A `look` carries `name`, the translated player-facing name the native look shows ("wooden floor" for `t_floor`), so a text or speech client need not read ids; creatures use the entity's `name`. A tiled client draws the same `look`s with the game's tileset. The engine publishes what only it can know, because it owns the data and the native selection, and the client never reimplements it: `tile` (the sprite id when it is not `id`: `corpse_<monster>`, `player_male`, `vp_<part>`), `looks_like` (the data's fallback chain, nearest first), `subtile` and `rotation` (the multitile key and quarter turn the native selection computed from the neighbours the avatar knows, so connection logic exists once), `stack` (the displayed item of a pile), `attitude` and `aware` (monsters and NPCs, which the native view marks with an overlay), `health` (a hurt creature's native look-around bar: `fifths` filled and its `color`), `tint` (a vehicle part's paint, which a tileset blends into its sprites), `reviving` (the cell holds a corpse that can rise), `facing` (creatures), the cell's `light` (native `lit_level`: 0 dark, 1 low, 2 bright only, 3 lit, 4 bright), its `glow` (the colored light the native tiles view adds over its sprites: the light's `color` and its `strength`, 1 to 255), `environment.season` the avatar's `look` and, for characters, `overlays` (worn and wielded items, mutations, bionics as `look`s of kind `overlay` whose `tile` and `looks_like` list the sprite ids to try in the native order). The client owns what the tileset defines: files, weighted variants, layering and darkening. Layer order is terrain, furniture, trap, field, item, vehicle part, creature; the last entry of `fields` and `items` is the one the native view draws. `light` covers squares in sight only: the game's dark and bright-only levels (0 and 2) are squares the avatar cannot see, so a client draws its hidden-lighting sprite under every square without a plain view, and no `lowlight_dark` or `lowlight_light` fact is sent. A remembered cell draws darkened, a `light` of 1 shaded, and an id without a sprite falls back to its `glyph`.
- A mutation overlay carries `mutation` (the `id`, `types` and `flags` of the mutation), and an avatar or entity carries `traits` (the ids of its mutations by mutation type); a tileset's `tints` and `tint_pairs` are keyed by them to tint hair, skin and eyes. The environment lists `mod_tilesets`, the game data files that add sprites to tilesets, in the native load order, each with its `base` folder, its `index` in the file and the tilesets it is `compatibility`-listed for. A cell has `cargo` when a cargo part of a vehicle on it holds items; the native view highlights the part. The overlay of a worn or wielded item, a bionic or an effect carries `tint_keys`, the ids a tileset's `tints` are keyed by in the order the native view tries them (the flags, then the id). A hello may list `tint_ids`, the ids of the tints its tileset has; looks of terrain, furniture, monsters, vehicle parts and items then carry the `tint_keys` among them (flags, then id), and an item, terrain or furniture square with tint variables carries `tint_vars` (the color, blend and adjustments over the tileset's). A field look carries `tint`, the tint of its type, as the native view paints it. A field entry has `hides_items` when its type hides the items under it (smoke, fire, webs): while it is the displayed field the native tiles view draws neither the items nor their highlight.
- Terrain the game data flags as a wall (`WALL`) carries `wall: true`, in sight and in memory, so a client that draws a top-down tileset in 3D can raise walls without guessing from sprites. A window (`WINDOW`) also carries `window: true`, so such a client can leave its opening between a sill and a lintel. Terrain and furniture carry the `coverage` of their data, the percent of a person behind them they cover (1 to 100, absent for none), so such a client can raise what stands, such as a table or a shrub, by how much it covers.
- A square in sight on the level the `view` shows that the native tiles view looks through (open air and other terrain without a floor, such as treetops, glass roofs and ramps down) carries `below`, how many levels down the square is that the native tiles view draws there: the first square with a floor or with something remembered on it when it is in sight, remembered or a vehicle, else the lowest square in sight with something on it on the way down. That square is published as itself. The square looked through keeps what is on it, such as a field; bare open air carries nothing else, and bare open air with nothing seen through it is not published. Only squares in sight are looked through.

- A native query popup (a yes/no or other option query, a press-any-key notice) is the screen of kind `popup`, which has no view of its own: its components are the generic ones built from the native popup, in the `split:root` split when there are several. The `text:message` text (role `prompt` over the other parts) is the popup's text; an any-key popup has the `form:field` form, whose unlabelled `field:key` field of type `key` (the message says what the key is for) takes a key name as keybinding files spell it (`bn:fill:form:field`) and presses that key, and the `bn:any_key` affordance; the `list:choices` list has an `option:<action>` row per option (`#<n>` for the n-th with the same action) labelled with the action's name, with that registered action as `affordance` and no `description`, or the single `acknowledge` row `OK` of a popup without options, and Enter on a row (`bn:choose:list:choices`) answers with it. A cancellable popup has `bn:cancel`.
- The direction prompt (closing a door, prying, and every other action that asks for an adjacent square) is the screen of kind `direction`, titled `Choose direction`: the `direction` split of the `text:message` text (role `prompt`, the action's question) and the `direction:compass` grid, a cell per direction where it lies around the avatar's square (`x` and `y` from 0 to 2, north up, the avatar's own square in the middle) and, where the prompt offers them, above and below in a fourth column (`x` 3, `y` 0 and 2). A cell has the native short name as `glyph` (`N`, `NE`, ..., `CE`, `UP_CE`, `DN_CE`), the direction's name as `label` and `direction:choose` as `affordance`; `direction:choose` with a cell picks that direction and `bn:cancel` leaves. The direction keys of the map are the registered actions.
- The zone manager is the screen of kind `zones`, docked `overlapping` like the native window over the sidebar. It is a split of the `zones:list` panel (untitled under the screen's title `Zones`, the stat `No Zones defined.` while there is none) holding the `zones:rows` list, a row per zone named by its type and area (`zone:<type>:<start>:<end>`, with `#<n>` for the n-th alike before it), `toggled` while enabled, with the `type`, `distance`, `direction` and `vehicle` columns; the `zones:options` panel of the highlighted zone's options; and the `zones:display` list of `SHOW_ALL_ZONES`, `TOGGLE_ZONE_OVERLAY` and `debug_submap_grid`, `toggled` while on. `zones:pick` with a row moves the native cursor there and `zones:toggle` switches a display row; the zone actions are the registered actions, with a `denial` where the native key does nothing (a zone action without zones, a move with fewer than two). Picking the area of a zone (add, edit position, move position) is the `look` screen: its `target.status` is `zone_first`, `zone_second` or `zone_move` (`look` otherwise); `target:move` or the direction actions move the cursor and `CONFIRM` takes the square. The map editor is the screen of kind `editmap`, a target screen like `look` with `target.status` `editmap`: the cursor is the edited square, bounded by the loaded map, the `target` panel's `show_all` stat says whether the whole map is shown, the square's parts are its terrain, furniture, fields, trap, creature or vehicle and items with their ids and numbers, and the edit actions (`EDIT_TERRAIN`, `EDIT_FURNITURE`, `EDIT_TRAPS`, `EDIT_FIELDS`, `EDIT_ITEMS`, `EDIT_MONSTER`, `EDIT_OVERMAP`, `EDITMAP_SHOW_ALL`, `LEVEL_UP`, `LEVEL_DOWN`) are the registered actions; the editing menus are ordinary lists and `QUIT` leaves the editor. Shape selection (kind `editmap_shape`, `target.status` `editmap_shape_resize` or `editmap_shape_move`) and mapgen retargeting (kind `editmap_mapgen`, `target.status` `editmap_retarget`) are target screens of the same shape; `target:move` moves the cursor (and the selection while moving) and `RESIZE`, `SWAP`, `EDITMAP_MOVE`, `START`, `EDITMAP_SHOW_ALL` and `CONFIRM` are the registered actions. `target.marks` are the squares the native editor highlights: the `selection` the edits apply to, as `squares`; on the mapgen screens the `omt_border` of the targeted overmap terrain square, as a `rect`; and while a mapgen preview is open the `stamp`, the `rect` whose corners the native view marks around it. The editor screen keeps them while the mapgen lists are on top of it, and a client draws them over the map without changing what the avatar remembers.
- Settings screens are the native ones, opened from the main menu's `settings:options`, `settings:keybindings`, `settings:autopickup`, `settings:safemode`, `settings:distractions` and `settings:colors` rows (the options menu and the keybindings menu also open in the game). Options (kind `options`, role `screen`): the `options:pages` tabs, a page each by id (`general`, `interface`, `graphics`, ..., `world_default`, labelled `Current world` in the game; a world's own options are one page without tabs, titled `World options`), over the `options:body` detail split of the `options:items` list and the `options:detail` panel of the cursor row. The list has `group:<id>` rows (`toggled` while open) and `option:<NAME>` rows with a `value` column, their group as `parent_id` and a `denial` while a prerequisite is not met; the panel holds the `options:tooltip` text, in the game the `options:note` text on the world page, and for an option that can be set the `options:editor` form. Its one field, named by the row, is `bool` (`true`/`false`), `select` (one of `options[].id`), `integer` or `float` (within `min`/`max`) or `text` (at most `max_length`); `options:set` with that row and a text sets the option, and the engine refuses a value the field does not offer. `options:page` shows a page, `options:select` moves the cursor and `options:activate` is Enter on a row; leaving with `QUIT` asks the native "Save changes?" and saving applies and writes the options. Keybindings (kind `keybindings`): the `keybindings:window` panel (a `mode` stat outside the plain view, the `filter`) over the `keybindings:legend` text and the `keybindings:actions` list, an `action:<ID>` row per action with the `keys` and `scope` (`Unbound`, `Local` or `Global`) columns, colored as natively. The registered actions `ADD_LOCAL`, `ADD_GLOBAL`, `REMOVE` (and `EXECUTE` where the native menu offers it) select what `keybindings:pick` on a row does next, `keybindings:filter` with a text filters the actions by name in the plain view, and a prompt for a new key has a field of type `key` that takes a key name as keybinding files spell it (`z`, `=`, `F9`, `CTRL+A`). Autopickup (kind `auto_pickup`) and safe mode (kind `safemode`), both role `screen`: the `global` and `character` tabs (`autopickup:tabs`, `safemode:tabs`) over a `rule:<n>` row per rule (`<empty rule>` for an empty one) with the `i_e` and `active` columns, or `attitude`, `dist`, `whitelist`, `category` and `active`, beside the details panel with the enabled option as a stat over the pattern help. `autopickup:edit` and `autopickup:mode` edit a rule's text and its I/E, and `safemode:edit`, `safemode:attitude`, `safemode:dist`, `safemode:list` and `safemode:category` the matching column, as Enter on that column does; the rule actions (add, remove, move, test, ...) are the screen's registered actions, with a `denial` where there is no rule to act on, and testing a rule opens a dialog (`auto_pickup_test`, `safemode_test`) listing the items or monsters it matches. Distractions (kind `distraction_manager`): a `distraction:<name>` row per distraction, `toggled` while its `status` is `Enabled`, beside the `distractions:description` text; `distractions:toggle` (Enter) switches it. Colors (kind `colors`): the `colors:columns` tabs `normal` and `invert` over the `colors:items` list, a `color:<name>` row per color with the `normal`, `normal_custom`, `invert` and `invert_custom` columns, and the `colors:detail` panel with the `colors:note` text and the `colors:editor` form, a `select` field of the custom color in the shown column; `colors:set` with a color name sets it and `colors:activate` (Enter) opens the native color list.
- The auto notes manager is the screen of kind `auto_notes` (role `screen`), titled `AUTO NOTES MANAGER` with the native padding spaces: the `autonote:body` `detail` split of the `autonote:extras` list, an `extra:<map extra id>` row per discovered map extra with the `symbol` (in its map color) and `enabled` columns, `toggled` while its note is on, and the `autonote:status` panel, whose `enabled` stat `Auto notes enabled:` is `good` while the `AUTO_NOTES` option is on and `bad` otherwise; with nothing discovered the `autonote:notice` text follows and no row affordance is offered. `autonote:select` moves the cursor and Enter on a row (`autonote:toggle`) switches its note as `CONFIRM` does; `ENABLE_MAPEXTRA_NOTE`, `DISABLE_MAPEXTRA_NOTE` and `SWITCH_AUTO_NOTE_OPTION` are registered actions, and `QUIT` asks the native `Save changes?` when a note changed.
- `avatar.sidebar` is the native classic sidebar as values from the same getters, with the labels its panels print; a client lays it out and draws it itself. A text value is `{label, text, color}`: `label` is the translated panel label (absent where the panel prints none) and `color` the native color name where the color carries meaning. Members: `limbs` (`id`, `label` and its condition color, `hp`, `hp_max`, health `color`, `broken`), `pain`, `hunger`, `thirst`, `fatigue`, `temperature`, `power`, `location`, `weather` (unlabelled underground), `focus` (`label`, `value`), `morale` (`level`, native `face`), `stamina` (`label`, `current`, `max`, `color`), `speed` (`label`, `value`, `color`), `movement` (`counter`, `mode` of `walk`, `run`, `crouch` or `prone`, translated one-letter `mode_text`), `safe_mode` (`label`, `enabled`, `color`), `time` (`season`, `day_label`, `day`, `clock`: the watch time, else the approximate time of day, the native unknown-time text underground), optional `ambient_temperature` (thermometer only), `weapon` and optional wielded martial-arts `style`. Limb health and stamina are numbers, not bars: the client draws them in its own style. Texts are the engine's display language; the other values are language-neutral. `stats` entries may carry the native `color` and, for the four attributes, the sidebar's `short_label`.
- The terrain window is sized like a native window resize. `viewport = {cols, rows}` (1 to 512 map cells) in `bn.hello`, or later `bn.viewport`, resizes the terminal to those cells plus the side panels, so the engine shows that much map around the avatar; the effective `view` is authoritative because the native minimum terminal size still applies. A client that sends none gets the default terminal.
- Every event carries a generic `changes` block, applied in this order: `coverage`, `view`, `cells`, `forgotten`, `entities`, `gone`, then `avatar`, `environment`, `route` and `interaction` replace.
- To save bytes, a cell layer's `look` leaves out `kind`, which the layer already says (`terrain`, `furniture`, `trap`, `field`, `item`, `vehicle_part`; `memory.terrain` is `terrain`, while `memory.overlay` keeps its own), its `subtile` when it is `center` (the default of a shaped layer), and every `look` leaves out `rotation` when it is 0. The `interaction` of an event leaves out `actions` when they equal the previous boundary's: the client keeps its own, an empty list replaces them, and a snapshot always lists them.
- An event's `avatar` leaves out the members that equal the previous avatar's and are not empty, and names them in `keep` ("look", "overlays", "traits", "stats", "inventory", "sidebar", "ground"): the client keeps its own, and any other absent member is empty. A snapshot's avatar is always complete.
- `message.logged` is the native message log: `data = {id, text, kind, color, count, turn}`, one event per line in log order, attached to the command that caused it. `text` is the translated line without color tags and without the "x N" suffix; `kind` is the native type (`good`, `bad`, `mixed`, `warning`, `info`, `neutral`, `debug`) and `color` the native color name of that type. When the last line repeats, the same `id` is published again with a higher `count` and replaces the line. It changes no state (no `revision`) and, like every transient event, is lost across a `bn.resync`; the log itself is not: `bn.subscribe` returns the newest 100 lines as `messages` (oldest first, same shape as `data`, omitted when empty), so a client that subscribes after a load, or again after a resync, starts with the log the native client shows. Applying later `message.logged` events to that list (a repeat replaces the line with the same `id`, the oldest line falls off past 100) gives the list a fresh subscribe returns. Messages the native log hides by cooldown are not published. `label` is the line as the native log prints it, `text` followed by the translated repeat suffix (`x 2`) from a `count` of 2. `turn` is the game turn the line was logged on, or last repeated on, so a client can set the turns apart. A line made from a translatable format has a LocalisedString as `text` (`{key, ctx?, plural?, plural_key?, args?, npcname?}`: the msgid, its context, the count that picks the plural form, the plural msgid, the placeholder values in order, and what each `<npcname>` stands for once they are filled in), which a client words from the engine's catalogues in its own language; a name in it, such as a monster's, is a LocalisedString of its own, and a key no catalogue translates reads as `plural_key` for a `plural` other than one. A line about an NPC or a monster has its `npcname`: the NPC's name, or the monster's `the %s` LocalisedString. The snapshot names those catalogues as `catalogues`: the files of the connection's language on the engine's machine, the base game's and then the active mods', in lookup order (an earlier file's entry wins unless only a later one has plural forms); it is omitted for a language with none.
- `projectile.moved`, `explosion.started`, `explosion.blast`, `explosion.ended` and `combat_text.shown` are the native animation facts. They are published where the game starts an animation, so every client gets the same facts without a renderer. They change no state, are attached to the command that caused them, and arrive before the state event of that command. `display.duration_ms` is how long the native animation holds the fact (the `ANIMATION_DELAY` option per step). `projectile.moved` carries `path` (squares in drawing order; one square per event while a shot flies) and a `look` of kind `projectile` with its glyph and custom sprite id. `explosion.started` carries `at`, `radius`, `color` and the `tile` id the native tiles draw it with. Whether to draw them is the client's to decide, so the `ANIMATIONS` option does not silence them (a client never changes the game); only combat text needs `ANIMATION_SCT`. `explosion.blast` lists one ring of `cells` of an explosion shaped by terrain; a custom explosion (an EMP, a scrambler, a spell) lists its whole area at once with `colors`, the native color name of each cell in the same order. `combat_text.shown` is the floating text of one or two colored `segments` at `at`, which moves by `scroll` (a unit step) each animation step like the native text; `kind` `hp` marks a creature's hit-point readout, which stays beside it.
- A thrown item is told as game events too, which the animation options do not silence; each is published only for what the avatar sees. `item.activated` (`at`, `look`, and `turns`, the whole turns left on a fuse) comes when the fuse is lit and again every turn it burns. `item.thrown` (`projectile`, `look`, `by`, `from`, `to`) opens the flight, whose `projectile.moved` events carry the same `projectile`, and `item.landed` (`at`, `look`, `projectile` when an attack launched it) closes it. A thrown or fired projectile has the same `projectile` in its `projectile.hit` (`at`, and `entity` when the avatar sees the creature struck; an obstacle has none), which follows its `projectile.moved` and comes before the `entity.damaged` and the terrain changes it caused. The pellets of one multishot (a shotgun shell) fly one after another, each with its own `projectile`, and their events come in that order; their `projectile.moved`, `projectile.hit` and `item.landed` carry the same `group`, so a client can present the pellets together as the native game does. An explosion is `explosion.started`, then for every logical time step its `explosion.blast` or `explosion.shrapnel` ring followed by what the step did, then `explosion.ended`: `entity.damaged` (`id`, `amount`, and `part` for a character) for each hit a creature takes, `terrain.changed` and `furniture.changed` (`at`, the `from` and `to` looks) for a square the step changed, and `field.changed` (`at`, `field`, `intensity` afterwards, 0 when the field is gone) for each field it added or removed. `entity.damaged` follows every damage a creature takes, including damage applied directly. Terrain, furniture and field changes are told wherever the game makes them, not only in explosions: at the shared map boundary for every call that changes a square the avatar sees (bashing a door, setting furniture, adding or removing a field), and for the field turn (fire spreading, gas drifting, fields fading, also over skipped turns) by comparing the fields the avatar sees on its level before and after, one `field.changed` per square that differs. A square told after a long wait is told once.
- `sound.heard` (`text`, `volume`, `marker`, `logged`) is a sound that reached the avatar through the native hearing rules: its volume against the ambient noise, hearing protection, sleep and deafness. `text` is the description the native message names, `volume` the decibels the avatar hears it at, and `marker` the square the native game marks it on. The marker is never the source: it is a square out of the avatar's sight near it, and it is left out when the avatar is or sees the source, so a hidden source is not given away. The log line of a sound follows the native message rules and the cooldown; `sound.heard` is published for every sound heard, including those the log leaves out, such as footsteps. `logged` is `true` when the sound also has a line in the message log, so a client that shows both lists the sound once. The avatar's own shout counts as logged, since its action logs its own line (`You yell ...`).
- `sound.played`, `sound.channel` and `music.changed` are what the native sound player is asked to play, told whether or not the engine plays audio itself. The client plays them from the sound pack in the folder the hello names as `engine.sound.soundpack` (absent while the `SOUND_ENABLED` option is off), the way the native player does. `sound.played` (`id`, `variant`, `volume`, `angle`, `stacks`, `wait_ms`) is one `sound_effect` of the pack: a pack without the variant plays the effect's `default` variant, one of the effect's `files` is picked at random, `stacks` `false` skips the sound while the same one still plays, and a sound with `wait_ms` (footsteps, obstacles, gunshots) plays only once that many milliseconds passed since the last one with `wait_ms` played, then starts the wait again. `sound.channel` (`channel`, `id`, `variant`, `volume`, `gain`, `angle`, `loops`, `fade_ms`) is what a reserved channel (ambience, weather, danger themes, engines, the radio) plays now: a new sound starts with a fade-in of `fade_ms`, the same `id` and `variant` keep playing at the new `gain` (a volume change, in mixer units with no option or pack volume applied) or `angle`, and a channel without `id` fades out over `fade_ms`; channel `any` fades out every channel and sound effect. The first stream starts with the channels and the music that already play; a stream of a new `epoch` goes on from what the one before told. A channel still playing a sound that does not repeat until it stops (`loops` 0 or more) ignores a new start. `music.changed` (`playlist`, `volume`) names the pack's playlist to play, in order or shuffled as the playlist says; without `playlist` the music stops. `volume` is in mixer units (128 is the full gain) with the native `SOUND_EFFECT_VOLUME`, `AMBIENT_SOUND_VOLUME` or `MUSIC_VOLUME` option applied, and the pack's own `volume` (0-100) of the effect or playlist entry scales it. `angle` is clockwise degrees from straight ahead (90 is to the right) where the native mixer places the sound. An engine built without sound (`SOUND=OFF`) publishes none of them.
- `entity.moved` (`id`, `to`, `from`, `mode`) and `entity.gone` (`id`, `reason`) let a client follow creatures through an action without a resync, for the monsters and NPCs the snapshot discloses. `entity.moved` is published for every move of a creature the avatar sees at its new square; `from` is left out when the avatar did not see the square it came from, and `mode` is `walk` for a step to a neighboring square and `propelled` for any longer move (a shove, a teleport). The avatar's own moves are in the state delta. `entity.gone` says a creature the client knew is no longer disclosed: `lost_sight` (it stepped out of sight, or the avatar moved or the view changed), `died`, or `removed` (it left the game). A creature that steps out of sight is `gone` at once; the rest are found when the boundary is published. A busy turn publishes the first 256 `entity.moved`, `terrain.changed`, `furniture.changed` and `field.changed` events (the `gone` ones of creatures that step out of sight count too); the `cells.seen` change set of the boundary always holds the final state, so the events add order and timing and never replace it.

Events are `interaction.changed`, `coverage.moved`, `turn.passed`, `cells.seen`, `message.logged` the animation facts above and, later, the remaining presentation types listed in the schema. Event types added before 0.2 is released belong to 0.2; once it is released, a new event type needs a new exact version.
