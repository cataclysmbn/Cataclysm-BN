---
title: Engine/client protocol 0.2
---

An external client plays the game over newline-delimited JSON-RPC 2.0 on the stdio of `cataclysm-bn-tiles --client=mcp`. The values are defined by the [Draft 2020-12 schema](../../../schema/engine-client/0.2.schema.json), and every example below is checked against it in the [examples files](../../../schema/engine-client/0.2.examples/). The legacy MCP tools (`bn.observe`, `bn.press`, ...) are a separate, unchanged surface; once a client says `bn.hello`, they refuse input.

## A session

```text
-> {"jsonrpc":"2.0","id":1,"method":"bn.hello","params":{"versions":["0.2"],"client":{"name":"my-client","version":"1"},"schema":"sha256:0123456789abcdef"}}
<- {"jsonrpc":"2.0","id":1,"result":{"version":"0.2","epoch":"epoch:e7f3","engine":{"build":"...","mods":["bn"],"display":{"tiles":true,"tileset":"UNDEAD_PEOPLE_BASE"},"sound":{"soundpack":"/opt/bn/data/sound/Basic"}},"limits":{"frame_bytes":1048576,"cells_per_part":512,"cells_per_query":4096,"screen_queue":8},"schema":"sha256:0123456789abcdef","locale":"en","engine_locale":"en","role":"controller"}}
-> {"jsonrpc":"2.0","id":2,"method":"bn.subscribe","params":{}}
<- {"jsonrpc":"2.0","id":2,"result":{"at":{"epoch":"epoch:e7f3","sequence":"40","revision":"31"},"interaction":{...},"entities":[],"parts":1}}
<- {"jsonrpc":"2.0","method":"bn.snapshot.part","params":{"epoch":"epoch:e7f3","at":{...},"index":0,"last":true,"cells":[...]}}
-> {"jsonrpc":"2.0","id":3,"method":"bn.command.submit","params":{"epoch":"epoch:e7f3","expect":{"revision":"31","boundary_id":"boundary:90","schema_id":null},"operation":{"kind":"action","action_id":"RIGHT"}}}
<- {"jsonrpc":"2.0","id":3,"result":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"received"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"validated"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"executing"}}
<- {"jsonrpc":"2.0","method":"bn.events","params":{"epoch":"epoch:e7f3","events":[{"sequence":"41","revision":"32","type":"interaction.changed","command":"c:5","changes":{...}}]}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"completed","at":{"epoch":"epoch:e7f3","sequence":"41","revision":"32"}}}
```

Collect the `parts` snapshot parts, then apply `bn.events` in order. A gap, an epoch mismatch or `bn.resync` means: call `bn.subscribe` again. A new snapshot restores state only; transient events after `lost_after` are lost, never replayed. The engine keeps no event history: after `bn.unsubscribe`, or after falling behind, `bn.subscribe` is the only way back, and its snapshot (never a replay) supersedes the last seen `(epoch, sequence)`. A `bn.resync` stops only the events: the `bn.command` stages keep coming, since no snapshot carries them, and a stage may follow a newer snapshot than its `at`. Stages are pushed from `bn.subscribe` until `bn.unsubscribe` or `bn.hello`; read the outcome of a command outside that span with `bn.command.result`. Any request that names a stale `epoch` fails with `stale_epoch` and `action: "subscribe"`.

## Methods

| Method                   | Params                                                     | Result                                                                                           |
| ------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `bn.hello`               | `versions`, `client`, `schema`, `locale?`, `capabilities?` | `version`, `epoch`, `engine`, `limits`, `delivery?`, `schema`, `locale`, `engine_locale`, `role` |
| `bn.viewport`            | `cols`, `rows`                                             | none                                                                                             |
| `bn.interrupt`           | none                                                       | none                                                                                             |
| `bn.hold`                | `epoch`, `screen_id`, `affordance_id`                      | none                                                                                             |
| `bn.release`             | none                                                       | none                                                                                             |
| `bn.subscribe`           | none                                                       | snapshot header; parts and events follow                                                         |
| `bn.unsubscribe`         | none                                                       | none                                                                                             |
| `bn.interaction.choices` | `epoch`, `boundary_id`, `offset`, `limit`                  | `boundary_id`, `total`, `choices` (reads only)                                                   |
| `bn.world.describe`      | `epoch`, `boundary_id`, `pos`                              | `lines` (reads only)                                                                             |
| `bn.world.cells`         | `epoch`, `min`, `max`                                      | `at`, `cells`, `forgotten` (reads only)                                                          |
| `bn.overmap.cells`       | `epoch`, `min`, `max`                                      | `overmap` squares of an overmap level, whatever the cursor (reads only)                          |
| `bn.command.submit`      | `epoch`, `expect`, `operation`                             | `command_id`, `stage: "received"`                                                                |
| `bn.command.result`      | `epoch`, `command_id`                                      | latest stage, for recovering a lost notification                                                 |
| `bn.credit`              | `frames`                                                   | `credits` held after the grant                                                                   |

Notifications from the engine: `bn.snapshot.part`, `bn.events`, `bn.command`, `bn.resync`, `bn.loading`, `bn.progress`. All but `bn.loading` and `bn.progress` are sent at input boundaries to a subscribed client. `bn.progress` (`{epoch}`) is a heartbeat, sent every 2 seconds to a client that said `bn.hello` while a wait or other activity runs without reaching an input boundary, so silence on the wire means the engine is not working. `bn.loading` plays the same role while the world loads.

Errors use code `1000` with `error.data = {kind, action?, at?}`; `action` says what to do next (`hello`, `subscribe`, `retry`).

## Hello and the stack

The engine serves `"0.2"` only, on every transport. A hello that does not list `"0.2"` fails with `negotiation_failed` and `action: "hello"`. The hello must carry:

- `schema`: `sha256:` and the first 16 hex digits of the SHA-256 of the raw bytes of [`0.2.schema.json`](../../../schema/engine-client/0.2.schema.json). A different hash fails with `negotiation_failed`, `action: "hello"` and `error.data.schema = {engine, client}`. The engine takes its hash from the schema file when CMake configures.
- optional `locale` and `capabilities` (`tiles`, `tint_ids`, `viewport`, `delivery`; the members may also stand loose in the hello, but not both forms). The result adds `schema`, `locale` (the language of the connection's text), `engine_locale` and `role`. A `locale` the engine has no catalogue for fails with `unavailable_locale` and `action: "hello"`.

Every interaction boundary (snapshot header and events) carries `stack`, next to `interaction`. The stack is the open screens, outermost first; only the last has affordances. A screen's `kind` names what screen it is (`map`, `crafting`, `uilist`, ...), the same at every opening and in every language, so a client keys what it keeps per screen, such as a window's place, on it; a screen without `kind` is one the engine does not name yet. `bn.interaction.choices` with `component_id` reads that list of the top screen (`rows`, `total`).

`bn.command.submit` takes `operation: {kind: "invoke", affordance_id, args?}`. Its `expect` is the affordance's `expect` scope:

- `screen`: `{screen_id}`, valid while that screen is on top, else the command is rejected with `stale_screen`. The engine keeps up to 8 of these waiting (`limits.screen_queue` in the hello result) while a command runs and validates each when it takes its turn, so a held key keeps moving and keys aimed at a popup that has closed are rejected.
- `boundary`: `{boundary_id, revision}`, as before. While a command runs the submit fails with `command_busy`.

A form that does not match the affordance is `invalid_arguments`.

An affordance, row, tab or grid cell that is off and can be picked always carries a `denial`: the screen's reason in the player's language, else that it is not available now. A client shows it as the reason and adds none of its own.

## Held keys

A step of the map carries `holdable`. A client sends `bn.hold` once when its key goes down and `bn.release` when it comes up, and never invokes it for key repeats. While a hold stands, the map is the screen on top and input is awaited, the engine gives the game one step of that action at each input prompt, as if the native key were pressed once more, and reads the requests the client has sent before each step. A tap owes one step even if released first. A popup or other screen on top, a step that changes neither the avatar's square nor the turn, a new `bn.hello` and a disconnect end the hold. `bn.hold` fails with `not_ready` during an activity, `stale_screen` for a screen that is not on top, `unknown_affordance` and `invalid_arguments` for an affordance that is missing or not holdable. Screen-scoped invokes still queue (a held arrow in a list).

## Delivery credits

Opt in with `bn.hello` `delivery = {credits, max_hz?}` (`credits` 1 to 256, optional `max_hz` 1 to 240). The result then carries `delivery = {credits, held_frames, held_bytes, max_hz?}`, `max_hz` echoed when asked for. Without `delivery` nothing below applies: pushed frames are written at once, at input boundaries and auto-move steps, as before.

- A pushed `bn.events` or `bn.command` frame costs one credit. With none left the engine keeps the frame, in order, and writes it when `bn.credit {frames}` grants more (the result is the credits held, capped at 256; the held frames follow the response). Snapshot parts, `bn.resync`, `bn.loading` and `bn.progress` cost nothing.
- The engine holds at most `held_frames` frames and `held_bytes` bytes for a client. Past either bound it drops the held `bn.events`, sends `bn.resync` with reason `backpressure` (`lost_after` is the newest sequence it wrote) and stops pushing events until the client calls `bn.subscribe`, whose snapshot replaces what was dropped. The held `bn.command` frames stay and follow the `bn.resync` as credits pay for them, and `bn.subscribe` drops only held events too, so the end of a command is never lost; only a client that leaves more stages unpaid than the bounds hold loses the oldest of them.
- A client with credits also receives frames while an activity runs (a wait, a craft), before the command completes. Capturing the world costs far more than a turn, so the engine publishes a running activity only as often as publishing takes a fifth of the activity's time, not after every turn; with `max_hz` it also publishes at most once per 1/`max_hz` seconds of wall time, whichever is sparser: a frame carries what changed since the previous one, state changes merged and every message and presentation fact in order, and the boundary where the activity ends carries the rest. `bn.command` `completed` still comes at that input boundary. The stream never waits for the client: a client that stops granting credits costs the engine at most the held bound, and the game, its RNG and its saves are the same as for a client that reads everything or none.
- Credits never make an activity wait: stdout is served like a socket, as the controller (see Sockets and spectators), so a credited frame goes to a buffer that is written without blocking, and the engine keeps reading stdin while stdout is full. A frame larger than the pipe waits at most 10 ms for the client to read it, so a client that reads it at once gets it whole; one that takes nothing in that time is not waited for again until it reads. A client that reads more slowly than the activity publishes runs out of credits and is resynced as above; one that leaves more than 16 MiB unread is dropped, as a socket is. Stdio has no next controller, so the engine then saves the game being played and exits. On Windows stdio is not served this way: a write returns only when the pipe has taken it, so an activity waits for a client that does not read what it has credits for.

## Framing and failure

- A frame is one JSON value on one line, at most `limits.frame_bytes` long in either direction. Frames are written whole by a single writer and never interleave; the engine reads one frame at a time and holds no more than that.
- A line that is not JSON is answered with `-32700`, JSON of the wrong shape with `-32600`, an unknown `bn.` method with `-32601` and bad params with `-32602`; the `id` is `null` when none could be read, and a notification gets no reply. Such a frame changes neither the game nor the held frames, and the connection stays open, also while an activity runs.
- A frame longer than the maximum, or one cut off by the end of stdin, cannot be answered: the engine reads no further, writes the reason on stderr and exits with code 1 (on a socket, only that connection ends).
- While an activity runs, requests are answered but start nothing. `bn.command.submit` fails with `not_ready` until the next input boundary, `bn.interrupt` is the one control the activity accepts, and `bn.viewport`, `bn.subscribe` and `bn.credit` change only what is delivered: the command stays open until the boundary where the activity ends. A repeated `bn.hello` renegotiates delivery, drops the held frames and unsubscribes, so the stream restarts at the next `bn.subscribe`.
- At shutdown (stdin ends, the game exits) the engine writes the held frames that credits pay for, in order, and drops the rest; the `interrupted` stage of an unfinished command is among them. `SIGTERM` and `SIGINT` end the engine at once, after naming the signal on stderr. A client that stops reading and closes its end ends the engine through the failed write.

## Sockets and spectators

`--client=mcp --listen <path>` serves the same protocol on a local stream socket instead of stdio: a Unix domain socket, and `AF_UNIX` on Windows 10 and later. Without the option nothing changes. The engine creates the file readable by its user only, replaces a stale file nothing answers on and refuses a path in use. Frames are the same lines, with the same limits. At most 8 connections are served; more are closed at once. A client can connect while the world loads and receives `bn.loading`.

- **Roles.** The first connection, and any connection made while there is none, is the controller: it alone may command the game. Every other connection is a spectator with its own `bn.hello`, credits, held frames (256 frames, 1 MiB) and subscription. A spectator reads everything the controller can, including the command stages and events of the controller's commands, but `bn.command.submit`, `bn.interrupt`, `bn.viewport` and the legacy `bn.press` and `bn.interact` fail with `read_only`, and its `bn.hello` leaves the controller's viewport and tile settings alone. A role never changes while connected; a spectator that wants control reconnects after the controller left.
- **No blocking.** Output goes to a buffer of the connection that is written without blocking (the controller's frame waits at most 10 ms for its reader, as on stdio), and a connection that leaves more than 16 MiB unsent is closed, unless credits stopped its stream earlier. The game waits only for the controller's input, as it does on stdio, and serves the spectators meanwhile, so a spectator that reads slowly or not at all never slows the game or the controller. Credits never make an activity wait on a socket.
- **Disconnect.** Closing a connection frees everything held for it, and nothing is kept for a reconnect: a client that comes back says `bn.hello` and `bn.subscribe` and continues from that snapshot, as after a `bn.resync`. A frame that is not JSON is answered as above and the connection stays open; a frame past the limit, or cut off by the close, ends that connection only, where on stdio it ends the engine.
- **The controller leaves.** Its open command is `interrupted`. A running activity goes on to its end, and then the game waits at its input boundary, as for a player who has not pressed a key, until a connection arrives; the next connection becomes the controller. Spectators stay connected and are told where the game stands. A closing socket never ends the engine: it ends as the game does, or by `SIGTERM` and `SIGINT`.

## One clock

- `epoch` changes when the process starts or the world is replaced, never on reads.
- `sequence` counts published events (decimal string, contiguous, starting at `"1"`). `revision` counts events that change state. `at = {epoch, sequence, revision}` means "includes every event up to sequence".
- A command carries `expect = {revision, boundary_id, schema_id}`. A stale value is rejected, so a client never acts on a screen it has not seen. `schema_id` is `null` exactly when the boundary has no interaction.

## Commands

`operation.kind` is one of `choose`, `fill`, `set_count`, `set_target`, `cancel` (semantic menus) `action` (a registered action such as a movement key), `travel` (a map click) or `tile_action` (an action on a map square, below).

```json
{ "kind": "choose", "choice_id": "tab:new_game" }
{ "kind": "set_target", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
{ "kind": "action", "action_id": "RIGHT" }
{ "kind": "travel", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
```

Every boundary action lists `keys`, the portable names (`ESC`, `SPACE`, `RETURN`, `UP`, `>`, ...) of the single keyboard keys the active input context binds to it; `action` runs an action by its id, also one without keys (such as `open_options` while unbound). A client that wants to act on a pressed key finds the action whose `keys` contain it instead of guessing from the key settings files.

`travel` is the left click of Tiles and curses on an absolute map square in view, at a boundary without interaction. The first click publishes the engine's own route as `route`; clicking the same square again starts native auto-move. The avatar then walks one step at a time, each step publishing ordinary events attached to that command, and stops where the engine stops (arrival, a monster coming into view, ...). The command is `completed` when the walk ends and input is awaited again. Any other command or a click elsewhere replaces or clears the plan. A client never computes routes.

The engine also decides what a click or a chore does with the squares and items it names. A left `travel` onto a closed door beside the avatar that the avatar can open is the move into it (native movement opens the door) instead of a route click. `pickup` and `drop` take `{ "kind": "pickup" | "drop", "item_id", "count" }`: `item_id` is the `id` of a row of `avatar.ground` (pickup) or `avatar.inventory` (drop), `count` how much of the row in its native units (charges of a charges item such as nails, else items), and the engine starts the native pickup or drop activity as the menus would after marking and confirming. A row id stays while the stack stays what it is; the command is rejected with `validation_failed` when the row is gone or holds less than `count`. A command that fails carries `error_text` (a command result or `bn.command`) or `message` (a JSON-RPC error `data`): the localized reason, more specific than `error` where the engine knows it (a travel target outside the map window, a count past the stack). A target interaction (`context` `TARGET`) carries `target.distance` (how far `current` is from `source` by `distance_metric`, the vertical axis included) and, where the screen reports range, `target.status_text` (the localized range and readiness line). A screen that any key acknowledges and binds no key for (the press-any-key popups, the computer terminal prompt) names the choice to take in `interaction.any_key_choice_id`.

`context` is the right click (SEC_SELECT) on the same square: the native action examines an adjacent square, closes an adjacent door, picks up at the avatar, fires at a seen monster, or first cancels a planned route. `bn.world.describe` returns the text the native mouse view prints for a hovered square in the terrain window (`validation_failed` outside it); it selects and plans nothing. `bn.world.cells` returns what the avatar knows in a box of one level (`min` and `max` inclusive, same `dim` and `z`, at most `limits.cells_per_query` squares), the cells exactly as the snapshot holds them; `forgotten` lists the squares of the box inside the coverage that nothing is known about. An inverted box or one across levels is `validation_failed`, an oversized one `resource_limit`, and another `epoch` `stale_epoch`. A wheel step in a menu is the registered action `SCROLL_UP` or `SCROLL_DOWN` (the engine moves the native cursor by three rows).

`tile_action` takes one of the `actions` that `bn.world.describe` lists for a square, with `action_id` and `pos`, and does what the native action does on that square. The list holds only what applies now, in menu order, each with the native `label` and the player's `keys` (none for `attack`, `talk` and `travel`): `attack` (a seen creature beside the avatar that is not a friend), `fire` (a seen monster, with a ranged weapon wielded), `talk` (a seen character), `open`, `close`, `pickup` and `examine` (the avatar's square and the eight around it, where the native action finds something to do), `travel` (a square the avatar knows; it plans the route and starts walking it in one command) and `look` (always; it opens the look view on that square). An action the square does not list now is `validation_failed`. A client shows the list as the right-click menu of the square.

The map screen also carries `shortcuts`, the buttons of a shortcut bar. They are data (`client_shortcut` in the game's JSON: `id`, `action`, `icon`, `glyph`, `order`; a mod adds a button with a new id and replaces one by reusing its id): each names a registered action of the map's input context, and the engine publishes it with that context's `label` and `keys`, the data's `icon` (an opaque sprite id) and `glyph` (what to draw without art for it), and `enabled` while the map is on top and offers the action. A button the context names no action for is left out. The world map component also carries `item_lists`, the avatar's item lists a client shows beside the map in order, also while the map is covered: per list the avatar member holding its rows as `id` (`avatar.ground`, `avatar.inventory`), its heading as `label` and what moving a row out of it does as `verb` (pick up, drop), both localized. Its click is an `invoke` of the affordance named by `affordance_id`. A screen's affordances may carry the `role`s `navigate` (cursor, page, tab and scroll actions, which a client already reaches with keys, the wheel and clicks) and `help` (the keybindings menu) next to `confirm` and `cancel`.

Stages: `received`, `validated`, `executing`, `completed`; or `rejected`; or `interrupted`, whose `error` says why (`stale_epoch` when the world was replaced, `validation_failed` when the game refused the input, `not_ready` otherwise). Every stage comes with `stage_text`, its localized words (`Received.`, `Under way.`, `Refused.`, ...) for the player; `stage` stays the id to act on. `completed` means input is awaited again: a wait or other activity first runs to its end, or until the game asks something (a pop-up, an interruption); its `at` is the endpoint of that boundary. A prompt the input opens (a text field, an amount) is therefore in the state when `completed` arrives, since the events that carry it come first (after a `bn.resync`, the snapshot that follows carries it): a client that finds no prompt then knows none opened. One command is outstanding at a time (`command_busy`). While a wait or other activity runs, requests are still answered; `bn.interrupt` presses the native interrupt key, so the activity asks whether to stop as in Tiles, and that question is the next boundary. Outside an activity it fails with `not_ready`.

## Loading

While the world loads, the game thread is busy and reaches no input boundary, so a client that said `bn.hello` gets `bn.loading` instead, written at each step of the native loading screen (subscribed or not). Progress is the screen the native client shows: `title` is the current context (for example "Loading files"), `entries` its list, `index` the entry in progress (earlier ones are done) and `image` the loading image, chosen like the native client does. `image.path` is relative to the game's base path, `author` is omitted when the file name has none. `done` is sent once when the loading screen ends; after it the usual `bn.resync` or `bn.events` follow. `epoch` is the epoch in force when the step was sent.

```text
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","title":"Loading files","entries":["Terrain","Items"],"index":1,"image":{"path":"data/json/loading/Ada_dawn.webp","author":"Ada"}}}
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","done":true}}
```

## Values

- `pos = {dim, x, y, z}` is an absolute map square; `dim` is the game dimension, `""` for the primary one. Reality-bubble coordinates never appear on the wire.
- `look = {kind, id, glyph, color}` carries appearance from game data, so text clients need no tileset. Auto-wall terrain carries the line glyph for the connections the avatar knows, as the native text view draws it; a remembered cell keeps `memory.overlay` (furniture, trap or vehicle part) over `memory.terrain`.
- A `look` carries `name`, the translated player-facing name the native look shows ("wooden floor" for `t_floor`), so a text or speech client need not read ids; creatures use the entity's `name`. A tiled client draws the same `look`s with the game's tileset. The engine publishes what only it can know, because it owns the data and the native selection, and the client never reimplements it: `tile` (the sprite id when it is not `id`: `corpse_<monster>`, `player_male`, `vp_<part>`), `looks_like` (the data's fallback chain, nearest first), `subtile` and `rotation` (the multitile key and quarter turn the native selection computed from the neighbours the avatar knows, so connection logic exists once), `stack` (the displayed item of a pile), `attitude` and `aware` (monsters and NPCs, which the native view marks with an overlay), `tint` (a vehicle part's paint, which a tileset blends into its sprites), `reviving` (the cell holds a corpse that can rise), `facing` (creatures), the cell's `light` (native `lit_level`: 0 dark, 1 low, 2 bright only, 3 lit, 4 bright), its `glow` (the colored light the native tiles view adds over its sprites: the light's `color` and its `strength`, 1 to 255), `environment.season` the avatar's `look` and, for characters, `overlays` (worn and wielded items, mutations, bionics as `look`s of kind `overlay` whose `tile` and `looks_like` list the sprite ids to try in the native order). The client owns what the tileset defines: files, weighted variants, layering and darkening. Layer order is terrain, furniture, trap, field, item, vehicle part, creature; the last entry of `fields` and `items` is the one the native view draws. `light` covers squares in sight only: the game's dark and bright-only levels (0 and 2) are squares the avatar cannot see, so a client draws its hidden-lighting sprite under every square without a plain view, and no `lowlight_dark` or `lowlight_light` fact is sent. A remembered cell draws darkened, a `light` of 1 shaded, and an id without a sprite falls back to its `glyph`.
- A mutation overlay carries `mutation` (the `id`, `types` and `flags` of the mutation), and an avatar or entity carries `traits` (the ids of its mutations by mutation type); a tileset's `tints` and `tint_pairs` are keyed by them to tint hair, skin and eyes. The environment lists `mod_tilesets`, the game data files that add sprites to tilesets, in the native load order, each with its `base` folder, its `index` in the file and the tilesets it is `compatibility`-listed for. A cell has `cargo` when a cargo part of a vehicle on it holds items; the native view highlights the part. The overlay of a worn or wielded item, a bionic or an effect carries `tint_keys`, the ids a tileset's `tints` are keyed by in the order the native view tries them (the flags, then the id). A hello may list `tint_ids`, the ids of the tints its tileset has; looks of terrain, furniture, monsters, vehicle parts and items then carry the `tint_keys` among them (flags, then id), and an item, terrain or furniture square with tint variables carries `tint_vars` (the color, blend and adjustments over the tileset's). A field look carries `tint`, the tint of its type, as the native view paints it. A field entry has `hides_items` when its type hides the items under it (smoke, fire, webs): while it is the displayed field the native tiles view draws neither the items nor their highlight.
- Terrain the game data flags as a wall (`WALL`) carries `wall: true`, in sight and in memory, so a client that draws a top-down tileset in 3D can raise walls without guessing from sprites.
- A square in sight on the avatar's level that the native tiles view looks through (open air and other terrain without a floor, such as treetops, glass roofs and ramps down) carries `below`, how many levels down the square is that the native tiles view draws there: the first square with a floor or with something remembered on it when it is in sight, remembered or a vehicle, else the lowest square in sight with something on it on the way down. That square is published as itself. The square looked through keeps what is on it, such as a field; bare open air carries nothing else, and bare open air with nothing seen through it is not published. Only squares in sight are looked through.
- `interaction` is the native menu or dialog: every `columns` entry has a `key`, its stable untranslated name (the English caption in lower case with `_` between words, such as `spell_level`; an inventory cell is `cell0`, `cell1`, ...), and a `label`, the translated caption; clients look a column up by `key` only. A column may carry `color`, the native color name of its value. A choice may also carry `favorite` (a favorite spell), `color` and `key_color` (color names of the row text and its `hotkey`), `markup` (the name with native color tags), `mark` (`glyph` `+`, `#` or `-`, and `color`) where the native list prints a selection mark, and `parent_id` and `nest_color` where it draws a nesting slash. `choices` holds up to the first 200 rows, fewer when they would be too large; read the rest with `bn.interaction.choices` starting at `offset = choices.length`. `choice_total` is the full count. `compat.focus` and `compat.panes` keep native list state for 1:1 ports; clients may ignore them. A pane of the advanced inventory manager also carries `sort` (the native sort name) and `totals` (the header the native pane prints: `weight`, `volume`, and for capacity-bound areas `weight_max`/`volume_max`, with `weight_unit`, `volume_unit`, `over_weight`, `over_volume`; a max is empty where native shows none). The main menu is tabbed like the native one: every tab is a choice without `pane_id` (`tab:new_game`, `tab:load`, ...; the selected one has `selected`), followed by the entries of the selected tab only, each with that tab's `pane_id` (`new_game:tutorial`, `settings:options`, `load:<world>`). Choosing another tab publishes a new interaction with that tab's entries; ids never depend on position or language. The crafting menu (`context` `CRAFTING`) is tabbed the same way: category tabs (`tab:CC_ELECTRONIC`), then the sub-tabs of the selected category (`subtab:CSC_ELECTRONIC_TOOLS`, absent while a search is active), then its recipes (`recipe:<hash>`), the last two with the category as `pane_id`. Choosing a tab or sub-tab lists that group; choosing a recipe crafts it; `set_count` on a recipe starts batch mode. Each recipe carries its native detail text (skills, time, tools, components) as `description` without color markup. The construction menu (`context` `CONSTRUCTION`, key `*`) has the same shape: category tabs (`tab:<category id>`, one `tab:FILTER` while a search is active), then one `construction:<hash>` row per construction group with `Favorite` and `Buildable` columns and a `denial` when it cannot be built. Each row carries its requirements as `description` without color markup: per variant the result, required skills, required terrain, time, speed modifiers, tools and components with what is missing. `filter` is the native search. Choosing a row starts the native placement, which then asks for the adjacent tile. The `filter` field is the native search; `fill` it with `submit: true` to search and with an empty value to clear. A menu whose native callback tests raw keys itself (the wish menus, the technique menu) lists them first, before the entries, as `action:key:<keycode>` rows labelled with the key's name; `choose` one to press that key, so they are on the first page of a long menu. The spell menu publishes, on each spell row, the details its native side panel draws: `description` (class, text, level, difficulty, experience, cost, time, targets, damage, area, range, duration and components, with color markup) and `columns` `Spell Level`, `Failure Chance`, `Casting Cost`, `Casting Time` and `Range`, and `favorite` on a favorite spell; its keys to toggle a favorite, toggle casting distractions and assign a hotkey are `action:key:<keycode>` rows. The menus whose native callback draws a side panel (martial art styles, the wish menus for mutations, monsters and items, the effect picker, the translocator gates, a spellbook's spells) put that panel's text, with color markup, in the row's `description` after the row's own description; the panels that cost a lookup per row (martial art styles, wish monsters, wish items) fill only the selected row. A row the native list prints a key before (a menu entry's hotkey, an inventory item's letter) has `hotkey`, that key as text; pressing it chooses the row natively. The NPC trade window also publishes `category_mode` (whether category selection is on) on the interaction, `page` (`number`, `count`) on each pane, and `hotkey` only on the rows of the shown page. The inventory selectors (`context` `INVENTORY`, the `i` screen and the item pickers) and the ground pickup list publish one pane with `role` `inventory` or `pickup`: `area_label` is the native title, `area_description` the hint under it, `filter` the active filter and `totals` the carried (or, for pickup, predicted) weight and volume against capacity, absent where the native window prints none. Each inventory row carries `source` (`inventory`, `map_or_vehicle`, `worn_or_wielded`), the native cells after it, then `category` (the header the row sits under); the row's `color`, `key_color`, `markup` and, in a multi-select selector, `mark` are typed fields; `category_mode` is on while the selector is in category selection. Pickup rows carry the key the native list prints as `hotkey`, a backtick and two letters past the single letters, and none past those. A pickup row's `markup` is the row as the native list prints it: the stack size, the `ITEM_SYMBOLS` glyph and a `<color_light_red>!</color>` before an item that is not the avatar's; its `label` stays plain. The pickup pane's `area_id` is the `PICKUP_POSITION` option (`left`, `right`, `overlapping` or `cursor`), and its `totals` flag `over_weight`/`over_volume` where the native header prints red. The advanced inventory manager also carries `areas`, its area picker as the native header lays it out: per area the `action_id` that points the active pane at it, the localized `label` (a pane is on the area whose `label` is its `area_label`), `key` (the key the player has bound to that action, empty when none; rebinding it changes what clients show), `x` and `y` (character cells from the picker's top-left corner) and `available` (the area exists now: the vehicle is grabbed or on the square, the level is there). The action buttons are named by the registered actions' `name`. A choice may carry `action_id`, the registered action the row runs; the in-game main menu's rows have it, so its Options row is `open_options` in any language. The pickup list's `message` is the native header with color tags (`<color_c_red>` around a predicted weight or volume over capacity), then the filter on a second line.
- The world is what the avatar knows: `cells` (`remembered`, `visible` or `sensed`), `entities`, `avatar` (stats, `inventory`, `ground` and the `activity` it is busy with: its `name` and, for one of a set length, the thousandths `done`), `environment`, the loaded `coverage`, the `view` and the pending `route` (empty or absent when nothing is planned) with its localized `route_text` (such as `Route of 3 squares; select its end again to go.`, absent with the route). `view` is the native terrain window as `{min, max}` squares of the avatar's level (it follows the avatar): a `travel` click is accepted only inside it, anything else is rejected with `validation_failed`.
- `avatar.inventory` lists the wielded item, the worn items, then the carried stacks, each `{look, name, count?, slot, durability?}` with `slot` one of `wielded`, `worn` or `carried`; `avatar.ground` lists the stacks on the avatar's own square in the same shape without `slot`. `count` is how much the row holds in native units, charges of a charges item, else items: the most a `pickup` or `drop` of the row takes. `name` is the display name the native lists show, without color markup; `durability`, present when `name` starts with the native condition marker, gives that marker as `{symbol, color}` so a client can draw it in its color. Both arrays are absent when empty. Each row also has `label`, the row as the native lists word it: the stack's display name with its count and condition marker as color markup, then `(wielded)` or `(worn)` in the player's language.
- The character screens publish native values and colors, not text. `PLAYER_INFO` (`@`) lists its six tabs (`stats`, `encumbrance`, `skills`, `traits`, `bionics`, `effects`) as choices without `pane_id`, then the rows of every tab with that tab's `pane_id`. A column's `color` is the native color name of its value, and a trait or bionic row's `color` that of its name. A stat row's value is the `current` column. The speed breakdown is the rows with `pane_id` `speed`, each unselectable with a `value` column carrying `color`. This version's sheet has no proficiencies tab. `BIONICS` (`p`) names the `active` and `passive` tabs in `panes` (`role` `current` or `inactive`) and lists the rows of the current tab only; `NEXT_TAB` and `PREV_TAB` switch tabs. Its bionic rows carry the shortcut as `hotkey`, the row `color`, and the columns `power` (activation, trigger and upkeep cost), `state` (`On`, `Off`, `Passive` or `Incapacitated`) and `fuel` (`name: stored/capacity`); `REASSIGN`, `TOGGLE_EXAMINE`, `TOGGLE_SAFE_FUEL`, `TOGGLE_SPRITE`, `TOGGLE_AUTO_START` and `SORT` stay registered actions. `MUTATIONS` (`[`) puts its rows in the `passive` and `active` panes and the `action:` rows in `actions`; a row carries `Kind`, `Key`, `State`, `Sprite`, `Innate`, `Cost` and `Cooldown` columns and the row `color`, and choosing it activates or deactivates it natively.
- The overmap (`m`, action `map`) is an interaction of kind `target` with `context` `OVERMAP`. `overmap` carries the native window as drawn: `cols`, `rows`, `cells[row][col] = [glyph, foreground, background]` (curses color indexes 0-15: 0 black, 1 red, 2 green, 3 brown, 4 blue, 5 magenta, 6 cyan, 7 light gray, 8-15 their bright forms), `origin` (the square in the top-left cell), `player`, the sidebar text as `legend` lines and the `notes` in view. The window is centered on the cursor, `target.current`; `target.unit` is `"omt"`, so every position in this interaction is an absolute overmap terrain square, not a map square. `set_target` with a `pos` moves the cursor (any square within the engine's bounds, any level from -10 to 10), `cancel` closes the screen, and the native overmap actions (`CHOOSE_DESTINATION` to travel, `CREATE_NOTE`, `LEVEL_UP`/`LEVEL_DOWN`, `ZOOM_IN`, the toggles, ...) are the registered actions of the boundary. The overlays (player, notes, paths) are shown steadily, since a client cannot blink them. `path` is the planned travel route. A client that said `"tiles": true` in `bn.hello` also gets `tiles`: per cell `[tile, rotation, subtile]` (the `overmap_terrain` tile id, quarter turns and multitile key the native tiles view selects) and the `looks_like` fallbacks of each tile id; other clients never receive them. A client that switches between tiles and ASCII within a session sends `bn.hello` again with the new `tiles` value, at a time no command is running (otherwise `command_busy`), and then `bn.viewport` with its current size, which makes the engine publish the open screen again with or without the ids. `cursor_description` is what the native sidebar says of the cursor square, localized, without the window frame or the square's glyph. `cursor_here` (`You are here.` when the cursor is on the player's square), `cursor_note` (`Note:` followed by the text the native window prints in its corner for the cursor square's note, such as `Note: cache`) and `route_text` (the length of `path`, such as `Route of 2 squares.`) are localized engine lines, each absent when it does not apply.
- The vehicle window (`^`, `context` `VEH_INTERACT`) is a `choices` interaction with a `vehicle` object: the `cells` of the grid around the cursor part (`dx`, `dy` in screen cells relative to the cursor, `glyph`, game `color` name), the `parts` on the cursor square (`name` with contents, the `open`/`close` marks of its layer, `health`, `broken`), the native `stats` lines (an empty line is a blank slot), `cursor` in the vehicle's frame, `blocked`, `owner` and `owned`. `mode` is `main`, a task list (`install`, `repair`, `remove`, `mend`, `refill`) or `select` (siphon, crew and the like). On the main screen the choices are the native actions (`action:INSTALL`, `action:REPAIR`, ...) with `enabled` and, when denied, the `denial` the native message gives, and the cursor moves (`action:UP`, ...). In a task list the choices are the candidate parts, `part:<index>` with `highlighted` on the native cursor, and the install list also has `tab:<index>` choices with `vehicle.tabs`. `vehicle.detail` previews the highlighted part: `time`, part `stats`, `requirements` (`kind` `skill`, `component`, `tool` or `extra`, a component or tool row lists its alternatives joined with OR, `met`) and `can_do`. `choose` on the highlighted part starts the task natively; `choose` on another part only moves the highlight, so a client can show its requirements first; the highlighted row is `enabled: false` with a `denial` while a requirement is unmet. `cancel` goes back one level. `vehicle.verb` is the localized task verb (`Install`, `Repair`, ...) and is absent on the main screen. `detail.groups` lists the requirement headings in print order (`kind`, localized `heading`, and `empty_text` such as `NONE` to print when no requirement has that kind; an empty one leaves the group out then), and `detail.time_heading` heads `time`.
- A computer terminal (`context` `COMPUTER_TERMINAL` at an any-key prompt, `YESNOQUIT` at a query) is a `choices` interaction whose `title` is the computer's name and whose `message` is the terminal text as the native window prints it (`\n` between lines, color tags kept). The any-key prompt has the one choice `continue`; a query has `yes`, `no` and `quit`. `choose` answers like the key and `cancel` ends the prompt (a quit at a query). The root menu of a terminal is an ordinary list of its options. The extended description (`context` `EXTENDED_DESCRIPTION`) has the description of the current target as `message` and the choices `describe:creature`, `describe:furniture` and `describe:terrain`, the current one `selected`; `choose` switches the target and `cancel` closes it.
- The software mini-games (snake, minesweeper, Sokoban, Lights on, robotfindskitten; `context` `SNAKE`, `MINESWEEPER`, `SOKOBAN`, `LIGHTSON`, `IUSE_SOFTWARE_KITTEN`) are `custom` interactions with no choices whose `title` names the game and whose `canvas` is the game window as drawn: `rows`, one list of `[text, foreground, background]` runs per window row (curses color indexes 0-15 as in the overmap, the blank cells that end a row left out) and `cols`, its width. The game's keys are the registered actions of the boundary (`UP`, `FLAG`, `CONFIRM`, `QUIT`, ...), and a key without an action is a raw key `text` command. `canvas` is not part of `schema_id`, so a redraw does not make a command stale. A timed game (snake) has `refresh_ms`, the interval its native input wait runs for: the engine itself ends that wait when no command arrives within it, lets the game move, and publishes the redrawn `canvas` as an ordinary `interaction.changed` event, so a client only draws what it receives. A command sent while a refresh lands can be rejected as `stale_boundary`; resend it with the new `boundary_id`. robotfindskitten shows its ending animation as frames of `refresh_ms` 1000, and every state but those frames offers the choice `acknowledge` (description `ANY_INPUT`): choosing it is a key with no action, which the field answers with its invalid command line.
- The zone manager (`context` `ZONES_MANAGER`) is a `choices` interaction with three panes: `zones` (a `zone:<n>` row per zone, `selected` while enabled, with `Type`, `Distance`, `Direction` and `Vehicle` columns), `options` (the option rows of the highlighted zone, unselectable, with a `Value` column) and `actions` (`action:<ID>` rows with the native `hotkey` and a `Key` column; `enabled` is false where the native key does nothing, such as a move with fewer than two zones; `SHOW_ALL_ZONES`, `TOGGLE_ZONE_OVERLAY` and `debug_submap_grid` are `selected` while on). `choose` on a zone row moves the native cursor. Picking the area of a zone (add, edit position, move position) is the look `target` interaction: its `message` is `Select first point.`, `Select second point.` or `Moving zone.` and `target.status` is `zone_first`, `zone_second` or `zone_move` (`look` otherwise); `target.description` is the text the native look window prints of the cursor square, wrapped at 60 columns, one localized line per entry; the cursor moves with the registered direction actions or `set_target` (any square of the loaded map) and `CONFIRM` takes the square. The map editor (`context` `EDITMAP`) is a `target` interaction with `status` `editmap`: `target.cursor` is the edited square and `set_target` moves it to any square of the loaded map. Its `tile` pane lists what is on the square (`tile:terrain`, `tile:furniture`, `tile:field:<id>`, `tile:trap`, `tile:creature` or `tile:vehicle`, `tile:items`; the name is the `description`, ids and numbers are `columns`) and its `actions` pane the edit actions (`EDIT_TERRAIN`, `EDIT_FURNITURE`, `EDIT_TRAPS`, `EDIT_FIELDS`, `EDIT_ITEMS`, `EDIT_MONSTER`, `EDIT_OVERMAP`, `EDITMAP_SHOW_ALL` selected while the whole map is shown, `LEVEL_UP`, `LEVEL_DOWN`) with their `hotkey`; the editing menus are ordinary lists and `cancel` leaves the editor. Shape selection (`context` `EDITMAP_SHAPE`) and mapgen retargeting (`context` `EDITMAP_RETARGET`) are `target` interactions of the same shape with `status` `editmap_shape_resize`, `editmap_shape_move` or `editmap_retarget`; `set_target` moves the cursor (and the selection while moving), and their `actions` pane lists the native actions (`RESIZE`, `SWAP`, `EDITMAP_MOVE`, `START`, `EDITMAP_SHOW_ALL`, `CONFIRM`).
- Settings screens are the native ones, opened from `settings:options`, `settings:keybindings`, `settings:autopickup`, `settings:safemode`, `settings:distractions` and `settings:colors` (the options menu and the keybindings menu also open in the game). A row with an `editor` can be set directly: `fill` with `field_id` = the row's `choice_id`, `value` in the editor's form and `submit: true`. `editor.type` is `bool` (`true`/`false`), `select` (one of `values[].id`), `integer` or `float` (within `minimum`/`maximum`) or `text` (at most `max_length`); the engine refuses anything the native menu would not take. `choose` on a row does what Enter does natively. Options: tab rows `page:<id>`, then `option:<NAME>` and `group:<id>` rows of the selected page; leaving with `cancel` asks the native "Save changes?" and saving applies and writes the options. Keybindings: `mode:add_local`, `mode:add_global`, `mode:remove` (and `mode:execute` where the native menu offers it) select what the next `action:<ID>` row does, the field filters actions by name, and a prompt for a new key has a field of type `key` that takes a key name as keybinding files spell it (`z`, `=`, `F9`, `CTRL+A`). Autopickup and safe mode: tab rows `page:<n>`, column rows `column:<n>` and `rule:<n>` rows; rule actions (add, remove, move, ...) are the screen's registered actions. Distractions: `distraction:<name>` rows with a `bool` editor (true: interrupts). Colors: `column:<n>` and `color:<name>` rows; choosing a color opens the native color list.
- The world is what the avatar knows: `cells` (`remembered`, `visible` or `sensed`), `entities`, `avatar` (stats and `inventory`), `environment`, the loaded `coverage`, the `view` and the pending `route` (empty or absent when nothing is planned) with its localized `route_text` (such as `Route of 3 squares; select its end again to go.`, absent with the route). `view` is the native terrain window as `{min, max}` squares of the avatar's level (it follows the avatar): a `travel` click is accepted only inside it, anything else is rejected with `validation_failed`.
- `avatar.sidebar` is the native classic sidebar as values from the same getters, with the labels its panels print; a client lays it out and draws it itself. A text value is `{label, text, color}`: `label` is the translated panel label (absent where the panel prints none) and `color` the native color name where the color carries meaning. Members: `limbs` (`id`, `label` and its condition color, `hp`, `hp_max`, health `color`, `broken`), `pain`, `hunger`, `thirst`, `fatigue`, `temperature`, `power`, `location`, `weather` (unlabelled underground), `focus` (`label`, `value`), `morale` (`level`, native `face`), `stamina` (`label`, `current`, `max`, `color`), `speed` (`label`, `value`, `color`), `movement` (`counter`, `mode` of `walk`, `run`, `crouch` or `prone`, translated one-letter `mode_text`), `safe_mode` (`label`, `enabled`, `color`), `time` (`season`, `day_label`, `day`, `clock`: the watch time, else the approximate time of day, the native unknown-time text underground), optional `ambient_temperature` (thermometer only), `weapon` and optional wielded martial-arts `style`. Limb health and stamina are numbers, not bars: the client draws them in its own style. Texts are the engine's display language; the other values are language-neutral. `stats` entries may carry the native `color` and, for the four attributes, the sidebar's `short_label`.
- The terrain window is sized like a native window resize. `viewport = {cols, rows}` (1 to 512 map cells) in `bn.hello`, or later `bn.viewport`, resizes the terminal to those cells plus the side panels, so the engine shows that much map around the avatar; the effective `view` is authoritative because the native minimum terminal size still applies. A client that sends none gets the default terminal.
- Every event carries a generic `changes` block, applied in this order: `coverage`, `view`, `cells`, `forgotten`, `entities`, `gone`, then `avatar`, `environment`, `route` and `interaction` replace.
- To save bytes, a cell layer's `look` leaves out `kind`, which the layer already says (`terrain`, `furniture`, `trap`, `field`, `item`, `vehicle_part`; `memory.terrain` is `terrain`, while `memory.overlay` keeps its own), its `subtile` when it is `center` (the default of a shaped layer), and every `look` leaves out `rotation` when it is 0. The `interaction` of an event leaves out `actions` when they equal the previous boundary's: the client keeps its own, an empty list replaces them, and a snapshot always lists them.
- An event's `avatar` leaves out the members that equal the previous avatar's and are not empty, and names them in `keep` ("look", "overlays", "traits", "stats", "inventory", "sidebar", "ground"): the client keeps its own, and any other absent member is empty. A snapshot's avatar is always complete.
- `message.logged` is the native message log: `data = {id, text, kind, color, count, turn}`, one event per line in log order, attached to the command that caused it. `text` is the translated line without color tags and without the "x N" suffix; `kind` is the native type (`good`, `bad`, `mixed`, `warning`, `info`, `neutral`, `debug`) and `color` the native color name of that type. When the last line repeats, the same `id` is published again with a higher `count` and replaces the line. It changes no state (no `revision`) and, like every transient event, is lost across a `bn.resync`; the log itself is not: `bn.subscribe` returns the newest 100 lines as `messages` (oldest first, same shape as `data`, omitted when empty), so a client that subscribes after a load, or again after a resync, starts with the log the native client shows. Applying later `message.logged` events to that list (a repeat replaces the line with the same `id`, the oldest line falls off past 100) gives the list a fresh subscribe returns. Messages the native log hides by cooldown are not published. `label` is the line as the native log prints it, `text` followed by the translated repeat suffix (`x 2`) from a `count` of 2. `turn` is the game turn the line was logged on, or last repeated on, so a client can set the turns apart.
- `projectile.moved`, `explosion.started`, `explosion.blast`, `explosion.ended` and `combat_text.shown` are the native animation facts. They are published where the game starts an animation, so every client gets the same facts without a renderer. They change no state, are attached to the command that caused them, and arrive before the state event of that command. `display.duration_ms` is how long the native animation holds the fact (the `ANIMATION_DELAY` option per step). `projectile.moved` carries `path` (squares in drawing order; one square per event while a shot flies) and a `look` of kind `projectile` with its glyph and custom sprite id. `explosion.started` carries `at`, `radius`, `color` and the `tile` id the native tiles draw it with. Whether to draw them is the client's to decide, so the `ANIMATIONS` option does not silence them (a client never changes the game); only combat text needs `ANIMATION_SCT`. `explosion.blast` lists one ring of `cells` of an explosion shaped by terrain. `combat_text.shown` is the floating text of one or two colored `segments` at `at`, which moves by `scroll` (a unit step) each animation step like the native text; `kind` `hp` marks a creature's hit-point readout, which stays beside it.
- A thrown item is told as game events too, which the animation options do not silence; each is published only for what the avatar sees. `item.activated` (`at`, `look`, and `turns`, the whole turns left on a fuse) comes when the fuse is lit and again every turn it burns. `item.thrown` (`projectile`, `look`, `by`, `from`, `to`) opens the flight, whose `projectile.moved` events carry the same `projectile`, and `item.landed` (`at`, `look`, `projectile` when an attack launched it) closes it. A thrown or fired projectile has the same `projectile` in its `projectile.hit` (`at`, and `entity` when the avatar sees the creature struck; an obstacle has none), which follows its `projectile.moved` and comes before the `entity.damaged` and the terrain changes it caused. An explosion is `explosion.started`, then for every logical time step its `explosion.blast` or `explosion.shrapnel` ring followed by what the step did, then `explosion.ended`: `entity.damaged` (`id`, `amount`, and `part` for a character) for each hit a creature takes, `terrain.changed` and `furniture.changed` (`at`, the `from` and `to` looks) for a square the step changed, and `field.changed` (`at`, `field`, `intensity` afterwards, 0 when the field is gone) for each field it added or removed. `entity.damaged` follows every damage a creature takes, including damage applied directly. Terrain, furniture and field changes are told wherever the game makes them, not only in explosions: at the shared map boundary for every call that changes a square the avatar sees (bashing a door, setting furniture, adding or removing a field), and for the field turn (fire spreading, gas drifting, fields fading, also over skipped turns) by comparing the fields the avatar sees on its level before and after, one `field.changed` per square that differs. A square told after a long wait is told once.
- `sound.heard` (`text`, `volume`, `marker`, `logged`) is a sound that reached the avatar through the native hearing rules: its volume against the ambient noise, hearing protection, sleep and deafness. `text` is the description the native message names, `volume` the decibels the avatar hears it at, and `marker` the square the native game marks it on. The marker is never the source: it is a square out of the avatar's sight near it, and it is left out when the avatar is or sees the source, so a hidden source is not given away. The log line of a sound follows the native message rules and the cooldown; `sound.heard` is published for every sound heard, including those the log leaves out, such as footsteps. `logged` is `true` when the sound also has a line in the message log, so a client that shows both lists the sound once. The avatar's own shout counts as logged, since its action logs its own line (`You yell ...`).
- `sound.played`, `sound.channel` and `music.changed` are what the native sound player is asked to play, told whether or not the engine plays audio itself. The client plays them from the sound pack in the folder the hello names as `engine.sound.soundpack` (absent while the `SOUND_ENABLED` option is off), the way the native player does. `sound.played` (`id`, `variant`, `volume`, `angle`, `stacks`) is one `sound_effect` of the pack: a pack without the variant plays the effect's `default` variant, one of the effect's `files` is picked at random, and `stacks` `false` skips the sound while the same one still plays. `sound.channel` (`channel`, `id`, `variant`, `volume`, `gain`, `angle`, `loops`, `fade_ms`) is what a reserved channel (ambience, weather, danger themes, engines, the radio) plays now: a new sound starts with a fade-in of `fade_ms`, the same `id` and `variant` keep playing at the new `gain` (a volume change, in mixer units with no option or pack volume applied) or `angle`, and a channel without `id` fades out over `fade_ms`; channel `any` fades out every channel and sound effect. The first stream starts with the channels and the music that already play; a stream of a new `epoch` goes on from what the one before told. A channel still playing a sound that does not repeat until it stops (`loops` 0 or more) ignores a new start. `music.changed` (`playlist`, `volume`) names the pack's playlist to play, in order or shuffled as the playlist says; without `playlist` the music stops. `volume` is in mixer units (128 is the full gain) with the native `SOUND_EFFECT_VOLUME`, `AMBIENT_SOUND_VOLUME` or `MUSIC_VOLUME` option applied, and the pack's own `volume` (0-100) of the effect or playlist entry scales it. `angle` is clockwise degrees from straight ahead (90 is to the right) where the native mixer places the sound. An engine built without sound (`SOUND=OFF`) publishes none of them.
- `entity.moved` (`id`, `to`, `from`, `mode`) and `entity.gone` (`id`, `reason`) let a client follow creatures through an action without a resync, for the monsters and NPCs the snapshot discloses. `entity.moved` is published for every move of a creature the avatar sees at its new square; `from` is left out when the avatar did not see the square it came from, and `mode` is `walk` for a step to a neighboring square and `propelled` for any longer move (a shove, a teleport). The avatar's own moves are in the state delta. `entity.gone` says a creature the client knew is no longer disclosed: `lost_sight` (it stepped out of sight, or the avatar moved or the view changed), `died`, or `removed` (it left the game). A creature that steps out of sight is `gone` at once; the rest are found when the boundary is published. A busy turn publishes the first 256 `entity.moved`, `terrain.changed`, `furniture.changed` and `field.changed` events (the `gone` ones of creatures that step out of sight count too); the `cells.seen` change set of the boundary always holds the final state, so the events add order and timing and never replace it.

Events are `interaction.changed`, `coverage.moved`, `turn.passed`, `cells.seen`, `message.logged` the animation facts above and, later, the remaining presentation types listed in the schema. Event types added before 0.2 is released belong to 0.2; once it is released, a new event type needs a new exact version.
