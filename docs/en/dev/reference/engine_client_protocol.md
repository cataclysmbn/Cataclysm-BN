---
title: Engine/client protocol 0.2
---

An external client plays the game over newline-delimited JSON-RPC 2.0 on the stdio of `cataclysm-bn-tiles --client=mcp`. The values are defined by the [Draft 2020-12 schema](../../../schema/engine-client/0.2.schema.json), and every example below is checked against it in the [examples files](../../../schema/engine-client/0.2.examples/). The legacy MCP tools (`bn.observe`, `bn.press`, ...) are a separate, unchanged surface; once a client says `bn.hello`, they refuse input.

## A session

```text
-> {"jsonrpc":"2.0","id":1,"method":"bn.hello","params":{"versions":["0.2"],"client":{"name":"my-client","version":"1"},"schema":"sha256:0123456789abcdef"}}
<- {"jsonrpc":"2.0","id":1,"result":{"version":"0.2","epoch":"epoch:e7f3","engine":{"build":"...","mods":["bn"],"display":{"tiles":true,"tileset":"UNDEAD_PEOPLE_BASE"},"sound":{"soundpack":"/opt/bn/data/sound/Basic"}},"limits":{"frame_bytes":1048576,"cells_per_part":512,"cells_per_query":4096,"screen_queue":8},"schema":"sha256:0123456789abcdef","locale":"en","engine_locale":"en","role":"controller"}}
-> {"jsonrpc":"2.0","id":2,"method":"bn.subscribe","params":{}}
<- {"jsonrpc":"2.0","id":2,"result":{"at":{"epoch":"epoch:e7f3","sequence":"40","revision":"31"},"interaction":{...},"entities":[],"parts":1}}
<- {"jsonrpc":"2.0","method":"bn.snapshot.part","params":{"epoch":"epoch:e7f3","at":{...},"index":0,"last":true,"cells":[...]}}
-> {"jsonrpc":"2.0","id":3,"method":"bn.command.submit","params":{"epoch":"epoch:e7f3","expect":{"revision":"31","boundary_id":"boundary:90","schema_id":null},"operation":{"kind":"action","action_id":"RIGHT"}}}
<- {"jsonrpc":"2.0","id":3,"result":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"received"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"validated"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"executing"}}
<- {"jsonrpc":"2.0","method":"bn.events","params":{"epoch":"epoch:e7f3","events":[{"sequence":"41","revision":"32","type":"interaction.changed","command":"c:5","changes":{...}}]}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"completed","at":{"epoch":"epoch:e7f3","sequence":"41","revision":"32"}}}
```

Collect the `parts` snapshot parts, then apply `bn.events` in order. A gap, an epoch mismatch or `bn.resync` means: call `bn.subscribe` again. A new snapshot restores state only; transient events after `lost_after` are lost, never replayed. The engine keeps no event history: after `bn.unsubscribe`, or after falling behind, `bn.subscribe` is the only way back, and its snapshot (never a replay) supersedes the last seen `(epoch, sequence)`. A `bn.resync` stops only the events: the `bn.command` stages keep coming, since no snapshot carries them, and a stage may follow a newer snapshot than its `at`. Stages are pushed from `bn.subscribe` until `bn.unsubscribe` or `bn.hello`; read the outcome of a command outside that span with `bn.command.result`. Any request that names a stale `epoch` fails with `stale_epoch` and `action: "subscribe"`.

## Methods

| ------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `bn.hello`               | `versions`, `client`, `schema`, `locale?`, `capabilities?` | `version`, `epoch`, `engine`, `limits`, `delivery?`, `schema`, `locale`, `engine_locale`, `role`                                              |
| `bn.viewport`            | `cols`, `rows`                                             | none                                                                                                                                          |
| `bn.interrupt`           | none                                                       | none                                                                                                                                          |
| `bn.hold`                | `epoch`, `screen_id`, `affordance_id`                      | none                                                                                                                                          |
| `bn.release`             | none                                                       | none                                                                                                                                          |
| `bn.subscribe`           | none                                                       | snapshot header; parts and events follow                                                                                                      |
| `bn.unsubscribe`         | none                                                       | none                                                                                                                                          |
| `bn.interaction.choices` | `epoch`, `boundary_id`, `offset`, `limit`                  | `boundary_id`, `total`, `choices` (reads only)                                                                                                |
| `bn.world.describe`      | `epoch`, `boundary_id`, `pos`                              | `lines` (reads only)                                                                                                                          |
| `bn.world.cells`         | `epoch`, `min`, `max`                                      | `at`, `cells`, `forgotten` (reads only)                                                                                                       |
| `bn.overmap.cells`       | `epoch`, `min`, `max`                                      | `overmap` squares of an overmap level, whatever the cursor (reads only)                                                                       |
| `bn.panel.view`          | `epoch`, `panel` (`character` or `inventory`), `row?`      | the `screen` as it opens on the avatar, `row` (a row or tab id) focused, every list row while it fits a frame, nothing to invoke (reads only) |
| `bn.command.submit`      | `epoch`, `expect`, `operation`                             | `command_id`, `stage: "received"`                                                                                                             |
| `bn.command.result`      | `epoch`, `command_id`                                      | latest stage, for recovering a lost notification                                                                                              |
| `bn.credit`              | `frames`                                                   | `credits` held after the grant                                                                                                                |

Notifications from the engine: `bn.snapshot.part`, `bn.events`, `bn.command`, `bn.resync`, `bn.loading`, `bn.progress`. All but `bn.loading` and `bn.progress` are sent at input boundaries to a subscribed client. `bn.progress` (`{epoch}`) is a heartbeat, sent every 2 seconds to a client that said `bn.hello` while a wait or other activity runs without reaching an input boundary, so silence on the wire means the engine is not working. `bn.loading` plays the same role while the world loads.

Errors use code `1000` with `error.data = {kind, action?, at?}`; `action` says what to do next (`hello`, `subscribe`, `retry`).

## Hello and the stack

The engine serves `"0.2"` only, on every transport. A hello that does not list `"0.2"` fails with `negotiation_failed` and `action: "hello"`. The hello must carry:

- `schema`: `sha256:` and the first 16 hex digits of the SHA-256 of the raw bytes of [`0.2.schema.json`](../../../schema/engine-client/0.2.schema.json). A different hash fails with `negotiation_failed`, `action: "hello"` and `error.data.schema = {engine, client}`. The engine takes its hash from the schema file when CMake configures.
- optional `locale` and `capabilities` (`tiles`, `tint_ids`, `viewport`, `delivery`; the members may also stand loose in the hello, but not both forms). The result adds `schema`, `locale` (the language of the connection's text), `engine_locale` and `role`. A `locale` the engine has no catalogue for fails with `unavailable_locale` and `action: "hello"`.

Every interaction boundary (snapshot header and events) carries `stack`, next to `interaction`. The stack is the open screens, outermost first; only the last has affordances. A screen's `kind` names what screen it is (`map`, `crafting`, `uilist`, ...), the same at every opening and in every language, so a client keys what it keeps per screen, such as a window's place, on it; a screen without `kind` is one the engine does not name yet. `bn.interaction.choices` with `component_id` reads that list of the top screen (`rows`, `total`).

`bn.command.submit` takes `operation: {kind: "invoke", affordance_id, args?}`. Its `expect` is the affordance's `expect` scope:

- `screen`: `{screen_id}`, valid while that screen is on top, else the command is rejected with `stale_screen`. The engine keeps up to 8 of these waiting (`limits.screen_queue` in the hello result) while a command runs and validates each when it takes its turn, so a held key keeps moving and keys aimed at a popup that has closed are rejected.
- `boundary`: `{boundary_id, revision}`, as before. While a command runs the submit fails with `command_busy`.

A form that does not match the affordance is `invalid_arguments`. An affordance's `args.text` may carry `default`, the text a client puts in the box when it asks for one and the player may change, such as the free file name the vehicle editor suggests for New vehicle and Save as.

An affordance, row, tab or grid cell that is off and can be picked always carries a `denial`: the screen's reason in the player's language, else that it is not available now. A client shows it as the reason and adds none of its own.

A text with the `role` `prompt` is the question the parts after it in its split answer (a popup's or a menu's message), which a client shows above them. A row's `affordance` names the affordance of the screen that does what the row does (a popup's `YES`), present only while the screen offers it, so a client offers that action on the row and not again as a button. A panel never repeats its screen's `title`: where it would, its `title` is empty.

A grid that a client can draw with sprites carries `looks`, each look once, and each of its cells `looks`, indexes into them from the bottom up: what the square shows, as the world map's cells name it. The cell's `glyph` stands for them in text. The map editor's canvas and preview and the vehicle window's grid carry them. A grid of squares the player draws on has the role `canvas` and takes whatever room a client has; a grid that only shows or picks squares has none. A grid may carry `block`, the `x` by `y` squares a client outlines as one, such as each overmap square of the map editor's canvas, and a cell `faded` shows another level or overmap square, which a client draws faded.

A screen of role `workspace` is the whole view: a client draws no map, sidebar or toolbar of the game under it. Each part of its root split may carry a `slot`, what the part is for, which a client lays out as it likes: `tools` (the tools and their settings), `canvas` (the document being edited), `palette` (what the tools put down), `outline` (the parts of the document), `inspector` (the settings of what is picked), `log` (messages and history) or `status` (a line of facts about the cursor and the document); a part without one counts as `inspector`. Its affordances may carry a `group`, the localized name of the menu they belong in, such as File; a client builds a menu bar from the groups in the order they first appear.

## Held keys

A step of the map carries `holdable`. A client sends `bn.hold` once when its key goes down and `bn.release` when it comes up, and never invokes it for key repeats. While a hold stands, the map is the screen on top and input is awaited, the engine gives the game one step of that action at each input prompt, as if the native key were pressed once more, and reads the requests the client has sent before each step. A tap owes one step even if released first. A popup or other screen on top, a step that changes neither the avatar's square nor the turn, a new `bn.hello` and a disconnect end the hold. `bn.hold` fails with `not_ready` during an activity, `stale_screen` for a screen that is not on top, `unknown_affordance` and `invalid_arguments` for an affordance that is missing or not holdable. Screen-scoped invokes still queue (a held arrow in a list).

## Delivery credits

Opt in with `bn.hello` `delivery = {credits, max_hz?}` (`credits` 1 to 256, optional `max_hz` 1 to 240). The result then carries `delivery = {credits, held_frames, held_bytes, max_hz?}`, `max_hz` echoed when asked for. Without `delivery` nothing below applies: pushed frames are written at once, at input boundaries and auto-move steps, as before.

- A pushed `bn.events` or `bn.command` frame costs one credit. With none left the engine keeps the frame, in order, and writes it when `bn.credit {frames}` grants more (the result is the credits held, capped at 256; the held frames follow the response). Snapshot parts, `bn.resync`, `bn.loading` and `bn.progress` cost nothing.
- The engine holds at most `held_frames` frames and `held_bytes` bytes for a client. Past either bound it drops the held `bn.events`, sends `bn.resync` with reason `backpressure` (`lost_after` is the newest sequence it wrote) and stops pushing events until the client calls `bn.subscribe`, whose snapshot replaces what was dropped. The held `bn.command` frames stay and follow the `bn.resync` as credits pay for them, and `bn.subscribe` drops only held events too, so the end of a command is never lost; only a client that leaves more stages unpaid than the bounds hold loses the oldest of them.
- A client with credits also receives frames while an activity runs (a wait, a craft), before the command completes. Capturing the world costs far more than a turn, so the engine publishes a running activity only as often as publishing takes a fifth of the activity's time, not after every turn; with `max_hz` it also publishes at most once per 1/`max_hz` seconds of wall time, whichever is sparser: a frame carries what changed since the previous one, state changes merged and every message and presentation fact in order, and the boundary where the activity ends carries the rest. `bn.command` `completed` still comes at that input boundary. The stream never waits for the client: a client that stops granting credits costs the engine at most the held bound, and the game, its RNG and its saves are the same as for a client that reads everything or none.
- Credits never make an activity wait: stdout is served like a socket, as the controller (see Sockets and spectators), so a credited frame goes to a buffer that is written without blocking, and the engine keeps reading stdin while stdout is full. A frame larger than the pipe waits at most 10 ms for the client to read it, so a client that reads it at once gets it whole; one that takes nothing in that time is not waited for again until it reads. A client that reads more slowly than the activity publishes runs out of credits and is resynced as above; one that leaves more than 16 MiB unread is dropped, as a socket is. Stdio has no next controller, so the engine then saves the game being played and exits. On Windows stdio is not served this way: a write returns only when the pipe has taken it, so an activity waits for a client that does not read what it has credits for.

## Framing and failure

- A frame is one JSON value on one line, at most `limits.frame_bytes` long in either direction. Frames are written whole by a single writer and never interleave; the engine reads one frame at a time and holds no more than that.
- A line that is not JSON is answered with `-32700`, JSON of the wrong shape with `-32600`, an unknown `bn.` method with `-32601` and bad params with `-32602`; the `id` is `null` when none could be read, and a notification gets no reply. Such a frame changes neither the game nor the held frames, and the connection stays open, also while an activity runs.
- A frame longer than the maximum, or one cut off by the end of stdin, cannot be answered: the engine reads no further, writes the reason on stderr and exits with code 1 (on a socket, only that connection ends).
- While an activity runs, requests are answered but start nothing. `bn.command.submit` fails with `not_ready` until the next input boundary, `bn.interrupt` is the one control the activity accepts, and `bn.viewport`, `bn.subscribe` and `bn.credit` change only what is delivered: the command stays open until the boundary where the activity ends. A repeated `bn.hello` renegotiates delivery, drops the held frames and unsubscribes, so the stream restarts at the next `bn.subscribe`.
- At shutdown (stdin ends, the game exits) the engine writes the held frames that credits pay for, in order, and drops the rest; the `interrupted` stage of an unfinished command is among them. `SIGTERM` and `SIGINT` end the engine at once, after naming the signal on stderr. A client that stops reading and closes its end ends the engine through the failed write.

## Sockets and spectators

`--client=mcp --listen <path>` serves the same protocol on a local stream socket instead of stdio: a Unix domain socket, and `AF_UNIX` on Windows 10 and later. Without the option nothing changes. The engine creates the file readable by its user only, replaces a stale file nothing answers on and refuses a path in use. Frames are the same lines, with the same limits. At most 8 connections are served; more are closed at once. A client can connect while the world loads and receives `bn.loading`.

- **Roles.** The first connection, and any connection made while there is none, is the controller: it alone may command the game. Every other connection is a spectator with its own `bn.hello`, credits, held frames (256 frames, 1 MiB) and subscription. A spectator reads everything the controller can, including the command stages and events of the controller's commands, but `bn.command.submit`, `bn.interrupt`, `bn.viewport` and the legacy `bn.press` and `bn.interact` fail with `read_only`, and its `bn.hello` leaves the controller's viewport and tile settings alone. A role never changes while connected; a spectator that wants control reconnects after the controller left.
- **No blocking.** Output goes to a buffer of the connection that is written without blocking (the controller's frame waits at most 10 ms for its reader, as on stdio), and a connection that leaves more than 16 MiB unsent is closed, unless credits stopped its stream earlier. The game waits only for the controller's input, as it does on stdio, and serves the spectators meanwhile, so a spectator that reads slowly or not at all never slows the game or the controller. Credits never make an activity wait on a socket.
- **Disconnect.** Closing a connection frees everything held for it, and nothing is kept for a reconnect: a client that comes back says `bn.hello` and `bn.subscribe` and continues from that snapshot, as after a `bn.resync`. A frame that is not JSON is answered as above and the connection stays open; a frame past the limit, or cut off by the close, ends that connection only, where on stdio it ends the engine.
- **The controller leaves.** Its open command is `interrupted`. A running activity goes on to its end, and then the game waits at its input boundary, as for a player who has not pressed a key, until a connection arrives; the next connection becomes the controller. Spectators stay connected and are told where the game stands. A closing socket never ends the engine: it ends as the game does, or by `SIGTERM` and `SIGINT`.

## One clock

- `epoch` changes when the process starts or the world is replaced, never on reads.
- `sequence` counts published events (decimal string, contiguous, starting at `"1"`). `revision` counts events that change state. `at = {epoch, sequence, revision}` means "includes every event up to sequence".
- A command carries `expect = {revision, boundary_id, schema_id}`. A stale value is rejected, so a client never acts on a screen it has not seen. `schema_id` is `null` exactly when the boundary has no interaction.

## Commands

`operation.kind` is one of `choose`, `fill`, `set_count`, `set_target`, `cancel` (semantic menus) `action` (a registered action such as a movement key), `travel` (a map click), `tile_action` (an action on a map square, below) or `set_mode` (a setting to a named value, below).

```json
{ "kind": "choose", "choice_id": "tab:new_game" }
{ "kind": "set_target", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
{ "kind": "action", "action_id": "RIGHT" }
{ "kind": "travel", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
```

Every boundary action lists `keys`, the portable names (`ESC`, `SPACE`, `RETURN`, `UP`, `>`, ...) of the single keyboard keys the active input context binds to it; `action` runs an action by its id, also one without keys (such as `open_options` while unbound). A client that wants to act on a pressed key finds the action whose `keys` contain it instead of guessing from the key settings files.

`travel` is the left click of Tiles and curses on an absolute map square in view, at a boundary without interaction. The first click publishes the engine's own route as `route`; clicking the same square again starts native auto-move. The avatar then walks one step at a time, each step publishing ordinary events attached to that command, and stops where the engine stops (arrival, a monster coming into view, ...). The command is `completed` when the walk ends and input is awaited again. Any other command or a click elsewhere replaces or clears the plan. A client never computes routes.

The engine also decides what a click or a chore does with the squares and items it names. A left `travel` onto a closed door beside the avatar that the avatar can open, or onto a locked one, is the move into it (native movement opens the door, or says that it is locked and plays the error sound) instead of a route click. `pickup` and `drop` take `{ "kind": "pickup" | "drop", "item_id", "count" }`: `item_id` is the `id` of a row of `avatar.ground` (pickup) or `avatar.inventory` (drop), `count` how much of the row in its native units (charges of a charges item such as nails, else items), and the engine starts the native pickup or drop activity as the menus would after marking and confirming. A row id stays while the stack stays what it is; the command is rejected with `validation_failed` when the row is gone or holds less than `count`. A command that fails carries `error_text` (a command result or `bn.command`) or `message` (a JSON-RPC error `data`): the localized reason, more specific than `error` where the engine knows it (a travel target outside the map window, a count past the stack, a value a form field does not take, which names the field and what it takes: `Facing takes a whole number from 0 to 359.`). An `integer` form field's `min` and `max` are whole numbers. The aiming screen (kind `target`: firing, throwing, reach attacks, spells and turrets), titled as the native one, is the `target` panel, whose stats are `range` (against the maximum, `bad` out of range), `elevation`, `targets` and the gun, aim, throw, spell or turret figures, over the `target:map` map. Its `target` carries `distance` (how far `current` is from `source` by `distance_metric`, the vertical axis included), `status` (`good`, `bad_target`, `out_of_ammo` or `out_of_range`), `status_text` (the localized range and readiness line), the `candidates` the cursor can jump to, the `trajectory` (the squares of the line of fire in order, the source left out, while aiming) and the `parts` of the cursor square. `target:move` with a `pos` puts the cursor on that square; firing, the aim modes and the cursor keys are the registered actions. A popup that any key acknowledges and binds no key for names the choice to take in `interaction.any_key_choice_id`.

`context` is the right click (SEC_SELECT) on the same square: the native action examines an adjacent square, closes an adjacent door, picks up at the avatar, fires at a seen monster, or first cancels a planned route. `bn.world.describe` returns the text the native mouse view prints for a hovered square in the terrain window (`validation_failed` outside it); it selects and plans nothing. `bn.world.cells` returns what the avatar knows in a box of one level (`min` and `max` inclusive, same `dim` and `z`, at most `limits.cells_per_query` squares), the cells exactly as the snapshot holds them; `forgotten` lists the squares of the box inside the coverage that nothing is known about. An inverted box or one across levels is `validation_failed`, an oversized one `resource_limit`, and another `epoch` `stale_epoch`. A wheel step in a menu is the registered action `SCROLL_UP` or `SCROLL_DOWN` (the engine moves the native cursor by three rows).

`tile_action` takes one of the `actions` that `bn.world.describe` lists for a square, with `action_id` and `pos`, and does what the native action does on that square. The list holds only what applies now, in menu order, each with the native `label` and the player's `keys` (none for `attack`, `talk` and `travel`): `attack` (a seen creature beside the avatar that is not a friend), `fire` (a seen monster, with a ranged weapon wielded), `talk` (a seen character), `open`, `close`, `pickup` and `examine` (the avatar's square and the eight around it, where the native action finds something to do), `travel` (a square the avatar knows; it plans the route and starts walking it in one command) and `look` (always; it opens the look view on that square). An action the square does not list now is `validation_failed`. A client shows the list as the right-click menu of the square.

`set_mode` takes `{ "kind": "set_mode", "mode", "value" }` and sets a mode to the value named, so a duplicated, retried or raced command still ends on that value and the client never reads the current value first. `avatar.modes` lists every mode now as `{ id, label, value, values: [{ id, label }] }` (ids are language-neutral, labels the engine's display language): `safe_mode`, `auto_safe_mode`, `auto_travel_mode`, `manual_combat_mode`, `auto_features`, `auto_mining`, `auto_pickup`, `zone_overlay`, `map_memory`, `hour_timer` and `debug_mode` (`on` or `off`; `debug_mode` is absent where the native key is disabled), `auto_pulp_butcher` and `auto_foraging` (their option values, such as `off`, `pulp`, `butcher`), `thief_mode` (`ask`, `honest`, `steal`) and `move_mode` (`walk`, `run`, `crouch`, `prone`). `safe_mode` is the safe mode key's state (`avatar.sidebar.safe_mode.enabled` also counts auto safe mode). Setting the value a mode holds is a success that changes nothing; an unknown mode or value is `validation_failed` with a localized `error_text`. Otherwise the engine does what the native key does when it lands on that value (its messages and side effects, saving the options that the key saves), without passing through another value, at a map screen like `action`. Where the game refuses it as natively (running while too tired, say), only its message remains and the published value stays. The registered actions that toggle or cycle stay the native keys.

The map screen also carries `shortcuts`, the buttons of a shortcut bar. They are data (`client_shortcut` in the game's JSON: `id`, `action`, `icon`, `glyph`, `order`; a mod adds a button with a new id and replaces one by reusing its id): each names a registered action of the map's input context, and the engine publishes it with that context's `label` and `keys`, the data's `icon` (an opaque sprite id) and `glyph` (what to draw without art for it), and `enabled` while the map is on top and offers the action. A button the context names no action for is left out. The `editor` action opens the map editor; without the `DEBUG_EDITOR` trait it carries the `denial` `You need the Debug Editor trait: open the debug menu (<key>), then Player…, Mutate, and pick Debug Editor.`, `<key>` the key bound to the debug menu The world map component also carries `item_lists`, the avatar's item lists a client shows beside the map in order, also while the map is covered: per list the avatar member holding its rows as `id` (`avatar.ground`, `avatar.inventory`), its heading as `label` and what moving a row out of it does as `verb` (pick up, drop), both localized. Its click is an `invoke` of the affordance named by `affordance_id`. A screen's affordances may carry the `role`s `navigate` (cursor, page, tab and scroll actions, which a client already reaches with keys, the wheel and clicks), `help` (the keybindings menu), `digit` (a typed digit of a counting list's count, read before any action bound to the key: as in the native list, it goes into the count the next mark takes, or opens the count prompt with it; a client need not draw it) and `layout` (an action that only resizes or rearranges the native window, which changes nothing the screen publishes: `TOGGLE_WIDE_DISPLAY` and `TOGGLE_FULL_HEIGHT_DISPLAY` of the message log, `TOGGLE_ITEM_INFO` of the trade window, `TOGGLE_EXPANDED` of the Lua console, `toggle_fullscreen` of the map; a client that lays out its own windows need not draw it) and `edit` (a key that edits the text of the screen's text field: `TEXT.BACKSPACE`, `TEXT.DELETE`, `TEXT.CLEAR`, `TEXT.PASTE`, `TEXT.INPUT_FROM_FILE`; a client's own text box takes it, so it need not draw a button) next to `confirm` and `cancel`.

Stages: `received`, `validated`, `executing`, `completed`; or `rejected`; or `interrupted`, whose `error` says why (`stale_epoch` when the world was replaced, `validation_failed` when the game refused the input, `not_ready` otherwise). Every stage comes with `stage_text`, its localized words (`Received.`, `Under way.`, `Refused.`, ...) for the player; `stage` stays the id to act on. `completed` means input is awaited again: a wait or other activity first runs to its end, or until the game asks something (a pop-up, an interruption); its `at` is the endpoint of that boundary. A prompt the input opens (a text field, an amount) is therefore in the state when `completed` arrives, since the events that carry it come first (after a `bn.resync`, the snapshot that follows carries it): a client that finds no prompt then knows none opened. One command is outstanding at a time (`command_busy`). While a wait or other activity runs, requests are still answered; `bn.interrupt` presses the native interrupt key, so the activity asks whether to stop as in Tiles, and that question is the next boundary. Outside an activity it fails with `not_ready`.

## Loading

While the world loads, the game thread is busy and reaches no input boundary, so a client that said `bn.hello` gets `bn.loading` instead, written at each step of the native loading screen (subscribed or not). Progress is the screen the native client shows: `title` is the current context (for example "Loading files"), `entries` its list, `index` the entry in progress (earlier ones are done) and `image` the loading image, chosen like the native client does. `image.path` is relative to the game's base path, `author` is omitted when the file name has none. `done` is sent once when the loading screen ends; after it the usual `bn.resync` or `bn.events` follow. `epoch` is the epoch in force when the step was sent.

```text
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","title":"Loading files","entries":["Terrain","Items"],"index":1,"image":{"path":"data/json/loading/Ada_dawn.webp","author":"Ada"}}}
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","done":true}}
```

## Values

- `pos = {dim, x, y, z}` is an absolute map square; `dim` is the game dimension, `""` for the primary one. Reality-bubble coordinates never appear on the wire.
- `look = {kind, id, glyph, color}` carries appearance from game data, so text clients need no tileset. Auto-wall terrain carries the line glyph for the connections the avatar knows, as the native text view draws it; a remembered cell keeps `memory.overlay` (furniture, trap or vehicle part) over `memory.terrain`.
- A `look` carries `name`, the translated player-facing name the native look shows ("wooden floor" for `t_floor`), so a text or speech client need not read ids; creatures use the entity's `name`. A tiled client draws the same `look`s with the game's tileset. The engine publishes what only it can know, because it owns the data and the native selection, and the client never reimplements it: `tile` (the sprite id when it is not `id`: `corpse_<monster>`, `player_male`, `vp_<part>`), `looks_like` (the data's fallback chain, nearest first), `subtile` and `rotation` (the multitile key and quarter turn the native selection computed from the neighbours the avatar knows, so connection logic exists once), `stack` (the displayed item of a pile), `attitude` and `aware` (monsters and NPCs, which the native view marks with an overlay), `health` (a hurt creature's native look-around bar: `fifths` filled and its `color`), `tint` (a vehicle part's paint, which a tileset blends into its sprites), `reviving` (the cell holds a corpse that can rise), `facing` (creatures), the cell's `light` (native `lit_level`: 0 dark, 1 low, 2 bright only, 3 lit, 4 bright), its `glow` (the colored light the native tiles view adds over its sprites: the light's `color` and its `strength`, 1 to 255), `environment.season` the avatar's `look` and, for characters, `overlays` (worn and wielded items, mutations, bionics as `look`s of kind `overlay` whose `tile` and `looks_like` list the sprite ids to try in the native order). The client owns what the tileset defines: files, weighted variants, layering and darkening. Layer order is terrain, furniture, trap, field, item, vehicle part, creature; the last entry of `fields` and `items` is the one the native view draws. `light` covers squares in sight only: the game's dark and bright-only levels (0 and 2) are squares the avatar cannot see, so a client draws its hidden-lighting sprite under every square without a plain view, and no `lowlight_dark` or `lowlight_light` fact is sent. A remembered cell draws darkened, a `light` of 1 shaded, and an id without a sprite falls back to its `glyph`.
- A mutation overlay carries `mutation` (the `id`, `types` and `flags` of the mutation), and an avatar or entity carries `traits` (the ids of its mutations by mutation type); a tileset's `tints` and `tint_pairs` are keyed by them to tint hair, skin and eyes. The environment's `sky` says how much `daylight` there is in percent of the season's full daylight, the weather's `precipitation`, whether it falls as `rain` (else snow), the ambient light the weather takes away (`dimming`), how far in percent the `sun` has crossed the sky from sunrise (east) to sunset (west), absent at night, how far the `moon` has crossed the night sky from sunset to sunrise, absent by day, and the `moon_phase`. The environment lists `mod_tilesets`, the game data files that add sprites to tilesets, in the native load order, each with its `base` folder, its `index` in the file and the tilesets it is `compatibility`-listed for. A cell has `cargo` when a cargo part of a vehicle on it holds items; the native view highlights the part. A visible cell has `roofed` when the square is not outside, the game's `is_outside` being false there: a roof or a floor above covers it, which is where rain and snow do not fall; a client may draw a ceiling over it. The overlay of a worn or wielded item, a bionic or an effect carries `tint_keys`, the ids a tileset's `tints` are keyed by in the order the native view tries them (the flags, then the id). A hello may list `tint_ids`, the ids of the tints its tileset has; looks of terrain, furniture, monsters, vehicle parts and items then carry the `tint_keys` among them (flags, then id), and an item, terrain or furniture square with tint variables carries `tint_vars` (the color, blend and adjustments over the tileset's). A field look carries `tint`, the tint of its type, as the native view paints it. A field entry has `hides_items` when its type hides the items under it (smoke, fire, webs): while it is the displayed field the native tiles view draws neither the items nor their highlight.
- Terrain the game data flags as a wall (`WALL`) carries `wall: true`, in sight and in memory, so a client that draws a top-down tileset in 3D can raise walls without guessing from sprites. A window (`WINDOW`) also carries `window: true`, so such a client can leave its opening between a sill and a lintel. Terrain and furniture carry the `coverage` of their data, the percent of a person behind them they cover (1 to 100, absent for none), so such a client can raise what stands, such as a table or a shrub, by how much it covers. Terrain, furniture and fields carry the `form` their data gives them (`door`, `fence`, `plant`, `seat`, `table`, `bed`, `fire` or `gas`, absent otherwise), so such a client can build a door, a shrub or a chair in its own shape and draw fire and gas as what gives light or lets it through.
- A square in sight on the level the `view` shows that the native tiles view looks through (open air and other terrain without a floor, such as treetops, glass roofs and ramps down) carries `below`, how many levels down the square is that the native tiles view draws there: the first square with a floor or with something remembered on it when it is in sight, remembered or a vehicle, else the lowest square in sight with something on it on the way down, else the first floor when the avatar neither sees it nor remembers it (a roof edge hides the ground below it), a square the native view leaves dark: then the square carries `below` and no cell is published at that depth, so a client knows open air in sight with ground it may not draw. That square is published as itself. The square looked through keeps what is on it, such as a field; bare open air carries nothing else, and bare open air with nothing seen through it is not published. Only squares in sight are looked through.
- `interaction` is the native menu or dialog: every `columns` entry has a `key`, its stable untranslated name (the English caption in lower case with `_` between words, such as `spell_level`; an inventory cell is `cell0`, `cell1`, ...), and a `label`, the translated caption; clients look a column up by `key` only. A column may carry `color`, the native color name of its value. A choice may also carry `favorite` (a favorite spell), `color` and `key_color` (color names of the row text and its `hotkey`), `markup` (the name with native color tags), `mark` (`glyph` `+`, `#` or `-`, and `color`) where the native list prints a selection mark, and `parent_id` and `nest_color` where it draws a nesting slash. `choices` holds up to the first 200 rows, fewer when they would be too large; read the rest with `bn.interaction.choices` starting at `offset = choices.length`. `choice_total` is the full count. `compat.focus` and `compat.panes` keep native list state for 1:1 ports; clients may ignore them. The `FILTER` affordance opens the native search prompt, whose `filter` field you `fill` with `submit: true` to search and with an empty value to clear. A filterable list also carries the `filter` text it holds, and its `bn:filter:<list id>` affordance (an `invoke` with a `text` argument, no prompt) sets that text and narrows the rows at once; an empty text clears it. A menu whose native callback tests raw keys itself (the wish menus, the technique menu) offers each as a `bn:key:<keycode>` affordance of the screen, labelled with the key's name and carrying the key in `keys`; `invoke` one to press that key. They are never rows, so a filtered list holds only its results. The spell menu publishes, on each spell row, the details its native side panel draws: `description` (class, text, level, difficulty, experience, cost, time, targets, damage, area, range, duration and components, with color markup) and `columns` `Spell Level`, `Failure Chance`, `Casting Cost`, `Casting Time` and `Range`, and `favorite` on a favorite spell; its keys to toggle a favorite, toggle casting distractions and assign a hotkey are `bn:key:<keycode>` affordances. The menus whose native callback draws a side panel (martial art styles, the wish menus for mutations, monsters and items, the effect picker, the translocator gates, a spellbook's spells) put that panel's text, with color markup, in the row's `description` after the row's own description; the panels that cost a lookup per row (martial art styles, wish monsters, wish items) fill only the selected row. A row the native list prints a key before (a menu entry's hotkey, an inventory item's letter) has `hotkey`, that key as text; pressing it chooses the row natively. The action buttons are named by the registered actions' `name`. A choice may carry `action_id`, the registered action the row runs; the in-game main menu's rows have it, so its Options row is `open_options` in any language.
- The main menu is the screen of kind `main_menu` (role `screen`), a split of the `menu:banner` text (the title art) and the `menu:tabs` tabs, one per native tab (`motd`, `new_game`, `load`, `world`, `editor`, `settings`, `help`, `credits`, `quit`; the shown one `selected`). Under them the shown tab holds its prose as the `menu:text` text (the MOTD, the credits) or its entries as the `menu:entries` list, a row per entry named by what it opens (`new_game:tutorial`, `editor:map`, `settings:options`, `load:<world>`, `world:create`, `world:<world>`) with its native hint as `description`; ids never depend on position or language. `menu:tab` with a tab id shows that tab (the help and quit tabs act at once, as their native keys do), and `menu:entry` with a row runs it as Enter does. `editor:map` starts the map editor without making a character: it first shows the mod list as the `world_creation` screen (the default mods active; choosing a mod adds its dependencies; its header panel's first note, `heading`, says `Turn on the mod that holds your files, then press Esc.`; leaving it asks `Open the editor with these mods?` with `YES` selected, and answering no returns to the main menu with no world made), then a world named `EDITOR` with the mods chosen, deleted at world end like the tutorial's, whose first overmap is open field at noon, all of it seen, and an avatar in its middle with the `DEBUG_EDITOR` trait and the debug traits that keep creatures from noticing or harming it; the map editor opens before the first turn as a screen of role `workspace`, the whole view with no map under it. Its Test and the vehicle editor's Spawn leave it for the map where the avatar stands; the `editor` action of that map reopens it. Leaving it ends the world and returns to the main menu. `editor:vehicle` asks for the mods the same way and starts the same world with the vehicle editor open instead, also a `workspace`; leaving it ends the world the same way. `editor:save` lists the saves of every world (a list of rows labelled `<world>: <character>`; the return row leaves it); choosing one loads that save as a normal game, with the editor allowed for that session (no trait is added, so the save is not changed), and opens the map editor before the first turn; the avatar stays where the save put it, and leaving the editor shows the map there. After these rows come the documents the editors opened, newest first and at most 10 (`editor:recent:<n>`, labelled with the file or the vehicle prototype, kept in `editor_recent.json` in the configuration directory); choosing one asks for the mods as `editor:map` does, starting from the mods the document was opened with, and opens it in its editor.
- The world picker (a new game with more than one world to pick from) is the screen of kind `world_pick` (role `screen`), titled `WORLD SELECTION`: the `world_pick` split holds the `world_pick:worlds` panel, whose `hint` stat is `Pick a world to enter game`, over the `world_pick:rows` list, a row per world of every native page named `world:<world>` with the native label `<world> (<saves>)`. `world_pick:pick` with a row moves the native cursor there (onto its page) and Enter on a row (`bn:activate:world_pick:pick`) enters that world; a row the list does not hold is rejected with `invalid_arguments`. `NEXT_TAB`, `PREV_TAB` and `QUIT` stay registered actions.
- World creation is the screen of kind `world_creation` (role `screen`), titled `World creation`: the `worldgen:tabs` tabs `mods`, `options` and `confirm` over the `worldgen:<tab>` split; `worldgen:tab` with a tab id goes there through the tabs between. The mods tab is the `worldgen:mods:header` panel (the `filter` stat `Filter: <text>` while one is set) holding the `worldgen:mods:body` `detail` split of the `worldgen:mods:lists` split (`active` the list with the cursor) and the `worldgen:mods:details` text of the mod under the cursor. The lists are the `worldgen:mods:categories` tabs, one per native mod category by its id, holding the `worldgen:mods:available` panel with its `worldgen:mods:available:rows` list of `mod:<mod id>` rows, and the `worldgen:mods:active` panel with its `worldgen:mods:active:rows` list, an `active:<mod id>` row per active mod in load order, `toggled`, with its `order` column; the panel of an empty list has the `none` stat (`--NO AVAILABLE MODS--`, `--NO MATCHES--` or `--NO ACTIVE MODS--`). `worldgen:mods:category` shows a category, `worldgen:mods:add` and `worldgen:mods:remove` move the cursor to a row of their list, and Enter on a row (`bn:activate:worldgen:mods:add`, `bn:activate:worldgen:mods:remove`) is the native Enter: it activates the mod (with the native `Cannot add mod` popup where it cannot) or deactivates it. Editing the mods of an existing world is the same screen without the tabs, titled `Mods`. The options tab is the `options` screen of the world's options. The confirm tab is the `worldgen:confirm:notes` panel, whose `random`, `format` (`good` for V2), `format_help` and `finish` stats are the native lines, holding the `worldgen:confirm:name` form of one `name` field (`World Name:`, at most the native length); `worldgen:confirm:name` with a text sets the name, `NEXT_TAB` finishes through the native queries, `PREV_TAB` goes back, and `PICK_RANDOM_WORLDNAME` and `TOGGLE_V2_SAVE_FORMAT` are registered actions.
- A world's active mods list (the main menu's world tab and the game's entry that show them) is the screen of kind `world_mods` (role `screen`), titled `ACTIVE WORLD MODS`: the `worldgen:active_mods` split of the `worldgen:active_mods` panel (the `none` stat `--NO ACTIVE MODS--` while there is none) holding the `worldgen:active_mods:rows` list of `mod:<mod id>` rows in load order, and the `worldgen:active_mods:details` text of the mod under the cursor. `worldgen:active_mods:pick` moves the cursor and Enter on a row (`bn:activate:worldgen:active_mods:pick`) closes the list, as the native Enter does; `CONFIRM` and `QUIT` close it.
- Character creation is the screen of kind `new_character` (role `screen`), titled `Character creation`: the `newchar:tabs` tabs (`points`, `scenario`, `profession`, `stats`, `traits`, `bionics` and `magic` where the profession and scenario allow them, `skills`, `overview`) over the `newchar:<tab>:notes` panel, whose stats are the tab's native lines (`points_left` first, then such as `hint`, what the row under the cursor costs, `good` or `bad` by whether it can be taken), holding the `newchar:<tab>` `detail` split. `newchar:tab` with a tab id goes there through the tabs between. Each list's `newchar:<tab>:pick` (`newchar:<tab>:<page>:pick` on the traits and bionics pages) moves the cursor to a row, and Enter on a row (that id after `bn:activate:`) is the native Enter there. Points: the `newchar:points:rows` list of `points:multi_pool`, `points:one_pool` and `points:freeform` as the world allows, `toggled` on the one in use. Stats: the `newchar:stats:rows` list of `stat:str`, `stat:dex`, `stat:int` and `stat:per` with the `value` column, and the `newchar:stats:details` text. Traits and bionics: the `newchar:<tab>:pages` split of the `newchar:<tab>:advantage`, `newchar:<tab>:disadvantage` and `newchar:<tab>:neutral` panels the native tab uses, each holding its `:rows` list of `trait:<id>` or `bionic:<id>` rows with the `points` column, `toggled` when taken and a `denial` where the scenario forbids it; outside freeform the `pools` stat. Profession and scenario: the `newchar:<tab>:list` panel with the native `filter`, holding the filterable `newchar:<tab>:list:rows` list (`FILTER`) of `profession:<id>` or `scenario:<id>` rows with the `points` column, `toggled` on the chosen one (a `denial` on a scenario the world's city size rules out), beside the `newchar:profession:details` text or the `newchar:scenario:details` panel (the `professions`, `location`, `vehicle` and `flags` stats); the `sort` stat, and `gender` for professions. Skills: the `newchar:skills:rows` list of `skill_type:<id>` headers over `skill:<id>` rows (the `level`, `profession` and `cost` columns) and the `newchar:skills:details` text. Magic: the `newchar:magic:rows` list of `spell_class:<trait id>` headers over `spell:<id>` rows (the `level` and `cost` columns, `toggled` when known). the stats, skills and magic tabs register no `CONFIRM`, so their lists offer no Enter on a row. Overview: the `newchar:overview:fields` list of the `name`, `height`, `age`, `gender` and `location` rows with the `value` column, where Enter on `name`, `height` or `age` opens the native input for it, on `gender` switches it and on `location` opens the native location list, beside the `newchar:overview:facts` panel with the `str`, `dex`, `int`, `per`, `traits`, `bionics`, `spells`, `skills`, `vehicle`, `companions`, `cash`, `pets`, `addictions`, `items`, `scenario` and `profession` stats (an empty one `None!`, `bad`); `NEXT_TAB` there finishes through the native checks and queries.
- The crafting menu is the screen of kind `crafting` (role `screen`): the `crafting:tabs` category tabs (`CC_WEAPON`, ...) over the `crafting:subtabs` tabs of the selected category (`CSC_WEAPON_BASHING`, ..., disabled when empty) over the `crafting:body` detail split; while a search is active the two are one `search` tab, in batch mode one `batch` tab. The `crafting:recipes` list has a row per recipe named by its recipe id (`#<n>` for the n-th alike before it; in batch mode `1`, `2`, ... for the batch sizes) with its `look`, `favorite`, `parent_id` under a nested group (`toggled` while the group is expanded), the `availability` column (`Ready`, `Strained`, `Unlearned` or `Missing`, colored as the native list), `known` and `unread` columns where they apply, and a `denial` when it cannot be crafted. Beside it the `crafting:detail` panel of the highlighted recipe has the result name as title, the time, batch savings, speed factors, amount made, crafting in the dark and the count nearby as stats, and the `crafting:facts` split: the `crafting:description` and `crafting:result` (the native item info of the result) texts, the `crafting:warnings` text, the `crafting:primary_skill`, `crafting:other_skills` and `crafting:autolearn` skill lists (`required` and `level` columns, `enabled` when met), the `requirements:tools` and `requirements:components` lists (a row per alternative with `required` and, where native counts it, `available` columns, `enabled` when at hand, under a parent row for a group of several) and the `crafting:byproducts` and `crafting:books` lists. `craft:select` moves the highlight, `craft:craft` (Enter) crafts the row, `craft:batch` with a `count` opens batch mode on that batch size, `craft:tab` and `craft:subtab` pick a tab by id, `craft:search` with a text is the native search (empty clears it), and `craft:favorite` and `craft:hide` toggle the row as their native keys do.
- The construction menu (`*`) is the screen of kind `construction` (role `screen`): the `construction:tabs` category tabs (one `FILTER` tab while a search is active) over the `construction:body` detail split. The `construction:groups` list has a row per construction group named by its group id, with the `look` of what it builds, `favorite` and a `denial` when it cannot be built. Beside it the `construction:detail` panel of the highlighted group has the group name as title and the `origin` and `category` stats, over the `construction:stages` split of a `construction:stage:<id>` panel per variant: the result name as title, `Stage/Variant #<n>` as subtitle, the move cost, bash strength, required terrain (`good` or `bad` by whether it is there), annotation, time, speed factors and terrain flags as stats, and the `<panel>:result` text, the `<panel>:skills` skill list and the `<panel>:tools` and `<panel>:components` requirement lists shaped as in the crafting menu. `construct:select` moves the highlight, `construct:construct` (Enter) starts the native placement, which then asks for the adjacent tile, `construct:tab` picks a tab by id, `construct:search` with a text is the native search (empty clears it) and `construct:favorite` toggles the row.
- The inventory selectors (the `i` screen and the item pickers) are the screen of kind `inventory` (role `screen`): the `inventory` panel, with the native title as the screen's title, the hint under it as subtitle, the active `filter` and, where the native window prints them, the `weight` and `volume` stats against capacity (`bad` past it), over the `split:columns` split of a panel per native column (`panel:inventory`, `panel:worn`, `panel:nearby`, `panel:extra<n>`; `active` is the cursor's), each holding its `list:<column>` list; an empty selector is the `text:empty` text. A list has a header row per category (`category:<hash>`, told apart by order) and a row per stack named by its items' serials (`item:<serial>` for one item, `stack:<lowest serial>` for several, never by position): `label` is the native name cell and `columns` the native cells after it (`cell1`, `cell2`, ...), with `hotkey` (the item's letter), `color`, `key_color`, `markup`, `look`, a `denial` where the selector refuses it, `selected` while chosen, the native item info as `description` on the cursor row only and, in a multi-select selector, `mark`, `selected_count`, `minimum_count` and `max`. In category selection the focus is the heading of the cursor's category. `list:<column>:choose` picks the row as its letter does; in a counting selector `list:<column>:count` sets the count of a row (0 clears the mark, a number is held to the stack) and `inventory:digit:<n>` (role `digit`) types a digit of the next count.
- The ground pickup list is the screen of kind `pickup`, docked by the `PICKUP_POSITION` option (`left`, `right`, `overlapping` or `cursor`): the `pickup` panel (title `Pick up`, the source as subtitle: ground, vehicle cargo, or ground or vehicle cargo nearby; the active `filter`; the predicted `weight` and `volume` against capacity as stats, `bad` where the native header prints red) holding the `pickup:items` list. A row per stack is named by its items' serials as in the inventory and carries the key the native list prints as `hotkey`, a backtick and two letters past the single letters, and none past those. Its `markup` is the row as the native list prints it: the stack size, the `ITEM_SYMBOLS` glyph and a `<color_light_red>!</color>` before an item that is not the avatar's; its `label` stays plain. `parent_id` and `nest_color` mark a stack nested in another, `selected`, `mark`, `selected_count` and `max` the marked amount, and the cursor row has the native item info as `description`. `pickup:toggle` (Enter) marks or unmarks a stack as its key does and `pickup:count` marks that many of it (0 unmarks it).
- The advanced inventory manager is the screen of kind `advanced_inventory` (role `screen`), the `aim:panes` split of the `aim:pane:left` and `aim:pane:right` panels (`active` is the source pane). A pane has `Left pane` or `Right pane` as title, the shown area or vehicle with its description and hazards as subtitle, its `filter`, and the stats `weight` and `volume` (against capacity for the carried areas, `bad` past it; the volume against the area's maximum elsewhere), `items` (against the maximum where the area has one) and `sort` (the native sort name). It holds the `<pane>:areas` grid, a cell per area of the native area picker (`area:INVENTORY`, `area:SW`, ..., `area:CENTER`, ..., `area:ABOVE`, `area:BELOW`, `area:DRAGGED`, `area:ALL`, `area:CONTAINER`, `area:WORN`) where the native header prints its key, three characters to a column, with that key as `glyph` (`V` on the shown area while it shows vehicle cargo), its localized `label`, `aim:set_area` as `affordance`, `selected` on the shown one and a `denial` where the item under the cursor cannot go, and the `<pane>:items` list: a header row per category while sorted by category (`<pane>:items:category:<id>`) and a row per stack named by its items' serials with `amount`, `weight` and `volume` columns (and `source` in the all-areas view), the native item info as `description`, `favorite`, `color`, `look`, `max` (charges or items) and `toggled` while auto-pickup takes it. `aim:move` with the source `pane` and `rows` (each with an optional `count`) moves them to the other pane's area as the native move does, and carries a `denial` when there is nothing to move or the destination takes none; `aim:set_area` with a `pane` and an area cell points that pane at the area as the native area key does; `aim:toggle_vehicle` switches a pane between the ground and the vehicle cargo there; `aim:filter` with a `pane` and a text sets its filter; `aim:close` leaves.
- The NPC trade window is the screen of kind `trade` (role `screen`), titled with the deal and the NPC (`Trading with`, `Paying`, `Accepting a reward from`): the `trade:head` panel, whose `category_mode` stat says whether category selection is on, holding the `trade:panes` split of the `trade:balance` text (credit, debt or exchange; `good` when the NPC would accept) and the `pane:npc` and `pane:you` panels (title `Inventory: <name>`, the carried `weight` and `volume` against capacity except for a shopkeeper, the pane's `filter`). Each holds its `list:npc` or `list:you` list (selection `count`): a header row per category (`trade-category:<hash>`, `selected` while category selection is on it) and a row per stack named by its items' serials with the `qty`, `weight`, `vol` and `price` columns (the price colored by how it compares to the item's value), `hotkey` only on the rows of the shown page, `mark`, `selected_count`, `max`, and the native item info as `description` on the cursor row. `trade:set_count` with a row and a `count` sets how much of it changes hands, `trade:filter` with a `pane` and a text filters that pane, and `trade:confirm` and `trade:cancel` are Enter and Escape.

- `message.logged` is the native message log: `data = {id, text, kind, color, count, turn}`, one event per line in log order, attached to the command that caused it. `text` is the translated line without color tags and without the "x N" suffix; `kind` is the native type (`good`, `bad`, `mixed`, `warning`, `info`, `neutral`, `debug`) and `color` the native color name of that type. When the last line repeats, the same `id` is published again with a higher `count` and replaces the line. It changes no state (no `revision`) and, like every transient event, is lost across a `bn.resync`; the log itself is not: `bn.subscribe` returns the newest 100 lines as `messages` (oldest first, same shape as `data`, omitted when empty), so a client that subscribes after a load, or again after a resync, starts with the log the native client shows. They are published where the game starts an animation, so every client gets the same facts without a renderer. They change no state, are attached to the command that caused them, and arrive before the state event of that command. `display.duration_ms` is how long the native animation holds the fact (the `ANIMATION_DELAY` option per step). `projectile.moved` carries `path` (squares in drawing order; one square per event while a shot flies) and a `look` of kind `projectile` with its glyph and custom sprite id. `explosion.started` carries `at`, `radius`, `color` and the `tile` id the native tiles draw it with. Whether to draw them is the client's to decide, so the `ANIMATIONS` option does not silence them (a client never changes the game); only combat text needs `ANIMATION_SCT`. `explosion.blast` lists one ring of `cells` of an explosion shaped by terrain; a custom explosion (an EMP, a scrambler, a spell) lists its whole area at once with `colors`, the native color name of each cell in the same order. `combat_text.shown` is the floating text of one or two colored `segments` at `at`, which moves by `scroll` (a unit step) each animation step like the native text; `kind` `hp` marks a creature's hit-point readout, which stays beside it.
- A thrown item is told as game events too, which the animation options do not silence; each is published only for what the avatar sees. `item.activated` (`at`, `look`, and `turns`, the whole turns left on a fuse) comes when the fuse is lit and again every turn it burns. `item.thrown` (`projectile`, `look`, `by`, `from`, `to`) opens the flight, whose `projectile.moved` events carry the same `projectile`, and `item.landed` (`at`, `look`, `projectile` when an attack launched it) closes it. A thrown or fired projectile has the same `projectile` in its `projectile.hit` (`at`, and `entity` when the avatar sees the creature struck; an obstacle has none), which follows its `projectile.moved` and comes before the `entity.damaged` and the terrain changes it caused. The pellets of one multishot (a shotgun shell) fly one after another, each with its own `projectile`, and their events come in that order; their `projectile.moved`, `projectile.hit` and `item.landed` carry the same `group`, so a client can present the pellets together as the native game does. An explosion is `explosion.started`, then for every logical time step its `explosion.blast` or `explosion.shrapnel` ring followed by what the step did, then `explosion.ended`: `entity.damaged` (`id`, `amount`, and `part` for a character) for each hit a creature takes, `terrain.changed` and `furniture.changed` (`at`, the `from` and `to` looks) for a square the step changed, and `field.changed` (`at`, `field`, `intensity` afterwards, 0 when the field is gone) for each field it added or removed. `entity.damaged` follows every damage a creature takes, including damage applied directly. Terrain, furniture and field changes are told wherever the game makes them, not only in explosions: at the shared map boundary for every call that changes a square the avatar sees (bashing a door, setting furniture, adding or removing a field), and for the field turn (fire spreading, gas drifting, fields fading, also over skipped turns) by comparing the fields the avatar sees on its level before and after, one `field.changed` per square that differs. A square told after a long wait is told once.
- `sound.heard` (`text`, `volume`, `marker`, `logged`) is a sound that reached the avatar through the native hearing rules: its volume against the ambient noise, hearing protection, sleep and deafness. `text` is the description the native message names, `volume` the decibels the avatar hears it at, and `marker` the square the native game marks it on. The marker is never the source: it is a square out of the avatar's sight near it, and it is left out when the avatar is or sees the source, so a hidden source is not given away. The log line of a sound follows the native message rules and the cooldown; `sound.heard` is published for every sound heard, including those the log leaves out, such as footsteps. `logged` is `true` when the sound also has a line in the message log, so a client that shows both lists the sound once. The avatar's own shout counts as logged, since its action logs its own line (`You yell ...`).
- `sound.played`, `sound.channel` and `music.changed` are what the native sound player is asked to play, told whether or not the engine plays audio itself. The client plays them from the sound pack in the folder the hello names as `engine.sound.soundpack` (absent while the `SOUND_ENABLED` option is off), the way the native player does. `sound.played` (`id`, `variant`, `volume`, `angle`, `stacks`, `wait_ms`) is one `sound_effect` of the pack: a pack without the variant plays the effect's `default` variant, one of the effect's `files` is picked at random, `stacks` `false` skips the sound while the same one still plays, and a sound with `wait_ms` (footsteps, obstacles, gunshots) plays only once that many milliseconds passed since the last one with `wait_ms` played, then starts the wait again. `sound.channel` (`channel`, `id`, `variant`, `volume`, `gain`, `angle`, `loops`, `fade_ms`) is what a reserved channel (ambience, weather, danger themes, engines, the radio) plays now: a new sound starts with a fade-in of `fade_ms`, the same `id` and `variant` keep playing at the new `gain` (a volume change, in mixer units with no option or pack volume applied) or `angle`, and a channel without `id` fades out over `fade_ms`; channel `any` fades out every channel and sound effect. The first stream starts with the channels and the music that already play; a stream of a new `epoch` goes on from what the one before told. A channel still playing a sound that does not repeat until it stops (`loops` 0 or more) ignores a new start. `music.changed` (`playlist`, `volume`) names the pack's playlist to play, in order or shuffled as the playlist says; without `playlist` the music stops. `volume` is in mixer units (128 is the full gain) with the native `SOUND_EFFECT_VOLUME`, `AMBIENT_SOUND_VOLUME` or `MUSIC_VOLUME` option applied, and the pack's own `volume` (0-100) of the effect or playlist entry scales it. `angle` is clockwise degrees from straight ahead (90 is to the right) where the native mixer places the sound. An engine built without sound (`SOUND=OFF`) publishes none of them.
- `entity.moved` (`id`, `to`, `from`, `mode`) and `entity.gone` (`id`, `reason`) let a client follow creatures through an action without a resync, for the monsters and NPCs the snapshot discloses. `entity.moved` is published for every move of a creature the avatar sees at its new square; `from` is left out when the avatar did not see the square it came from, and `mode` is `walk` for a step to a neighboring square and `propelled` for any longer move (a shove, a teleport). The avatar's own moves are in the state delta. `entity.gone` says a creature the client knew is no longer disclosed: `lost_sight` (it stepped out of sight, or the avatar moved or the view changed), `died`, or `removed` (it left the game). A creature that steps out of sight is `gone` at once; the rest are found when the boundary is published. A busy turn publishes the first 256 `entity.moved`, `terrain.changed`, `furniture.changed` and `field.changed` events (the `gone` ones of creatures that step out of sight count too); the `cells.seen` change set of the boundary always holds the final state, so the events add order and timing and never replace it.

Events are `interaction.changed`, `coverage.moved`, `turn.passed`, `cells.seen`, `message.logged` the animation facts above and, later, the remaining presentation types listed in the schema. Event types added before 0.2 is released belong to 0.2; once it is released, a new event type needs a new exact version.
