외부 클라이언트는 `cataclysm-bn-tiles --client=mcp`의 stdio에서 줄바꿈으로 구분된 JSON-RPC 2.0으로 게임을 플레이합니다. 값은 [Draft 2020-12 스키마](../../../schema/engine-client/0.2.schema.json)가 정의하며, 아래 예시는 모두 [예시 파일](../../../schema/engine-client/0.2.examples/)에서 스키마로 검증됩니다. 기존 MCP 도구(`bn.observe`, `bn.press` 등)는 별개이며 바뀌지 않습니다. 클라이언트가 `bn.hello`를 호출하면 이 도구들은 입력을 거부합니다.

## 세션

```text
-> {"jsonrpc":"2.0","id":1,"method":"bn.hello","params":{"versions":["0.2"],"client":{"name":"my-client","version":"1"},"schema":"sha256:0123456789abcdef"}}
<- {"jsonrpc":"2.0","id":1,"result":{"version":"0.2","epoch":"epoch:e7f3","engine":{"build":"...","mods":["bn"],"display":{"tiles":true,"tileset":"UNDEAD_PEOPLE_BASE"},"sound":{"soundpack":"/opt/bn/data/sound/Basic"}},"limits":{"frame_bytes":1048576,"cells_per_part":512,"cells_per_query":4096,"screen_queue":8},"schema":"sha256:0123456789abcdef","locale":"en","engine_locale":"en","role":"controller"}}
-> {"jsonrpc":"2.0","id":2,"method":"bn.subscribe","params":{}}
<- {"jsonrpc":"2.0","id":2,"result":{"at":{"epoch":"epoch:e7f3","sequence":"40","revision":"31"},"interaction":{...},"entities":[],"parts":1}}
<- {"jsonrpc":"2.0","method":"bn.snapshot.part","params":{"epoch":"epoch:e7f3","at":{...},"index":0,"last":true,"cells":[...]}}
-> {"jsonrpc":"2.0","id":3,"method":"bn.command.submit","params":{"epoch":"epoch:e7f3","expect":{"revision":"31","boundary_id":"boundary:90","schema_id":null},"operation":{"kind":"action","action_id":"RIGHT"}}}
<- {"jsonrpc":"2.0","id":3,"result":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"received"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"validated"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"executing"}}
<- {"jsonrpc":"2.0","method":"bn.events","params":{"epoch":"epoch:e7f3","events":[{"sequence":"41","revision":"32","type":"interaction.changed","command":"c:5","changes":{...}}]}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"completed","at":{"epoch":"epoch:e7f3","sequence":"41","revision":"32"}}}
```

`parts` 개수만큼 스냅샷 파트를 모은 뒤 `bn.events`를 순서대로 적용합니다. 누락(gap), epoch 불일치, `bn.resync`가 오면 `bn.subscribe`를 다시 호출합니다. 새 스냅샷은 상태만 복원하며, `lost_after` 이후의 일시적 이벤트는 유실로 보고되고 다시 전송되지 않습니다. 엔진은 이벤트 이력을 보관하지 않습니다. `bn.unsubscribe` 이후나 뒤처진 뒤에는 `bn.subscribe`만이 복구 방법이며, 그 스냅샷(재전송이 아님)이 마지막으로 본 `(epoch, sequence)`를 대체합니다. `bn.resync`가 멈추는 것은 이벤트뿐이며, 스냅샷에 담기지 않는 `bn.command` 단계는 계속 옵니다. 단계는 그 `at`보다 새로운 스냅샷 뒤에 올 수도 있습니다. 단계는 `bn.subscribe`부터 `bn.unsubscribe` 또는 `bn.hello`까지 푸시되며, 그 밖의 명령 결과는 `bn.command.result`로 읽습니다. 오래된 `epoch`를 지정한 요청은 모두 `stale_epoch`와 `action: "subscribe"`로 실패합니다.

## 메서드

| 메서드                   | 매개변수                                                   | 결과                                                                                             |
| ------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `bn.hello`               | `versions`, `client`, `schema`, `locale?`, `capabilities?` | `version`, `epoch`, `engine`, `limits`, `delivery?`, `schema`, `locale`, `engine_locale`, `role` |
| `bn.viewport`            | `cols`, `rows`                                             | 없음                                                                                             |
| `bn.interrupt`           | 없음                                                       | 없음                                                                                             |
| `bn.hold`                | `epoch`, `screen_id`, `affordance_id`                      | 없음                                                                                             |
| `bn.release`             | 없음                                                       | 없음                                                                                             |
| `bn.subscribe`           | 없음                                                       | 스냅샷 헤더. 이어서 파트와 이벤트가 전송됨                                                       |
| `bn.unsubscribe`         | 없음                                                       | 없음                                                                                             |
| `bn.interaction.choices` | `epoch`, `boundary_id`, `offset`, `limit`                  | `boundary_id`, `total`, `choices` (읽기 전용)                                                    |
| `bn.world.describe`      | `epoch`, `boundary_id`, `pos`                              | `lines` (읽기 전용)                                                                              |
| `bn.world.cells`         | `epoch`, `min`, `max`                                      | `at`, `cells`, `forgotten` (읽기 전용)                                                           |
| `bn.overmap.cells`       | `epoch`, `min`, `max`                                      | `overmap` 한 층의 칸들, 커서와 무관 (읽기 전용)                                                  |
| `bn.command.submit`      | `epoch`, `expect`, `operation`                             | `command_id`, `stage: "received"`                                                                |
| `bn.command.result`      | `epoch`, `command_id`                                      | 최신 단계. 유실된 알림을 복구할 때 사용                                                          |
| `bn.credit`              | `frames`                                                   | 부여 후 보유 `credits`                                                                           |

엔진이 보내는 알림은 `bn.snapshot.part`, `bn.events`, `bn.command`, `bn.resync`, `bn.loading`, `bn.progress`입니다. `bn.loading`과 `bn.progress`를 제외한 알림은 구독한 클라이언트에 입력 경계마다 전송됩니다. `bn.progress`(`{epoch}`)는 하트비트로, 대기 같은 활동이 입력 경계에 도달하지 않고 계속되는 동안 `bn.hello`를 마친 클라이언트에 2초마다 전송됩니다. 통신이 끊기면 엔진이 일하지 않는다는 뜻입니다. 월드를 불러오는 동안은 `bn.loading`이 같은 역할을 합니다.

오류는 코드 `1000`과 `error.data = {kind, action?, at?}`를 사용하며, `action`은 다음에 할 일(`hello`, `subscribe`, `retry`)을 알려 줍니다.

## hello와 스택

엔진은 모든 전송 방식에서 `"0.2"`만 제공한다. `"0.2"`를 나열하지 않은 hello는 `negotiation_failed`, `action: "hello"`로 실패한다. hello는 다음을 담아야 한다.

- `schema`: `sha256:`과 [`0.2.schema.json`](../../../schema/engine-client/0.2.schema.json) 원본 바이트의 SHA-256 앞 16자리 16진수. 해시가 다르면 `negotiation_failed`, `action: "hello"`, `error.data.schema = {engine, client}`로 실패한다. 엔진은 CMake 구성 시 스키마 파일에서 해시를 얻는다.
- 선택 항목 `locale`, `capabilities`(`tiles`, `tint_ids`, `viewport`, `delivery`; 개별 멤버로 보내도 받지만 두 형식을 함께 쓸 수 없다). 결과에는 `schema`, `locale`(연결의 텍스트 언어), `engine_locale`, `role`이 추가된다. 엔진에 카탈로그가 없는 `locale`은 `unavailable_locale`, `action: "hello"`로 실패한다.

모든 상호작용 경계(스냅샷 헤더와 이벤트)는 `interaction` 옆에 `stack`을 담는다. 스택은 열린 화면을 바깥쪽부터 나열하며 마지막 화면만 affordance를 가진다. 화면의 `kind`는 어떤 화면인지(`map`, `crafting`, `uilist`, ...)를 나타내며, 열 때마다 그리고 어느 언어에서나 같으므로 클라이언트는 창의 위치처럼 화면마다 기억하는 것을 이 값으로 구분한다. `kind`가 없는 화면은 엔진이 아직 이름을 붙이지 않은 화면이다. `component_id`가 있는 `bn.interaction.choices`는 맨 위 화면의 해당 목록(`rows`, `total`)을 읽는다.

`bn.command.submit`은 `operation: {kind: "invoke", affordance_id, args?}`를 받는다. `expect`는 affordance의 `expect` 범위를 따른다.

- `screen`: `{screen_id}`. 그 화면이 맨 위인 동안만 유효하며, 아니면 `stale_screen`으로 거부된다. 엔진은 명령이 실행 중일 때 이런 제출을 최대 8개(hello 결과의 `limits.screen_queue`) 대기시키고 차례가 되면 각각 검증한다. 키를 누르고 있어도 계속 움직이고, 이미 닫힌 팝업을 향한 키는 거부된다.
- `boundary`: `{boundary_id, revision}`, 기존과 같다. 명령이 실행 중이면 `command_busy`로 실패한다.

affordance와 맞지 않는 형식은 `invalid_arguments`다.

꺼져 있지만 고를 수 있는 affordance, 행, 탭, 격자 칸에는 항상 `denial`이 있다. 화면이 준 이유를 플레이어의 언어로 담고, 없으면 지금은 쓸 수 없다는 말을 담는다. 클라이언트는 이것을 이유로 보여 주고 자기 말을 덧붙이지 않는다.

## 누르고 있는 키

지도의 이동 한 걸음에는 `holdable`이 붙습니다. 클라이언트는 키가 내려갈 때 `bn.hold`를 한 번, 올라올 때 `bn.release`를 보내며 키 반복에는 invoke를 보내지 않습니다. hold가 유지되고 지도가 최상단 화면이며 입력을 기다리는 동안 엔진은 입력 프롬프트마다 네이티브 키를 한 번 더 누른 것처럼 그 동작을 한 걸음씩 게임에 넘기며, 걸음 전에 클라이언트가 이미 보낸 요청을 먼저 읽습니다. 탭은 먼저 놓아도 한 걸음을 보장합니다. 팝업이나 다른 화면이 위에 오거나, 걸음이 아바타의 칸도 턴도 바꾸지 못했거나, 새 `bn.hello`, 연결 종료가 hold를 끝냅니다. `bn.hold`는 활동 중이면 `not_ready`, 최상단이 아닌 화면이면 `stale_screen`, 없거나 hold할 수 없는 affordance면 `unknown_affordance`/`invalid_arguments`로 실패합니다. 화면 범위 invoke는 그대로 큐에 쌓입니다(목록에서 화살표를 누르고 있을 때).

## 전달 크레딧

`bn.hello`의 `delivery = {credits, max_hz?}`(`credits` 1~256, 선택 `max_hz` 1~240)로 켭니다. 결과에는 `delivery = {credits, held_frames, held_bytes, max_hz?}`가 붙고, `max_hz`를 요청했다면 그대로 되돌려 줍니다. `delivery`를 보내지 않으면 아래는 적용되지 않으며, 푸시되는 프레임은 전과 같이 입력 경계와 자동 이동 단계에서 즉시 기록됩니다.

- 푸시되는 `bn.events`와 `bn.command` 프레임은 크레딧 1을 소비합니다. 남은 크레딧이 없으면 엔진은 프레임을 순서대로 보관했다가 `bn.credit {frames}`로 더 부여되면 기록합니다(결과는 부여 후 보유 크레딧이며 상한은 256, 보관된 프레임은 응답 뒤에 이어집니다). 스냅샷 부분, `bn.resync`, `bn.loading`, `bn.progress`는 크레딧을 쓰지 않습니다.
- 엔진이 클라이언트 하나를 위해 보관하는 양은 최대 `held_frames` 프레임, `held_bytes` 바이트입니다. 둘 중 하나를 넘기면 보관 중인 `bn.events`를 버리고, 이유 `backpressure`의 `bn.resync`(`lost_after`는 기록한 가장 최근 sequence)를 보낸 뒤 클라이언트가 `bn.subscribe`를 호출할 때까지 이벤트 푸시를 멈춥니다. 그 스냅샷이 버려진 것을 대체합니다. 보관 중인 `bn.command` 프레임은 남아 크레딧이 지불되는 대로 `bn.resync` 뒤에 옵니다. `bn.subscribe`도 보관 중인 이벤트만 버리므로 명령의 끝은 유실되지 않습니다. 보관 한도보다 많은 단계를 지불하지 않고 남긴 클라이언트만 그중 가장 오래된 것을 잃습니다.
- 크레딧이 있는 클라이언트는 진행 중인 활동(대기, 제작 등) 동안에도 명령이 완료되기 전에 프레임을 받습니다. 월드 캡처는 한 턴보다 훨씬 비싸므로 엔진은 매 턴이 아니라 게시에 드는 시간이 활동 시간의 5분의 1이 되는 간격으로만 게시하며, `max_hz`가 있으면 실제 시간 기준 1/`max_hz`초에 한 번 이하라는 제한도 더해 더 성긴 쪽을 따릅니다. 프레임은 직전 프레임 이후의 변경분을 담고, 상태 변경은 합쳐지며 모든 메시지와 연출 사실은 순서대로 들어 있고, 활동이 끝나는 경계가 나머지를 담습니다. `bn.command`의 `completed`는 여전히 입력 경계에서 옵니다. 스트림은 클라이언트를 기다리지 않습니다. 크레딧 부여를 멈춘 클라이언트가 엔진에 지우는 비용은 보관 상한까지이며, 게임, RNG, 저장은 모두 읽는 클라이언트나 클라이언트가 없는 경우와 같습니다.
- 크레딧 때문에 활동이 기다리는 일은 없습니다. stdout은 컨트롤러로서 소켓과 같이 처리되므로(`소켓과 관전자` 참고), 크레딧이 있는 프레임은 막히지 않고 기록되는 버퍼로 가며 stdout이 가득 차도 엔진은 stdin을 계속 읽습니다. 파이프보다 큰 프레임은 클라이언트가 읽기를 최대 10 ms 기다리므로, 바로 읽는 클라이언트는 프레임 전체를 받습니다. 그동안 아무것도 읽지 않은 클라이언트는 다시 읽을 때까지 기다리지 않습니다. 활동이 프레임을 내보내는 속도보다 느리게 읽는 클라이언트는 크레딧이 바닥나 위와 같이 재동기됩니다. 16 MiB를 넘게 읽지 않은 클라이언트는 소켓과 같이 연결이 끊깁니다. stdio에는 다음 컨트롤러가 없으므로 엔진은 진행 중인 게임을 저장하고 종료합니다. Windows의 stdio는 이렇게 처리되지 않습니다. 기록은 파이프가 받아 줄 때에야 끝나므로, 크레딧을 준 만큼 읽지 않는 클라이언트를 활동이 기다립니다.

## 프레임과 실패

- 프레임은 한 줄의 JSON 값 하나이며 양방향 모두 `limits.frame_bytes`를 넘지 않습니다. 프레임은 단일 기록자가 통째로 쓰므로 섞이지 않으며, 엔진은 한 번에 프레임 하나만 읽고 그 이상 쌓아 두지 않습니다.
- JSON이 아닌 줄에는 `-32700`, 모양이 틀린 JSON에는 `-32600`, 알 수 없는 `bn.` 메서드에는 `-32601`, 잘못된 params에는 `-32602`로 답합니다. 읽을 수 있는 `id`가 없으면 `id`는 `null`이고, 알림에는 답하지 않습니다. 이런 프레임은 게임도 보관된 프레임도 바꾸지 않으며, 활동이 진행 중이어도 연결은 유지됩니다.
- 최대 길이를 넘는 프레임이나 stdin 종료로 잘린 프레임에는 답할 수 없습니다. 엔진은 더 읽지 않고 이유를 stderr에 쓴 뒤 종료 코드 1로 끝납니다(소켓에서는 그 연결만 끝납니다).
- 활동이 진행 중에는 요청에 답하지만 아무것도 시작하지 않습니다. `bn.command.submit`은 다음 입력 경계까지 `not_ready`로 실패하고, `bn.interrupt`는 활동이 받는 유일한 제어이며, `bn.viewport`, `bn.subscribe`, `bn.credit`은 전달되는 내용만 바꿉니다. 명령은 활동이 끝나는 경계까지 열려 있습니다. `bn.hello`를 다시 보내면 전달을 재협상하고 보관된 프레임을 버리며 구독을 해제하므로, 스트림은 다음 `bn.subscribe`에서 다시 시작합니다.
- 종료 시(stdin 종료, 게임 종료) 엔진은 크레딧으로 지급되는 보관 프레임을 순서대로 기록하고 나머지는 버립니다. 끝나지 않은 명령의 `interrupted` 단계도 여기에 포함됩니다. `SIGTERM`과 `SIGINT`는 stderr에 신호를 밝힌 뒤 엔진을 즉시 끝냅니다. 읽기를 멈추고 자기 쪽을 닫은 클라이언트는 실패한 기록을 통해 엔진을 끝냅니다.

## 소켓과 관전자

`--client=mcp --listen <path>`는 stdio 대신 같은 프로토콜을 로컬 스트림 소켓(유닉스 도메인 소켓, Windows 10 이상에서는 `AF_UNIX`)으로 제공합니다. 옵션이 없으면 아무것도 바뀌지 않습니다. 엔진은 사용자만 읽을 수 있는 파일을 만들고, 응답하는 곳이 없는 오래된 파일은 교체하며, 사용 중인 경로는 거부합니다. 프레임은 같은 줄이고 한도도 같습니다. 동시에 최대 8개의 연결만 처리하며 그 이상은 즉시 닫습니다. 월드를 불러오는 동안에도 연결할 수 있고 `bn.loading`을 받습니다.

- **역할.** 첫 연결, 그리고 컨트롤러가 없을 때 맺은 연결이 컨트롤러이며 게임에 명령할 수 있는 것은 컨트롤러뿐입니다. 나머지 연결은 관전자이고 각자 `bn.hello`, 크레딧, 보관 프레임(256 프레임, 1 MiB), 구독을 따로 가집니다. 관전자는 컨트롤러가 읽을 수 있는 모든 것(컨트롤러 명령의 단계와 이벤트 포함)을 읽지만 `bn.command.submit`, `bn.interrupt`, `bn.viewport`, 레거시 `bn.press`와 `bn.interact`는 `read_only`로 실패하고, 관전자의 `bn.hello`는 컨트롤러의 뷰포트와 타일 설정을 건드리지 않습니다. 연결 중에는 역할이 바뀌지 않으며, 제어하려는 관전자는 컨트롤러가 떠난 뒤 다시 연결합니다.
- **막지 않음.** 출력은 연결별 버퍼에 막히지 않고 기록되며(컨트롤러의 프레임은 stdio와 같이 읽기를 최대 10 ms 기다립니다), 16 MiB를 넘게 보내지 못한 연결은 그전에 크레딧이 스트림을 멈추지 않았다면 닫힙니다. 게임은 stdio와 같이 컨트롤러의 입력만 기다리며 그동안 관전자를 처리하므로, 느리게 읽거나 전혀 읽지 않는 관전자가 게임이나 컨트롤러를 늦추지 않습니다. 크레딧 때문에 활동이 소켓을 기다리는 일도 없습니다.
- **연결 해제.** 연결을 닫으면 그 연결을 위해 보관하던 것이 모두 해제되고 재연결을 위해 남기는 것은 없습니다. 돌아온 클라이언트는 `bn.hello`와 `bn.subscribe`를 보내 그 스냅샷에서 이어 가며, 이는 `bn.resync` 뒤와 같습니다. JSON이 아닌 프레임은 위와 같이 답하고 연결을 유지하며, 한도를 넘거나 연결 종료로 잘린 프레임은 그 연결만 끝냅니다(stdio에서는 엔진이 끝납니다).
- **컨트롤러가 떠날 때.** 열려 있던 명령은 `interrupted`가 됩니다. 진행 중인 활동은 끝까지 이어지고, 그 뒤 게임은 키를 누르지 않은 플레이어처럼 입력 경계에서 연결이 올 때까지 기다리며, 다음 연결이 컨트롤러가 됩니다. 관전자는 연결된 채 남아 게임이 어디까지 왔는지 전달받습니다. 소켓이 닫혀도 엔진은 끝나지 않으며, 게임이 끝나는 방식이나 `SIGTERM`, `SIGINT`로 끝납니다.

## 하나의 시계

- `epoch`는 프로세스가 시작되거나 월드가 교체될 때 바뀌며, 읽기에서는 바뀌지 않습니다.
- `sequence`는 게시된 이벤트 수입니다(10진 문자열, 연속, `"1"`부터 시작). `revision`은 상태를 바꾸는 이벤트 수입니다. `at = {epoch, sequence, revision}`은 "sequence까지의 모든 이벤트를 포함한다"는 뜻입니다.
- 명령은 `expect = {revision, boundary_id, schema_id}`를 가집니다. 오래된 값은 거부되므로 클라이언트는 보지 못한 화면에 대해 행동하지 않습니다. `schema_id`는 해당 경계에 상호작용이 없을 때만 `null`입니다.

## 명령

`operation.kind`는 `choose`, `fill`, `set_count`, `set_target`, `cancel`(의미 기반 메뉴) `action`(이동 키 같은 등록된 행동) `travel`(맵 클릭) 또는 `tile_action`(맵 칸에 대한 행동, 아래 참조) 중 하나입니다.

```json
{ "kind": "choose", "choice_id": "tab:new_game" }
{ "kind": "set_target", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
{ "kind": "action", "action_id": "RIGHT" }
{ "kind": "travel", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
```

모든 경계 액션은 활성 입력 컨텍스트가 그 액션에 묶은 단일 키보드 키의 이식 가능한 이름(`ESC`, `SPACE`, `RETURN`, `UP`, `>` 등)을 `keys`로 나열합니다. `action`은 액션을 id로 실행하며, 키가 없는 액션(키가 지정되지 않은 `open_options` 등)도 실행합니다. 눌린 키로 동작하려는 클라이언트는 키 설정 파일에서 추측하지 말고 `keys`에 그 키가 있는 액션을 찾아야 합니다.

`travel`은 상호작용이 없는 경계에서 화면에 보이는 절대 맵 칸에 대한 Tiles와 curses의 왼쪽 클릭입니다. 첫 클릭은 엔진 자체의 경로를 `route`로 게시하고, 같은 칸을 다시 클릭하면 네이티브 자동 이동이 시작됩니다. 이후 아바타는 한 걸음씩 걸으며 걸음마다 해당 명령에 연결된 일반 이벤트가 게시되고, 엔진이 멈추는 곳(도착, 몬스터 시야 진입 등)에서 멈춥니다. 걷기가 끝나 다시 입력을 기다리면 명령은 `completed`가 됩니다. 다른 명령이나 다른 칸 클릭은 계획을 바꾸거나 지웁니다. 클라이언트는 경로를 직접 계산하지 않습니다.

클릭이나 잡무가 칸과 아이템에 무엇을 하는지도 엔진이 정합니다. 아바타 옆의 열 수 있는 닫힌 문에 대한 왼쪽 `travel`은 경로 클릭이 아니라 그 문으로의 이동(네이티브 이동이 문을 엶)입니다. `pickup`과 `drop`은 `{ "kind": "pickup" | "drop", "item_id", "count" }`를 받습니다. `item_id`는 `avatar.ground`(pickup) 또는 `avatar.inventory`(drop) 행의 `id`, `count`는 그 행에서 가져갈 양을 네이티브 단위(못처럼 충전량으로 세는 아이템은 충전량, 그 밖에는 아이템 개수)로 나타내며, 엔진은 메뉴에서 표시하고 확정했을 때와 같은 네이티브 줍기·버리기 활동을 시작합니다. 행 ID는 그 더미가 그대로인 동안 유지되고, 행이 사라졌거나 `count`보다 적게 남았으면 명령은 `validation_failed`로 거부됩니다. 실패한 명령은 현지화된 이유를 `error_text`(명령 결과와 `bn.command`) 또는 `message`(JSON-RPC 오류의 `data`)로 전합니다. 엔진이 아는 경우 `error`보다 구체적입니다(지도 창 밖으로의 이동, 더미보다 많은 개수 등). 대상 지정 상호작용(`context`가 `TARGET`)은 `target.distance`(`distance_metric`에 따른 `source`에서 `current`까지의 거리, 수직 축 포함)를 담고, 화면이 사거리와 준비 상태를 알려 주는 경우 `target.status_text`(현지화된 사거리와 상태 줄)도 담습니다. 아무 키로나 넘어가고 키가 지정되지 않은 화면(아무 키 팝업, 컴퓨터 단말 프롬프트)은 고를 선택지를 `interaction.any_key_choice_id`로 알려 줍니다.

`context`는 같은 칸에 대한 오른쪽 클릭(SEC_SELECT)입니다. 네이티브에서는 인접한 칸을 조사하거나, 인접한 문을 닫거나, 발밑 아이템을 줍거나, 보이는 몬스터를 쏘거나, 계획된 경로를 먼저 취소합니다. `bn.world.describe`는 터미널 창 안의 칸에 마우스를 올렸을 때 네이티브 마우스 뷰가 출력하는 텍스트를 돌려줍니다(범위 밖은 `validation_failed`). 아무것도 선택하거나 계획하지 않습니다. `bn.world.cells`는 한 층의 상자(`min`과 `max` 포함, `dim`과 `z`가 같고 최대 `limits.cells_per_query`칸) 안에서 아바타가 아는 것을 돌려줍니다. 셀은 스냅샷이 가진 그대로이며, `forgotten`은 상자 안의 로드된 범위(coverage) 안에서 아무것도 알려지지 않은 칸입니다. 뒤집힌 상자나 여러 층에 걸친 상자는 `validation_failed`, 너무 큰 상자는 `resource_limit`, 다른 `epoch`은 `stale_epoch`입니다. 메뉴의 휠 한 단계는 등록된 행동 `SCROLL_UP` 또는 `SCROLL_DOWN`이며 엔진이 네이티브 커서를 세 행 옮깁니다.

`tile_action`은 `bn.world.describe`가 칸에 대해 나열하는 `actions` 중 하나를 `action_id`와 `pos`로 지정해, 그 칸에서 네이티브 액션이 하는 일을 합니다. 목록에는 지금 할 수 있는 것만 메뉴 순서대로, 네이티브 `label`과 플레이어의 `keys`(`attack`, `talk`, `travel`은 없음)와 함께 담깁니다. `attack`(아바타 옆에 있는 보이는 비우호 생물), `fire`(보이는 몬스터, 원거리 무기를 든 경우), `talk`(보이는 캐릭터), `open`, `close`, `pickup`, `examine`(아바타의 칸과 주변 8칸에서 네이티브 액션이 할 일을 찾는 경우), `travel`(아바타가 아는 칸, 경로 계획과 걷기 시작을 한 명령으로 함), `look`(항상, 그 칸에서 둘러보기를 엶)입니다. 그 칸이 지금 나열하지 않은 액션은 `validation_failed`입니다. 클라이언트는 이 목록을 칸의 오른쪽 클릭 메뉴로 보여 줍니다.

맵 화면은 `shortcuts`, 곧 바로가기 막대의 버튼도 가집니다. 이는 데이터(게임 JSON의 `client_shortcut`: `id`, `action`, `icon`, `glyph`, `order`; 모드는 새 id로 버튼을 추가하고 같은 id로 교체합니다)이며, 각 버튼은 맵 입력 컨텍스트의 등록된 액션을 가리킵니다. 엔진은 그 컨텍스트의 `label`과 `keys`, 데이터의 `icon`(불투명한 스프라이트 id)과 `glyph`(전용 그림이 없을 때 그릴 것), 맵이 맨 위에 있고 그 액션을 받는 동안 `enabled`를 붙여 공개합니다. 컨텍스트가 이름을 주지 않는 액션의 버튼은 빠집니다. 월드 맵 컴포넌트는 `item_lists`도 가집니다. 클라이언트가 맵 옆에 순서대로 보여 주는 아바타의 아이템 목록으로, 맵이 가려진 동안에도 옵니다. 목록마다 행을 담은 아바타 멤버를 `id`(`avatar.ground`, `avatar.inventory`)로, 제목을 `label`로, 행을 목록 밖으로 옮기는 동작(줍기, 버리기)을 `verb`로 주며, 둘 다 현지화되어 있습니다. 클릭은 `affordance_id`가 가리키는 어포던스의 `invoke`입니다. 화면의 어포던스는 `confirm`, `cancel` 외에 `role`로 `navigate`(커서, 페이지, 탭, 스크롤. 클라이언트는 키, 휠, 클릭으로 이미 처리함), `help`(키 설정 메뉴), `digit`(개수를 세는 목록의 개수에 입력하는 숫자 한 자리. 그 키에 묶인 액션보다 먼저 읽으며, 네이티브 목록처럼 다음 표시가 받을 개수가 되거나 그 숫자로 개수 입력창을 엶. 클라이언트가 그릴 필요 없음)를 가질 수 있습니다.

단계는 `received`, `validated`, `executing`, `completed`이며, 또는 `rejected`, 또는 `interrupted`이며, `interrupted`의 `error`가 이유를 알려 줍니다(월드가 교체되면 `stale_epoch`, 게임이 입력을 거부하면 `validation_failed`, 그 외에는 `not_ready`). 모든 단계에는 플레이어에게 보여 줄 번역된 말 `stage_text`(`Received.`, `Under way.`, `Refused.` 등)가 붙습니다. 처리 판단에는 `stage` id를 씁니다. `completed`는 입력이 다시 대기 중이라는 뜻입니다. 대기 같은 활동은 끝나거나 게임이 무언가를 물을 때(팝업, 중단)까지 먼저 실행됩니다. 그 `at`은 해당 경계의 끝 지점입니다. 따라서 입력이 여는 프롬프트(텍스트 칸, 수량)는 그것을 담은 이벤트가 먼저 오므로(`bn.resync` 뒤에는 이어지는 스냅샷이 담습니다) `completed`가 도착할 때 이미 상태에 있습니다. 그때 프롬프트가 없으면 프롬프트는 열리지 않은 것입니다. 한 번에 하나의 명령만 진행할 수 있습니다(`command_busy`). 대기 같은 활동이 실행되는 동안에도 요청에는 응답합니다. `bn.interrupt`는 네이티브 중단 키를 눌러 활동이 Tiles처럼 중지할지 묻게 하며, 그 질문이 다음 경계가 됩니다. 활동 중이 아니면 `not_ready`로 실패합니다.

## 로딩 화면

월드를 불러오는 동안 게임 스레드는 작업 중이라 입력 경계에 도달하지 않으므로, `bn.hello`를 마친 클라이언트는 네이티브 로딩 화면의 단계마다 `bn.loading`을 받습니다(구독 여부와 무관). 진행 상황은 네이티브 클라이언트가 보여 주는 화면과 같습니다. `title`은 현재 단계(예: "Loading files"), `entries`는 그 목록, `index`는 진행 중인 항목(앞선 항목은 완료), `image`는 네이티브 클라이언트와 같은 방식으로 고른 로딩 이미지입니다. `image.path`는 게임 기본 경로 기준 상대 경로이며, 파일 이름에 제작자가 없으면 `author`는 생략됩니다. 로딩 화면이 끝나면 `done`이 한 번 전송되고, 그 뒤에 평소처럼 `bn.resync`나 `bn.events`가 이어집니다. `epoch`는 해당 단계를 보낼 때의 epoch입니다.

```text
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","title":"Loading files","entries":["Terrain","Items"],"index":1,"image":{"path":"data/json/loading/Ada_dawn.webp","author":"Ada"}}}
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","done":true}}
```

## 값

- `pos = {dim, x, y, z}`는 절대 맵 칸이며, `dim`은 게임 차원이고 기본 차원은 `""`입니다. 현실 거품 좌표는 전송 형식에 나타나지 않습니다.
- `look = {kind, id, glyph, color}`는 게임 데이터의 외형을 담으므로 텍스트 클라이언트에는 타일셋이 필요 없습니다. 자동 벽 지형은 아바타가 아는 연결 상태에 맞는 선 문자를 담으며, 기억된 칸은 `memory.terrain` 위에 `memory.overlay`(가구, 함정, 차량 부품)를 유지합니다.
- `look`은 `name`, 즉 네이티브 look이 보여 주는 번역된 플레이어용 이름(`t_floor`는 "wooden floor")을 담으므로 텍스트·음성 클라이언트가 ID를 읽을 필요가 없습니다. 생물은 엔티티의 `name`을 씁니다.
- 타일 클라이언트는 같은 `look`을 게임 타일셋으로 그립니다. 엔진만 알 수 있는 정보(데이터와 네이티브 선택 로직을 가진 쪽이 엔진이므로)를 공개하고, 클라이언트는 이를 다시 구현하지 않습니다: `tile`(`id`와 다른 스프라이트 ID: `corpse_<monster>`, `player_male`, `vp_<part>`), `looks_like`(데이터의 대체 체인, 가까운 순), `subtile`과 `rotation`(아바타가 아는 이웃 칸으로 네이티브 선택이 계산한 멀티타일 키와 90도 회전 수이므로 연결 로직은 한 곳에만 존재), `stack`(더미의 표시 아이템), `attitude`와 `aware`(몬스터와 NPC, 네이티브 화면이 표식을 겹쳐 그림), `health`(다친 생물의 네이티브 둘러보기 체력 막대: 채워진 `fifths`(5분의 몇)와 `color`), `tint`(차량 부품의 도색, 타일셋이 스프라이트에 섞음), `reviving`(되살아날 시체가 있는 칸), `facing`(생물), 칸의 `light`(네이티브 `lit_level`: 0 어두움, 1 낮음, 2 밝기만, 3 조명, 4 밝음), `glow`(네이티브 타일 화면이 스프라이트 위에 더하는 색광: 빛의 `color`와 `strength` 1–255), `environment.season`, 아바타의 `look`, 캐릭터의 `overlays`(착용·들고 있는 아이템, 돌연변이, 바이오닉을 네이티브 순서로 시도할 스프라이트 ID를 `tile`과 `looks_like`에 담은 종류 `overlay`의 `look`)입니다. 파일, 가중치 변형, 레이어, 어둡게 하기는 타일셋이 정의하므로 클라이언트가 맡습니다. 그리기 순서는 지형, 가구, 함정, 필드, 아이템, 차량 부품, 생물이며 `fields`와 `items`의 마지막 항목이 네이티브 화면에 그려지는 것입니다. `light`는 시야 안의 칸만 다룹니다. 게임의 어두움·밝기만(0과 2) 단계는 아바타가 볼 수 없는 칸이므로 클라이언트는 평범하게 보이지 않는 모든 칸 아래에 hidden 조명 스프라이트를 깔고 `lowlight_dark`, `lowlight_light` 사실은 보내지 않습니다. 기억된 칸은 어둡게, `light`가 1이면 음영으로 그리고 스프라이트가 없는 ID는 `glyph`로 대체합니다.
- 돌연변이 오버레이는 `mutation`(돌연변이의 `id`, `types`, `flags`)을, 아바타나 엔티티는 `traits`(돌연변이 종류별 돌연변이 ID)를 가집니다. 타일셋의 `tints`와 `tint_pairs`가 이를 키로 삼아 머리카락, 피부, 눈의 색을 입힙니다. 환경은 `mod_tilesets`로, 타일셋에 스프라이트를 더하는 게임 데이터 파일을 네이티브 로딩 순서대로 `base` 폴더, 파일 안의 `index`, `compatibility`에 적힌 타일셋과 함께 나열합니다. 셀은 그 위 차량의 화물 부품에 물건이 들어 있으면 `cargo`를 가지며, 네이티브 화면은 그 부품을 강조합니다. 착용하거나 든 아이템, 바이오닉, 효과의 오버레이는 `tint_keys`를 가집니다. 타일셋의 `tints`가 키로 삼는 ID이며, 네이티브 화면이 시도하는 순서(플래그, 그다음 ID)입니다. hello는 `tint_ids`로 타일셋이 가진 틴트의 ID를 나열할 수 있습니다. 그러면 지형, 가구, 몬스터, 차량 부품, 아이템의 look이 그중에 해당하는 `tint_keys`(플래그, 그다음 ID)를 가지며, 틴트 변수를 가진 아이템, 지형, 가구는 `tint_vars`(타일셋 틴트 위에 덮는 색, 블렌드, 보정)를 가집니다. 필드의 look은 네이티브 화면이 칠하는 필드 종류의 틴트를 `tint`로 가집니다. 필드 종류가 그 아래 아이템을 가리면(연기, 불, 거미줄) 필드 항목은 `hides_items`를 가집니다. 그것이 표시되는 필드인 동안 네이티브 타일 화면은 아이템도 그 강조도 그리지 않습니다.
- 게임 데이터가 벽(`WALL`)으로 플래그를 단 지형은 보일 때도 기억될 때도 `wall: true`를 가지므로, 위에서 내려다본 타일셋을 3D로 그리는 클라이언트는 스프라이트로 추측하지 않고 벽을 세울 수 있습니다.
- 아바타의 층에서 보이고 네이티브 타일 화면이 비쳐 보는 칸(허공, 그리고 나무 꼭대기, 유리 지붕, 내리막 경사로처럼 바닥이 없는 지형)은 `below`를 가집니다. `below`는 네이티브 타일 화면이 그 자리에 그리는 칸이 몇 층 아래인지 나타냅니다. 바닥이 있는 첫 칸이나 무언가를 기억하는 첫 칸이 보이거나, 기억되거나, 차량이면 그 칸이고, 아니면 내려가는 동안 본 무언가가 있는 가장 낮은 칸입니다. 그 칸은 그 자체로도 공개됩니다. 비쳐 보는 칸은 그 위에 있는 것(필드 등)을 유지하고, 빈 허공은 그 밖에 아무것도 갖지 않으며, 비쳐 보이는 것이 없는 빈 허공은 공개하지 않습니다. 비쳐 보는 것은 보이는 칸뿐입니다.
- `interaction`은 네이티브 메뉴나 대화상자입니다. `columns`의 각 항목은 안정적이고 번역되지 않는 이름 `key`(영어 머리글을 소문자로 하고 단어 사이를 `_`로 이은 것, 예 `spell_level`, 인벤토리 셀은 `cell0`, `cell1`, …)와 번역된 머리글 `label`을 가지며, 클라이언트는 `key`로만 열을 찾습니다. 열은 값의 네이티브 색 이름 `color`를 가질 수 있습니다. 선택지는 `favorite`(즐겨찾는 주문), `color`, `key_color`(행 글자와 `hotkey`의 색 이름), `markup`(네이티브 색 태그가 붙은 이름), 네이티브 목록이 선택 표시를 그리는 곳에서 `mark`(`glyph`는 `+`, `#`, `-`와 `color`), 중첩 빗금을 그리는 곳에서 `parent_id`와 `nest_color`도 가집니다. `choices`는 처음 최대 200행을 담지만 크기 때문에 더 적을 수 있으므로, 나머지는 `bn.interaction.choices`를 `offset = choices.length`부터 읽습니다. 전체 행 수는 `choice_total`입니다. `compat.focus`와 `compat.panes`는 1:1 이식을 위해 네이티브 목록 상태를 유지하며 클라이언트는 무시해도 됩니다. 고급 인벤토리 관리자의 창에는 `sort`(네이티브 정렬 이름)와 `totals`(네이티브 창 머리글: `weight`, `volume`, 용량이 있는 구역은 `weight_max`/`volume_max`, 그리고 `weight_unit`, `volume_unit`, `over_weight`, `over_volume`; 네이티브가 표시하지 않는 최대값은 빈 문자열)도 포함됩니다. 메인 메뉴는 네이티브와 같이 탭 구조입니다. 각 탭은 `pane_id`가 없는 선택지(`tab:new_game`, `tab:load` 등, 선택된 탭은 `selected`)이고, 그 뒤에 선택된 탭의 항목만 해당 탭의 `pane_id`와 함께 이어집니다(`new_game:tutorial`, `settings:options`, `load:<world>`). 다른 탭을 선택하면 그 탭의 항목을 담은 새 interaction이 게시됩니다. ID는 위치나 언어에 의존하지 않습니다. 제작 메뉴(`context`가 `CRAFTING`)도 같은 탭 구조입니다. 분류 탭(`tab:CC_ELECTRONIC`), 선택된 분류의 하위 탭(`subtab:CSC_ELECTRONIC_TOOLS`, 검색 중에는 없음), 레시피(`recipe:<hash>`) 순이며 뒤의 둘은 분류를 `pane_id`로 가집니다. 탭이나 하위 탭을 선택하면 그 묶음이 나열되고, 레시피를 선택하면 제작하며, 레시피에 `set_count`를 보내면 일괄 제작에 들어갑니다. 각 레시피는 네이티브 상세 텍스트(기술, 시간, 도구, 재료)를 색 태그 없이 `description`에 담습니다. 건설 메뉴(`context`가 `CONSTRUCTION`, 키 `*`)도 같은 구조입니다. 분류 탭(`tab:<category id>`, 검색 중에는 `tab:FILTER` 하나), 이어서 건설 그룹마다 `construction:<hash>` 행이 있으며 `Favorite`, `Buildable` 열을 가지고 건설할 수 없으면 `denial`이 붙습니다. 각 행은 요구 사항을 색 태그 없이 `description`에 담습니다. 변형별 결과물, 필요 기술, 필요한 지형, 시간, 속도 보정, 도구와 재료(부족한 것 포함)입니다. `filter`가 네이티브 검색입니다. 행을 선택하면 네이티브 배치가 시작되고 이어서 인접한 칸을 묻습니다. `filter` 필드가 네이티브 검색이며, `submit: true`로 `fill`하면 검색하고 빈 값이면 해제합니다. 네이티브 콜백이 원시 키를 직접 판정하는 메뉴(wish 메뉴, 기술 메뉴)는 해당 키를 항목보다 앞에 키 이름을 라벨로 한 `action:key:<keycode>` 행으로 나열합니다. `choose`로 그 키를 누를 수 있으며, 긴 메뉴에서도 첫 페이지에 들어갑니다. 주문 메뉴는 각 주문 행에 네이티브 측면 패널이 그리는 상세를 싣습니다. `description`(계열, 설명, 레벨, 난이도, 경험치, 비용, 시간, 대상, 피해, 범위, 사거리, 지속시간, 재료; 색 태그 포함)과 `columns`의 `Spell Level`, `Failure Chance`, `Casting Cost`, `Casting Time`, `Range`이며 즐겨찾는 주문에는 `favorite`가 붙습니다. 즐겨찾기 전환, 시전 방해 전환, 단축키 지정 키는 `action:key:<keycode>` 행입니다. 네이티브 콜백이 옆 패널을 그리는 메뉴(무술 스타일, 변이·몬스터·아이템 위시 메뉴, 효과 선택, 전송 관문, 마법서의 주문)는 그 패널의 글(색 태그 포함)을 행 자체 설명 뒤에 `description`으로 싣습니다. 행마다 조회 비용이 드는 패널(무술 스타일, 위시 몬스터와 아이템)은 선택된 행에만 붙습니다. 네이티브 목록이 행 앞에 키를 표시하는 경우(메뉴 항목의 단축키, 인벤토리 아이템 문자) 그 행은 `hotkey`에 해당 키를 문자열로 가집니다. 그 키를 누르면 네이티브처럼 행이 선택됩니다. NPC 거래 창은 인터랙션에 `category_mode`(카테고리 선택이 켜져 있는지), 각 창에 `page`(`number`, `count`)를 싣고, `hotkey`는 보이는 페이지의 행에만 붙입니다. 인벤토리 선택기(`context`가 `INVENTORY`인 `i` 화면과 아이템 선택기)와 지면 줍기 목록은 `role`이 `inventory` 또는 `pickup`인 창 하나를 게시합니다. `area_label`은 네이티브 제목, `area_description`은 그 아래 안내문, `filter`는 적용된 필터, `totals`는 소지량(줍기에서는 줍은 뒤 예상량)의 무게와 부피를 용량과 비교한 값이며 네이티브가 표시하지 않으면 없습니다. 인벤토리 각 행은 `source`(`inventory`, `map_or_vehicle`, `worn_or_wielded`), 그 뒤의 네이티브 셀, 이어서 `category`(행이 속한 머리글)를 가지고, 행의 `color`, `key_color`, `markup`과 다중 선택 선택기의 `mark`는 형식이 있는 필드이며, `category_mode`는 범주 선택 중에 켜집니다. 줍기 행은 네이티브 목록이 그리는 키를 `hotkey`에 가지며, 한 글자 범위를 넘으면 백틱과 두 글자이고 그마저 넘으면 없습니다. 줍기 행의 `markup`은 네이티브 목록이 그리는 행 그대로(묶음 수, `ITEM_SYMBOLS` 기호, 자기 것이 아닌 아이템 앞의 `<color_light_red>!</color>`)이고 `label`은 그대로 평문입니다. 줍기 창 `area_id`는 `PICKUP_POSITION` 옵션(`left`, `right`, `overlapping`, `cursor`)이며, `totals`의 `over_weight`/`over_volume`은 네이티브 머리글이 붉게 그리는 경우에 켜집니다. 고급 인벤토리 관리자의 interaction은 `areas`도 담습니다. 네이티브 헤더와 같은 배치의 구역 선택기이며, 구역마다 활성 창을 그 구역으로 향하게 하는 `action_id`, 번역된 `label`(창은 `label`이 자신의 `area_label`과 같은 구역에 있음), `key`(플레이어가 그 액션에 지정한 키, 없으면 빈 문자열이며 키를 바꾸면 클라이언트 표시도 바뀜), `x`와 `y`(선택기 왼쪽 위 모서리에서 문자 칸 수), `available`(그 구역이 지금 존재함: 차량을 잡고 있거나, 그 칸에 차량이 있거나, 그 층이 존재함)이 있습니다. 동작 버튼의 이름은 등록된 액션의 `name`입니다. choice는 그 행이 실행하는 등록된 액션인 `action_id`를 가질 수 있습니다. 게임 내 메인 메뉴의 행이 가지므로 Options 행은 언어와 관계없이 `open_options`입니다. 줍기 목록의 `message`는 색 태그가 붙은 네이티브 헤더이며(용량을 넘는 예상 무게나 부피는 `<color_c_red>`로 감쌈) 필터가 둘째 줄에 이어집니다.
- 월드는 아바타가 아는 것입니다. `cells`(`remembered`, `visible`, `sensed`), `entities`, `avatar`(능력치, 소지품 `inventory`, 발밑 `ground`, 진행 중인 `activity`: 그 `name`과 길이가 정해진 활동이면 끝낸 천분율 `done`), `environment`, 로드된 `coverage`, `view`, 대기 중인 `route`(계획이 없으면 비어 있거나 없음)와 그 번역된 줄 `route_text`(예 `Route of 3 squares; select its end again to go.`, 경로가 없으면 없음)로 구성됩니다. `view`는 아바타가 있는 층에서 네이티브 지형 창이 보여 주는 `{min, max}` 칸입니다(아바타를 따라 움직임). `travel` 클릭은 이 안에서만 받아들여지고, 밖이면 `validation_failed`로 거부됩니다.
- `avatar.inventory`는 손에 든 아이템, 착용한 아이템, 들고 있는 스택 순서이며 각 항목은 `{look, name, count?, slot, durability?}`이고 `slot`은 `wielded`, `worn`, `carried` 중 하나입니다. `avatar.ground`는 아바타가 선 칸의 스택을 `slot` 없이 같은 형태로 나열합니다. `count`는 행이 가진 양을 네이티브 단위(충전량으로 세는 아이템은 충전량, 그 밖에는 아이템 개수)로 나타내며, 그 행의 `pickup`이나 `drop`이 가져갈 수 있는 최대량입니다. `name`은 네이티브 목록이 보여 주는 표시 이름이며 색 마크업을 포함하지 않습니다. `name`이 네이티브 상태 표시로 시작하면 `durability`가 그 표시를 `{symbol, color}`로 알려 주어 클라이언트가 그 색으로 그릴 수 있습니다. 두 배열 모두 비어 있으면 생략됩니다. 각 행에는 `label`도 있으며, 네이티브 목록이 표시하는 그대로의 행입니다. 스택의 표시 이름에 개수와 상태 표시를 색 마크업으로 붙이고, 이어서 장비 상태(`(wielded)`, `(worn)`)를 플레이어의 언어로 붙입니다.
- 캐릭터 화면은 텍스트가 아니라 네이티브 값과 색을 공개합니다. `PLAYER_INFO`(`@`)는 여섯 탭(`stats`, `encumbrance`, `skills`, `traits`, `bionics`, `effects`)을 `pane_id` 없는 choice로, 이어서 각 탭의 행을 그 탭의 `pane_id`로 나열합니다. 열의 `color`는 값의 네이티브 색 이름이고 특성과 바이오닉 행은 행의 `color`가 이름의 색입니다. 능력치 행의 값은 `current` 열입니다. 속도 내역은 `pane_id`가 `speed`인 행으로, 선택할 수 없고 `color`가 붙은 `value` 열을 가집니다. 이 버전의 시트에는 숙련 탭이 없습니다. `BIONICS`(`p`)는 `active`와 `passive` 탭을 `panes`(`role`은 `current` 또는 `inactive`)에 보이고 현재 탭의 행만 나열하며, 탭은 `NEXT_TAB`과 `PREV_TAB`으로 바뀝니다. 바이오닉 행은 단축키를 `hotkey`에, 행의 `color`와 `Power`(작동·트리거·유지 비용), `State`(`On`, `Off`, `Passive`, `Incapacitated`), `Fuel`(`name: stored/capacity`) 열을 가지며, `REASSIGN`, `TOGGLE_EXAMINE`, `TOGGLE_SAFE_FUEL`, `TOGGLE_SPRITE`, `TOGGLE_AUTO_START`, `SORT`는 등록된 액션으로 남습니다. `MUTATIONS`(`[`)는 행을 `passive`와 `active` 창에, `action:` 행을 `actions`에 두며, 행은 `Kind`, `Key`, `State`, `Sprite`, `Innate`, `Cost`, `Cooldown` 열과 행의 `color`를 가지고 선택하면 네이티브대로 활성화 또는 비활성화됩니다.
- 오버맵(`m`, 액션 `map`)은 `context`가 `OVERMAP`인 `target` 종류의 interaction입니다. `overmap`은 네이티브 창을 그려진 그대로 담습니다. `cols`, `rows`, `cells[행][열] = [글리프, 전경, 배경]`(curses 색 인덱스 0~15: 0 검정, 1 빨강, 2 초록, 3 갈색, 4 파랑, 5 마젠타, 6 청록, 7 밝은 회색, 8~15는 각 색의 밝은 형태), 왼쪽 위 칸의 칸을 가리키는 `origin`, `player`, 사이드바 글을 담은 `legend` 줄, 화면 안의 `notes`입니다. 창은 커서 `target.current`를 중심으로 하고 `target.unit`은 `"omt"`이므로 이 interaction의 모든 위치는 맵 칸이 아니라 절대 오버맵 지형 칸입니다. `pos`가 있는 `set_target`은 커서를 옮기고(엔진 범위 안의 어떤 칸이든, 층은 -10~10), `cancel`은 화면을 닫으며, 네이티브 오버맵 동작(이동의 `CHOOSE_DESTINATION`, `CREATE_NOTE`, `LEVEL_UP`/`LEVEL_DOWN`, `ZOOM_IN`, 각종 토글 등)은 그 경계의 등록된 액션입니다. 클라이언트는 깜박일 수 없으므로 오버레이(플레이어, 메모, 경로)는 계속 표시됩니다. `path`는 계획된 이동 경로입니다. `bn.hello`에서 `"tiles": true`라고 알린 클라이언트는 `tiles`도 받습니다. 칸마다 `[tile, rotation, subtile]`(네이티브 타일 화면이 고르는 `overmap_terrain` 타일 id, 90도 회전 수, 멀티타일 키)과 각 타일 id의 `looks_like` 대체 목록입니다. 다른 클라이언트에는 보내지 않습니다. 세션 중에 타일과 ASCII를 전환하는 클라이언트는 실행 중인 명령이 없을 때 새 `tiles` 값으로 `bn.hello`를 다시 보내고(실행 중이면 `command_busy`), 이어서 현재 크기로 `bn.viewport`를 보냅니다. 그러면 엔진이 열려 있는 화면을 id를 넣거나 뺀 채 다시 발행합니다. `cursor_description`은 네이티브 사이드바가 커서 칸에 대해 말하는 번역된 문장이며, 창 테두리와 칸의 글리프는 없습니다. `cursor_here`(커서가 플레이어의 칸에 있을 때의 `You are here.`), `cursor_note`(`Note:` 뒤에 네이티브 창이 커서 칸의 메모에 대해 모서리에 표시하는 텍스트를 붙인 것. 예 `Note: cache`), `route_text`(`path`의 길이. 예 `Route of 2 squares.`)는 엔진이 만드는 번역된 줄이며, 해당하지 않으면 없습니다.
- 차량 창(`^`, `context`가 `VEH_INTERACT`)은 `vehicle` 객체를 가진 `choices` 인터랙션입니다. 커서 부품 주변 격자의 `cells`(커서 기준 화면 칸 상대값 `dx`, `dy`, `glyph`, 게임 `color` 이름), 커서 칸의 `parts`(내용물이 붙은 `name`, 층별 `open`/`close` 기호, `health`, `broken`), 네이티브 `stats` 줄(빈 줄은 빈 슬롯), 차량 좌표계의 `cursor`, `blocked`, `owner`, `owned`를 담습니다. `mode`는 `main`, 작업 목록(`install`, `repair`, `remove`, `mend`, `refill`) 또는 `select`(기름 빼기, 승무원 등)입니다. 메인 화면의 선택지는 네이티브 액션(`action:INSTALL`, `action:REPAIR` 등)이며 `enabled`와, 거부될 때 네이티브 메시지와 같은 `denial`을 가지고, 커서 이동(`action:UP` 등)도 포함합니다. 작업 목록의 선택지는 후보 부품 `part:<index>`이고 네이티브 커서에 `highlighted`가 붙습니다. 설치 목록에는 `tab:<index>` 선택지와 `vehicle.tabs`도 있습니다. `vehicle.detail`은 강조된 부품의 미리보기로, `time`, 부품 `stats`, `requirements`(`kind`는 `skill`, `component`, `tool`, `extra`이며 component와 tool 행은 대안을 OR로 잇고 `met`을 가짐), `can_do`를 담습니다. 강조된 부품에 `choose`하면 네이티브 작업이 시작되고, 다른 부품에 `choose`하면 강조만 옮겨지므로 클라이언트가 먼저 요구 사항을 보여 줄 수 있습니다. 요구 사항이 충족되지 않은 동안 강조된 행은 `enabled: false`와 `denial`을 가집니다. `cancel`은 한 단계 뒤로 돌아갑니다. `vehicle.verb`는 번역된 작업 동사(`Install`, `Repair` 등)이며 메인 화면에는 없습니다. `detail.groups`는 요구 사항 제목을 출력 순서대로 나열하고(`kind`, 번역된 `heading`, 그 종류의 요구 사항이 없을 때 출력할 `NONE` 같은 `empty_text`이며 비어 있으면 그때는 그룹을 생략), `detail.time_heading`은 `time`의 제목입니다.
- 컴퓨터 단말기(아무 키 대기에서는 `context`가 `COMPUTER_TERMINAL`, 질의에서는 `YESNOQUIT`)는 `choices` 인터랙션이며 `title`은 컴퓨터 이름, `message`는 기본 창이 출력하는 단말기 텍스트(줄 구분은 `\n`, 색상 태그 유지)입니다. 아무 키 대기의 선택지는 `continue` 하나이고 질의는 `yes`, `no`, `quit`입니다. `choose`는 해당 키와 같은 응답이며 `cancel`은 프롬프트를 끝냅니다(질의에서는 quit). 단말기의 루트 메뉴는 옵션을 나열한 일반 목록입니다. 확장 설명(`context`가 `EXTENDED_DESCRIPTION`)은 현재 대상의 설명을 `message`로, 선택지 `describe:creature`, `describe:furniture`, `describe:terrain`을 가지며 현재 대상이 `selected`입니다. `choose`로 대상을 바꾸고 `cancel`로 닫습니다.
- 소프트웨어 게임(스네이크, 지뢰 찾기, 소코반, Lights on, robotfindskitten; `context`는 `SNAKE`, `MINESWEEPER`, `SOKOBAN`, `LIGHTSON`, `IUSE_SOFTWARE_KITTEN`)은 선택지가 없는 `custom` interaction이며, `title`은 게임 이름, `canvas`는 그려진 게임 창입니다. `rows`는 창의 행마다 `[text, foreground, background]` run의 목록(색은 오버맵과 같은 curses 색 번호 0-15이고 행 끝의 빈 칸은 생략), `cols`는 너비입니다. 게임의 키는 boundary에 등록된 액션(`UP`, `FLAG`, `CONFIRM`, `QUIT` 등)이고, 액션이 없는 키는 원시 키 `text` 명령입니다. `canvas`는 `schema_id`에 포함되지 않으므로 다시 그려도 명령이 stale이 되지 않습니다. 시간으로 진행되는 게임(스네이크)은 `refresh_ms`를 가지며, 네이티브 입력 대기가 지속되는 시간입니다. 그 안에 명령이 없으면 엔진이 직접 대기를 끝내고 게임을 진행시킨 뒤 다시 그려진 `canvas`를 일반 `interaction.changed` 이벤트로 공개하므로, 클라이언트는 받은 것을 그리기만 하면 됩니다. 갱신과 겹친 명령은 `stale_boundary`로 거부될 수 있으며, 새 `boundary_id`로 다시 보내면 됩니다. robotfindskitten은 종료 애니메이션을 `refresh_ms` 1000인 프레임으로 공개하며, 그 프레임을 제외한 모든 상태는 선택지 `acknowledge`(description `ANY_INPUT`)를 가집니다. 이를 고르면 액션이 없는 키가 되고, 필드는 잘못된 명령 줄로 응답합니다.
- 구역 관리자(`context` `ZONES_MANAGER`)는 세 개의 pane을 가진 `choices` 인터랙션입니다. `zones`(구역마다 `zone:<n>` 행, 활성이면 `selected`, `Type`, `Distance`, `Direction`, `Vehicle` 열), `options`(강조된 구역의 옵션 행, 선택 불가, `Value` 열), `actions`(네이티브 `hotkey`와 `Key` 열을 가진 `action:<ID>` 행. 구역이 둘 미만일 때의 이동처럼 네이티브 키가 아무것도 하지 않으면 `enabled`가 false이고, `SHOW_ALL_ZONES`, `TOGGLE_ZONE_OVERLAY`, `debug_submap_grid`는 켜져 있는 동안 `selected`)입니다. 구역 행에 `choose`하면 네이티브 커서가 이동합니다. 구역의 영역을 고르는 단계(추가, 위치 편집, 위치 이동)는 둘러보기 `target` 인터랙션입니다. `message`는 `Select first point.`, `Select second point.`, `Moving zone.`이고 `target.status`는 `zone_first`, `zone_second`, `zone_move`(그 밖에는 `look`)이며, `target.description`은 네이티브 둘러보기 창이 커서 칸에 대해 표시하는 텍스트를 60열에서 줄바꿈한 것으로 번역된 한 줄이 한 항목이며, 커서는 등록된 방향 액션 또는 `set_target`(불러온 맵의 모든 칸)으로 움직이고 `CONFIRM`이 칸을 확정합니다. 맵 에디터(`context` `EDITMAP`)는 `status`가 `editmap`인 `target` 인터랙션입니다. `target.cursor`가 편집 중인 칸이고 `set_target`으로 불러온 맵의 어느 칸으로든 옮깁니다. `tile` pane은 그 칸에 있는 것(`tile:terrain`, `tile:furniture`, `tile:field:<id>`, `tile:trap`, `tile:creature` 또는 `tile:vehicle`, `tile:items`. 이름은 `description`, ID와 수치는 `columns`)을, `actions` pane은 `hotkey`가 붙은 편집 액션(`EDIT_TERRAIN`, `EDIT_FURNITURE`, `EDIT_TRAPS`, `EDIT_FIELDS`, `EDIT_ITEMS`, `EDIT_MONSTER`, `EDIT_OVERMAP`, 전체 맵을 보는 동안 `selected`인 `EDITMAP_SHOW_ALL`, `LEVEL_UP`, `LEVEL_DOWN`)을 나열합니다. 편집 메뉴는 일반 목록이고 `cancel`로 에디터를 닫습니다. 모양 선택(`context` `EDITMAP_SHAPE`)과 맵젠 대상 이동(`context` `EDITMAP_RETARGET`)은 `status`가 `editmap_shape_resize`, `editmap_shape_move`, `editmap_retarget`인 같은 형태의 `target` 상호작용이며, `set_target`이 커서(이동 중에는 선택 영역도)를 옮기고 `actions` 창에 기본 액션(`RESIZE`, `SWAP`, `EDITMAP_MOVE`, `START`, `EDITMAP_SHOW_ALL`, `CONFIRM`)이 나열됩니다.
- 설정 화면은 네이티브 화면입니다. `settings:options`, `settings:keybindings`, `settings:autopickup`, `settings:safemode`, `settings:distractions`, `settings:colors`로 열며, 옵션과 키 설정은 게임 안에서도 열립니다. `editor`가 있는 행은 직접 설정할 수 있습니다. `fill`의 `field_id`에 행의 `choice_id`, `value`에 편집기 형식의 값, `submit: true`를 보냅니다. `editor.type`은 `bool`(`true`/`false`), `select`(`values[].id` 중 하나), `integer`/`float`(`minimum`~`maximum`), `text`(`max_length` 이하)이며 네이티브 메뉴가 받지 않는 값은 엔진이 거부합니다. 행에 대한 `choose`는 네이티브 Enter와 같습니다. 옵션: 탭 행 `page:<id>` 뒤에 선택한 페이지의 `option:<NAME>`, `group:<id>` 행이 옵니다. `cancel`로 나가면 네이티브 "변경 사항을 저장하시겠습니까?"가 나오고, 저장하면 적용되고 기록됩니다. 키 설정: `mode:add_local`, `mode:add_global`, `mode:remove`(네이티브가 제공하면 `mode:execute`)가 다음 `action:<ID>` 행의 동작을 정하고, 필드는 이름으로 행동을 거르며, 새 키를 묻는 프롬프트에는 `key` 형식 필드가 있어 키 설정 파일과 같은 표기(`z`, `=`, `F9`, `CTRL+A`)의 키 이름을 받습니다. 자동 줍기와 안전 모드: 탭 행 `page:<n>`, 열 행 `column:<n>`, `rule:<n>` 행이며 규칙 동작(추가, 제거, 이동 등)은 화면의 등록된 행동입니다. 주의 분산: `bool` 편집기가 있는 `distraction:<name>` 행(true면 중단). 색상: `column:<n>`과 `color:<name>` 행이며 색을 고르면 네이티브 색상 목록이 열립니다.
- 월드는 아바타가 아는 것입니다. `cells`(`remembered`, `visible`, `sensed`), `entities`, `avatar`(능력치와 소지품 `inventory`), `environment`, 로드된 `coverage`, `view`, 대기 중인 `route`(계획이 없으면 비어 있거나 없음)와 그 번역된 줄 `route_text`(예 `Route of 3 squares; select its end again to go.`, 경로가 없으면 없음)로 구성됩니다. `view`는 아바타가 있는 층에서 네이티브 지형 창이 보여 주는 `{min, max}` 칸입니다(아바타를 따라 움직임). `travel` 클릭은 이 안에서만 받아들여지고, 밖이면 `validation_failed`로 거부됩니다.
- `avatar.sidebar`는 같은 getter에서 가져온 네이티브 클래식 사이드바 값과 그 패널이 출력하는 레이블입니다. 배치와 그리기는 클라이언트가 합니다. 문자열 값은 `{label, text, color}`이며, `label`은 번역된 패널 레이블(패널이 출력하지 않으면 없음), `color`는 색이 의미를 가질 때의 네이티브 색 이름입니다. 멤버는 `limbs`(`id`, `label`과 상태 색, `hp`, `hp_max`, 체력 `color`, `broken`), `pain`, `hunger`, `thirst`, `fatigue`, `temperature`, `power`, `location`, `weather`(지하에서는 레이블 없음), `focus`(`label`, `value`), `morale`(`level`, 네이티브 `face`), `stamina`(`label`, `current`, `max`, `color`), `speed`(`label`, `value`, `color`), `movement`(`counter`, `mode`는 `walk`, `run`, `crouch`, `prone`, 번역된 한 글자 `mode_text`), `safe_mode`(`label`, `enabled`, `color`), `time`(`season`, `day_label`, `day`, `clock`: 시계 시각, 없으면 대략의 시간대, 지하에서는 네이티브 시각 불명 문구), 선택적 `ambient_temperature`(온도계가 있을 때만), `weapon`, 선택적 `style`(무술 스타일)입니다. 팔다리 체력과 스태미나는 막대가 아닌 숫자이며 클라이언트가 자신의 방식으로 그립니다. 문자열은 엔진의 표시 언어이고 나머지 값은 언어 중립입니다. `stats` 항목은 네이티브 `color`를 가질 수 있고, 네 능력치는 사이드바의 `short_label`도 가집니다.
- 지형 창은 네이티브 창 크기 변경과 같은 방식으로 정해집니다. `bn.hello`의 `viewport = {cols, rows}`(맵 칸 1~512) 또는 이후의 `bn.viewport`는 터미널을 그 칸 수에 옆 패널을 더한 크기로 바꿔, 엔진이 아바타 주변의 그만큼을 보여 주게 합니다. 네이티브 최소 터미널 크기가 여전히 적용되므로 실제 `view`가 기준입니다. 아무것도 보내지 않으면 기본 터미널이 쓰입니다.
- 모든 이벤트는 일반 `changes` 블록을 가지며, `coverage`, `view`, `cells`, `forgotten`, `entities`, `gone` 순으로 적용한 뒤 `avatar`, `environment`, `route`, `interaction`을 교체합니다.
- 바이트를 줄이기 위해, 셀 레이어의 `look`은 레이어가 이미 말해 주는 `kind`를 생략하고(`terrain`, `furniture`, `trap`, `field`, `item`, `vehicle_part`; `memory.terrain`은 `terrain`이며 `memory.overlay`는 자신의 값을 유지), `subtile`이 `center`이면(모양을 가진 레이어의 기본값) 생략하며, 모든 `look`은 `rotation`이 0이면 생략합니다. 이벤트의 `interaction`은 `actions`가 이전 경계와 같으면 생략합니다. 클라이언트는 자신의 값을 유지하고, 빈 목록은 이를 교체하며, 스냅샷은 항상 목록을 담습니다.
- 이벤트의 `avatar`는 이전 avatar와 같고 비어 있지 않은 멤버를 생략하고 `keep`에 이름을 적습니다 ("look", "overlays", "traits", "stats", "inventory", "sidebar", "ground"). 클라이언트는 자신의 값을 유지하고, 그 밖에 없는 멤버는 비어 있는 것입니다. 스냅샷의 avatar는 항상 완전합니다.
- `message.logged`는 네이티브 메시지 로그입니다. `data = {id, text, kind, color, count, turn}`이며, 한 줄마다 이벤트 하나가 로그 순서대로, 원인이 된 명령에 연결되어 전송됩니다. `text`는 색 태그와 "x N"을 뺀 번역된 줄, `kind`는 네이티브 유형(`good`, `bad`, `mixed`, `warning`, `info`, `neutral`, `debug`), `color`는 그 유형의 네이티브 색 이름입니다. 마지막 줄이 반복되면 같은 `id`가 더 큰 `count`로 다시 전송되어 그 줄을 대체합니다. 상태를 바꾸지 않으며(`revision` 불변) 다른 일시 이벤트처럼 `bn.resync`를 거치면 사라집니다. 다만 로그 자체는 `bn.subscribe`가 최근 100줄을 `messages`(오래된 줄부터, `data`와 같은 형태, 비어 있으면 생략)로 돌려주므로, 로드 뒤나 resync 뒤에 구독하는 클라이언트도 네이티브 클라이언트가 보여 주는 로그에서 시작합니다. 이후 `message.logged` 이벤트를 이 목록에 적용하면(반복은 같은 `id`의 줄을 대체하고, 100줄을 넘으면 가장 오래된 줄이 빠집니다) 새로 구독했을 때 돌려받는 목록과 같아집니다. 네이티브 로그가 쿨다운으로 숨기는 메시지는 전송되지 않습니다. `label`은 네이티브 로그가 표시하는 그대로의 줄이며, `count`가 2 이상이면 `text` 뒤에 번역된 반복 접미사(`x 2`)가 붙습니다. `turn`은 그 줄이 기록되었거나 마지막으로 반복된 게임 턴이므로, 클라이언트는 턴을 구분해 보여줄 수 있습니다.
- `projectile.moved`, `explosion.started`, `explosion.blast`, `explosion.ended`, `combat_text.shown`은 네이티브 애니메이션 사실입니다. 게임이 애니메이션을 시작하는 지점에서 게시되므로 모든 클라이언트가 렌더러 없이 같은 사실을 받습니다. 상태를 바꾸지 않고, 원인 명령에 붙으며, 그 명령의 상태 이벤트보다 먼저 도착합니다. `display.duration_ms`는 네이티브 애니메이션이 그 사실을 유지하는 시간입니다(단계마다 `ANIMATION_DELAY` 옵션). `projectile.moved`는 `path`(그리는 순서의 칸. 탄이 날아가는 동안은 이벤트마다 한 칸)와 글리프와 사용자 지정 스프라이트 ID를 가진 `projectile` 종류의 `look`을 담습니다. `explosion.started`는 `at`, `radius`, `color`와 네이티브 타일이 쓰는 타일 ID `tile`을 담습니다. 그릴지는 클라이언트가 정하므로 `ANIMATIONS` 옵션은 이 사실들을 막지 않습니다(클라이언트는 게임을 바꾸지 않습니다). 전투 텍스트에만 `ANIMATION_SCT`가 필요합니다. `explosion.blast`는 지형에 따라 모양이 달라지는 폭발의 한 고리 `cells`를 나열합니다. `combat_text.shown`은 `at`에 뜨는 한두 색 `segments`의 떠오르는 글자로, 네이티브처럼 애니메이션 단계마다 `scroll`(단위 이동)만큼 움직입니다. `kind`가 `hp`이면 생물의 체력 표시이며 그 옆에 머무릅니다.
- 던진 아이템은 게임 이벤트로도 게시되며 애니메이션 옵션으로 꺼지지 않습니다. 모두 아바타가 보는 것만 게시됩니다. `item.activated`(`at`, `look`, 심지의 남은 턴 수 `turns`)는 심지에 불이 붙을 때와 타는 동안 매 턴 나옵니다. `item.thrown`(`projectile`, `look`, `by`, `from`, `to`)이 비행의 시작이고 그 `projectile.moved` 이벤트는 같은 `projectile`을 담으며, `item.landed`(`at`, `look`, 공격이 쏘아 보낸 경우 `projectile`)가 끝입니다. 던지거나 쏜 투사체는 `projectile.hit`(`at`, 아바타가 보는 생물에 맞았으면 `entity`, 장애물이면 없음)에도 같은 `projectile`을 담으며, 이는 `projectile.moved` 뒤, 그것이 일으킨 `entity.damaged`와 지형 변화 앞에 옵니다. 폭발은 `explosion.started`, 논리 시간 단계마다 `explosion.blast` 또는 `explosion.shrapnel` 고리와 그 단계가 일으킨 일, 그리고 `explosion.ended`입니다. 일으킨 일은 생물이 받은 타격마다 `entity.damaged`(`id`, `amount`, 캐릭터면 `part`), 단계가 바꾼 칸의 `terrain.changed`와 `furniture.changed`(`at`, `from`과 `to` look), 더하거나 없앤 필드마다 `field.changed`(`at`, `field`, 이후의 `intensity`. 사라지면 0)입니다. `entity.damaged`는 생물이 받는 모든 피해(직접 가해진 것 포함)에서 나옵니다. 지형, 가구, 필드 변화는 폭발만이 아니라 게임이 일으킬 때마다 게시됩니다. 아바타에게 보이는 칸을 바꾸는 모든 호출(문을 부수기, 가구 놓기, 필드 더하기·없애기)은 공유 맵 경계에서, 필드 턴(불 번짐, 가스 확산, 필드 소멸. 건너뛴 턴 포함)은 아바타 층에서 보이는 필드를 전후로 비교해 달라진 칸마다 `field.changed` 하나로 게시됩니다. 긴 대기 뒤에도 그 칸은 한 번만 알려집니다.
- `sound.heard`(`text`, `volume`, `marker`, `logged`)는 네이티브 청각 규칙(주변 소음 대비 음량, 청각 보호, 수면, 난청)을 거쳐 아바타에게 닿은 소리입니다. `text`는 네이티브 메시지가 부르는 설명, `volume`은 아바타에게 들리는 데시벨, `marker`는 네이티브 게임이 소리를 표시하는 칸입니다. 마커는 음원이 아니라 그 근처에서 아바타 시야 밖인 칸이며, 아바타가 음원에 있거나 음원이 보이면 생략되므로 숨은 음원이 드러나지 않습니다. 소리의 로그 줄은 네이티브 메시지 규칙과 쿨다운을 따르지만, `sound.heard`는 발소리처럼 로그가 생략하는 소리를 포함해 들린 모든 소리에 대해 게시됩니다. `logged`는 그 소리가 메시지 로그에도 줄을 가질 때 `true`이며, 둘을 모두 표시하는 클라이언트는 같은 소리를 한 번만 보여 줄 수 있습니다. 아바타 자신의 외침은 그 행동이 직접 줄(`You yell ...`)을 기록하므로 logged로 취급합니다.
- `sound.played`, `sound.channel`, `music.changed`는 엔진이 직접 소리를 내든 아니든 네이티브 사운드 플레이어가 받는 재생 요청입니다. 클라이언트는 hello가 `engine.sound.soundpack`으로 알려 주는 폴더의 사운드팩에서(`SOUND_ENABLED` 옵션이 꺼져 있으면 생략) 네이티브 플레이어와 같은 방식으로 재생합니다. `sound.played`(`id`, `variant`, `volume`, `angle`, `stacks`)는 사운드팩의 `sound_effect` 하나입니다. 그 변형이 없는 팩은 효과의 `default` 변형을 재생하고, 효과의 `files` 중 하나를 무작위로 고르며, `stacks`가 `false`이면 같은 소리가 아직 재생 중일 때 건너뜁니다. `sound.channel`(`channel`, `id`, `variant`, `volume`, `gain`, `angle`, `loops`, `fade_ms`)은 예약 채널(환경음, 날씨, 위험 테마, 엔진, 라디오)이 지금 재생하는 것입니다. 새 소리는 `fade_ms` 동안 페이드인하며 시작하고, 같은 `id`와 `variant`는 새 `gain`(음량 변경으로, 옵션이나 팩 음량을 곱하지 않은 믹서 단위)이나 `angle`로 계속 재생하며, `id`가 없는 채널은 `fade_ms` 동안 페이드아웃합니다. 채널 `any`는 모든 채널과 효과음을 페이드아웃합니다. 첫 스트림은 이미 재생 중인 채널과 음악으로 시작합니다. 새 `epoch`의 스트림은 이전 스트림이 알린 것에서 이어집니다. 멈출 때까지 반복하지 않는 소리(`loops` 0 이상)를 아직 재생 중인 채널은 새 시작을 무시합니다. `music.changed`(`playlist`, `volume`)는 재생할 팩의 플레이리스트를 알려 주며, 플레이리스트가 정한 대로 순서대로 또는 섞어서 재생합니다. `playlist`가 없으면 음악이 멈춥니다. `volume`은 네이티브 `SOUND_EFFECT_VOLUME`, `AMBIENT_SOUND_VOLUME`, `MUSIC_VOLUME` 옵션을 적용한 믹서 단위(128이 최대 게인)이며, 효과나 플레이리스트 항목에 팩이 정한 `volume`(0-100)이 여기에 곱해집니다. `angle`은 네이티브 믹서가 소리를 놓는 방향으로, 정면에서 시계 방향 각도(90은 오른쪽)입니다. 사운드 없이 빌드한 엔진(`SOUND=OFF`)은 이 중 아무것도 게시하지 않습니다.
- `entity.moved`(`id`, `to`, `from`, `mode`)와 `entity.gone`(`id`, `reason`)으로 클라이언트는 스냅샷이 공개하는 몬스터와 NPC를 재동기화 없이 행동 내내 따라갈 수 있습니다. `entity.moved`는 아바타에게 보이는 생물의 이동마다 도착한 칸에서 게시됩니다. 출발한 칸을 아바타가 보지 못했으면 `from`은 생략되고, `mode`는 이웃한 칸으로의 한 걸음이면 `walk`, 그보다 긴 이동(밀침, 순간이동)이면 `propelled`입니다. 아바타 자신의 이동은 상태 변경분에 있습니다. `entity.gone`은 클라이언트가 알던 생물이 더는 공개되지 않음을 알리며, `reason`은 `lost_sight`(시야에서 걸어 나감, 또는 아바타나 시점이 움직임), `died`, `removed`(게임에서 사라짐)입니다. 시야 밖으로 걸어 나간 생물은 즉시 `gone`이 되고 나머지는 경계를 게시할 때 찾아냅니다. 붐비는 턴에는 `entity.moved`, `terrain.changed`, `furniture.changed`, `field.changed`의 처음 256개만 게시됩니다(시야 밖으로 걸어 나간 생물의 `gone`도 셉니다). 경계의 `cells.seen` 변경 집합은 항상 최종 상태를 담으므로 이벤트는 순서와 시점을 더할 뿐 상태를 대체하지 않습니다.

이벤트는 `interaction.changed`, `coverage.moved`, `turn.passed`, `cells.seen`, `message.logged`와 위의 애니메이션 사실이며, 이후 스키마에 나열된 나머지 연출 유형이 추가됩니다. 0.2 공개 전에 추가한 이벤트 유형은 0.2에 포함되며, 공개 후에는 새 이벤트 유형에 새로운 정확한 버전이 필요합니다.
