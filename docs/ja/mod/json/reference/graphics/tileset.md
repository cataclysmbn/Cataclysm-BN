# タイルセット

タイルセットは、ゲームにグラフィック画像を提供します。各タイルセットは、画像スプライトが収められた1つ以上の「タイルシート」と、スプライトシートの内容をゲーム内の様々なエンティティ(実体)にどのように紐付けるかを記述した `tile_config.json` ファイルで構成されます。また、メタデータを提供する `tileset.txt` ファイルも含まれます。

## コンポジット・タイルセット

2019年10月以前、タイルセットは各タイルシートが完全に結合された状態でリポジトリに提出され、`tile_config.json` 内のスプライトのインデックス番号は手計算で割り振る必要がありました。その後、個別のスプライト画像ファイルと、それらのファイル名を使用した `tile_entry` JSON ファイルを含むディレクトリとして提出できるようになりました。TypeScript 版タイルセットツールは、個別の画像をタイルシートに統合し、ファイル名をスプライトのインデックス番号に変換した上で、各エントリを1つの `tile_config.json` に集約します。

本ドキュメントでは、統合済みのタイルシートで構成されるタイルセットを「レガシー・タイルセット」、個別のスプライト画像で構成されるものを「コンポジット・タイルセット」と呼びます。

<a id="typescript-tileset-tool"></a>

### TypeScript タイルセットツール

通常の合成・分解作業には `scripts/tileset.ts` を使用します。このツールは [PR #8151](https://github.com/cataclysmbn/Cataclysm-BN/pull/8151) で古い Python 版 compose ワークフローを置き換えるために追加されました。

```sh
# 個別のスプライトファイルと tile_entry を tile_config.json とタイルシート PNG に合成します。
deno run -A scripts/tileset.ts --pack gfx/Retrodays

# 合成結果を別のディレクトリへ書き込みます。
deno run -A scripts/tileset.ts --pack gfx/Retrodays /tmp/Retrodays-composed

# レガシー・タイルセットを個別のスプライトファイルと tile_entry に分解します。
deno run -A scripts/tileset.ts --unpack gfx/ChestHole16Tileset
```

よく使うオプション:

- `--format-json`: 生成される `tile_config.json` を整形します。
- `--only-json`: タイルシート PNG を書き込まず、`tile_config.json` だけを再生成します。
- `--use-all`: 参照されていない PNG もファイル名を元にした ID で含めます。
- `--palette` と `--palette-copies`: 8-bit パレット出力を生成します。

古い `tools/gfx_tools/compose.py` と `tools/gfx_tools/decompose.py` は、日常的なタイルセット作業向けとしては非推奨です。互換性と parity test のためにリポジトリには残っています。

合成時も元のスプライト画像ファイルや `tile_entry` JSON ファイルは上書きされず、そのまま保持されます。

小規模な例やブラウザ上での簡単な確認には、[Tileset Web Tool](/dev/reference/tileset_web_tool/) を使用できます。

### ディレクトリ構造

各コンポジット・タイルセットには、`pngs_tree_32x40` や `pngs_overlay` のように、名前が `pngs_`で始まるディレクトリが1つ以上含まれています。これらは画像ディレクトリです。画像ディレクトリ内のスプライトはすべて幅と高さが一致している必要があり、実行時に1つのタイルシートへと統合されます。

タイルセットの開発者は、画像ディレクトリ名にスプライトの寸法を含めることが推奨されていますが、これは必須ではありません。例えば `pngs_overlay` よりも `pngs_overlay_24x24` という命名が好ましいですが、どちらも許容されます。画像ディレクトリごとに個別のタイルシートが作成されますが、パフォーマンスの観点からはタイルシートをなるべく大きく(数を少なく)した方がよいため、画像ディレクトリの数は最小限に抑えることが強く推奨されます。

各画像ディレクトリ内には、サブディレクトリ、`tile_entry` JSONファイル、およびスプライト画像ファイルを階層的に配置できます。これらのファイルの配置や命名に制限はありませんが、拡張タイルシート用の `tile_entry` JSONファイルだけは、必ず画像ディレクトリの直下に配置してください。サブディレクトリの使用は必須ではありませんが、管理を容易にするために活用することをお勧めします。

#### `tile_entry` JSON

各 `tile_entry` JSONは、1つ以上のゲーム内エンティティ(実体)を1つ以上のスプライトにどのように紐付けるかを記述した「辞書」形式のデータです。最もシンプルな構成では、単一のゲームエンティティに対して、単一の前景スプライト、任意の背景スプライト、および回転の有無を指定します。

例えば、以下のように記述します。

```cpp
{                                           // これはオブジェクトであり、リスト化する必要はありません
    "id": "mon_cat",                        // このスプライトが表すゲーム内のID
    "fg": "mon_cat_black",                  // 前景スプライト名(ファイル名)
    "bg": "shadow_bg_1",                    // 背景スプライト名。常に単一の値です
    "rotates": false                        // 車両パーツのように回転する場合は true に設定します
}
```

`"id"`、`"fg"`、および `"bg"` に指定する値は、同一の画像ディレクトリ内、あるいは異なる画像ディレクトリ間で繰り返し使用することができます。`"fg"` や `"bg"` のスプライト画像は、別の画像ディレクトリから参照することも可能ですが、そのスプライト自体は、同じ幅と高さを持つスプライトが収められた画像ディレクトリ内に保存されていなければなりません。

`"id"` には、`"id": ["vp_door", "vp_hddoor"]` のように、同じスプライトを共有する複数のゲームエンティティのリストも指定できます。`"id"` には、ゲーム内の車両パーツ、地形、家具、アイテム、モンスターを指定できます。特殊ID `"player_female"`、`"player_male"`、`"npc_female"`、`"npc_male"` はプレイヤーアバターとNPCのスプライトを識別します。特殊ID `"unknown"` は、ほかにスプライトがないエンティティを表示するためのスプライトを提供します。

任意のIDに対して、特殊な接尾辞である `_season_spring`(春)、`_season_summer`(夏)、`_season_autumn`(秋)、`_season_winter`(冬)を付け加えることで、その季節に応じた外見のバリエーションを作成できます。この設定をすると、指定した季節においてその画像が優先的に表示されます。
例: `"id": "mon_wolf_season_winter"` (冬の装いになったオオカミ)

特殊な接頭辞である `overlay_mutation_`、`overlay_female_mutation_`、`overlay_male_mutation_` を、ゲーム内の任意の特性やCBMのIDの前に付けることができます。これにより、プレイヤーやNPCのスプライトの上に重ねて表示される「オーバーレイ画像」を指定し、それらの変異や義体を有していることを視覚的に表現できます。

特殊な接頭辞である `overlay_worn_`、`overlay_female_worn_`、`overlay_male_worn_` を、ゲーム内の任意のアイテムIDの前に付けることができます。これにより、プレイヤーやNPCのスプライトの上に重ねて表示されるオーバーレイ画像を指定し、そのアイテムを「着用」している状態を表現できます。

特殊な接頭辞である `overlay_wielded_`、`overlay_female_wielded_`、`overlay_male_wielded_` を、ゲーム内の任意のアイテムIDの前に付けることができます。これにより、プレイヤーやNPCのスプライトの上に重ねて表示されるオーバーレイ画像を指定し、そのアイテムを「手に持っている(構えている)」状態を表現できます。

`"fg"`(前景)と `"bg"`(背景)には、あらかじめ回転させた2方向または4方向のバリエーションをリスト形式で指定することもできます。
例えば、`"bg": ["t_wall_n", "t_wall_e", "t_wall_s", "t_wall_w"]`(北・東・南・西の壁)や、`"fg": ["mon_dog_left", "mon_dog_right"]`(左向き・右向きの犬)といった指定が可能です。

`"fg"`(前景)と `"bg"`(背景)には、「重み付け(weight)」が設定された辞書のリストを指定することも可能です。これにより、複数の候補の中からランダムに画像を表示させることができます。また、それぞれの候補自体を、先ほど説明した「回転バリエーション用のリスト」にすることも可能です:

```cpp
"fg": [
    { "weight": 50, "sprite": "t_dirt_brown"},       // 53個中50個のタイルで表示される(高確率)
    { "weight": 1, "sprite": "t_dirt_black_specks"}, // 53個中1個のタイルで表示される
    { "weight": 1, "sprite": "t_dirt_specks_gray"},
    { "weight": 1, "sprite": "t_patchy_grass"}       // ファイル名は自由に命名可能です
],
```

`"multitile"` は任意のフィールドです。この値が存在し、かつ `true` に設定されている場合、必ず `"additional_tiles"` というリストを記述する必要があります。このリストには、壁の接続部分やアイテムの破損したバージョンなど、そのタイルに関連付けられたエンティティやスプライトを定義する辞書を1つ以上含めます。リスト内の各辞書には、前述のルールと同様に `"id"` フィールドと `"fg"` フィールドを持たせます。この `"fg"` フィールドには、単一のファイル名、ファイル名のリスト、または先ほどのような重み付け設定の辞書リストを指定できます。

各 `tile_entry.json` ファイルには、単一のオブジェクト、または次のように1つ以上のオブジェクトのリストを記述できます:

```cpp
[
    { "id": "mon_zombie", "fg": "mon_zombie", "bg": "mon_zombie_bg", "rotates": false },
    { "id": "corpse_mon_zombie", "fg": "mon_zombie_corpse", "bg": "mon_zombie_bg", "rotates": false },
    { "id": "overlay_wielding_corse_mon_zombie", "fg": "wielded_mon_zombie_corpse", "bg": [], "rotates": false }
]
```

ファイル内のタイルエントリをリストにすると整理に役立つ場合がありますが、互いにまったく関係のないエントリを同じファイルに記述しても問題はありません。

#### 拡張タイルシート( `tile_entry` JSON)

タイルシートには、MODなどによって提供される「拡張タイルシート」を含めることができます。各拡張タイルシートの定義は、単一の `"id"` 値を持ち、`"rotates": false`、かつ `"fg": 0` と指定されます。 拡張用の `tile_entry` JSONは、`"fg"` に整数値(数値の 0)を使用する唯一の例外であり、その値は必ず 0 でなければなりません。また、これら拡張用の `tile_entry` JSONファイルは、各画像ディレクトリ直下に配置する必要があります。

#### スプライト画像

一つの画像ディレクトリ内に含まれるすべてのスプライトは、そのディレクトリ内の他のすべてのスプライトと、高さおよび幅が同一でなければなりません。

画像ディレクトリ内のスプライトは、タイルセット制作者の好みに合わせて、自由にサブディレクトリに整理して配置することができます。スプライトのファイル名に制約は一切なく、制作者にとって分かりやすい命名規則を自由に採用してください。

タイルセットの読み込み後、config/debug.log には、そのタイルセット内でスプライトが不足しているすべてのエンティティが、スペース区切りのリストとして出力されます。なお、`"looks_like"` の定義によってスプライトが割り当てられているエンティティは、このリストには表示されません。

### `tile_info.json`

各コンポジット・タイルセットには、必ず `tile_info.json` が含まれていなければなりません。その構成は以下の通りです:

```
[
  {
    "width": 32,
    "pixelscale": 1,
    "height": 32
  },
  {
    "1_tiles_32x32_0-5199.png": {}
  },
  {
    "2_expan_32x32_5200-5391.png": {}
  },
  {
    "3_tree_64x80_5392-5471.png": {
      "sprite_offset_x": -16,
      "sprite_offset_y": -48,
      "sprite_height": 80,
      "sprite_width": 64
    }
  },
  {
    "4_fallback_5472-9567.png": { "fallback": true }
  }
]
```

最初の辞書の記述は必須であり、タイルセット内のすべてのタイルシートにおけるデフォルトのスプライトの幅と高さを指定します。各画像ディレクトリに対しては、タイルシートのPNG名をキーとした個別の辞書を用意する必要があります。もしそのタイルシートがデフォルトのスプライトサイズを使用しており、特殊なオフセット(表示位置のズレ)も設定しない場合は、タイルシート名をキーとした値の中身は空の辞書( {} )で構いません。そうでない場合は、スプライトのオフセット、高さ、および幅を含む辞書を記述してください。

`"fallback"` は特殊なキーであり、指定する場合は値を `true` に設定します。あるタイルシートがフォールバックとして指定されると、それはASCII文字を補完するためのタイルシートとして扱われます。`scripts/tileset.ts` は、このフォールバック用タイルシートをタイルセットの最後に合成します。また、もし `tile_info.json` 内に `"fallback"` エントリが存在しない場合、スクリプトは自動的に `tile_config.json` へ `"fallback.png"` を追加します。

`"filler"` は特殊なキーであり、指定する場合は値を `true` に設定します。あるタイルシートがフィラーとして指定されると、そのディレクトリ内のエントリは、非フィラー(通常)のディレクトリで既に同じIDが定義されている場合には無視されます。また、同じフィラーディレクトリ内で既にIDが定義されている場合も同様に無視されます。さらに、フィラーディレクトリ内のPNGファイルが、非フィラーディレクトリ内のPNGファイルと同じ名前を持っている場合も無視されます。
フィラータイルシートは、タイルセットのアートワークをアップグレードする際に便利です。古くて低品質な画像をフィラーシートに置いておけば、より高品質な画像が非フィラーシートに追加されるたびに、古い画像は自動的に置き換えられます。

## レガシー・タイルセット

### タイルシート

各タイルシートには、幅と高さが統一されたスプライトが1つ以上含まれます。また、各タイルシートは、1行につき正確に16個のスプライトが並んだ構造を1行以上持っている必要があります。スプライトのインデックス 0 は特殊な扱いであり、タイルセット内の最初のタイルシートにある最初のスプライトは「空白」にする必要があります。インデックス番号は、各シートを通じて連続しており、新しいシートに移ってもリセットされずに増え続けます。そのため、インデックス 32 は最初のシートの「3行目・1番目」のスプライトを指します。仮に最初のシートに 320 個のスプライトが含まれている場合、インデックス 352 は「2枚目のシートの3行目・1番目」のスプライトを指すことになります。

### `tile_config`

各レガシー・タイルセットには、スプライトシートの内容を各種タイルIDや異なる向きなどにどのように対応させるかを記述した `tile_config.json` が存在します。また、変異を表示する際に使用されるオーバーレイの表示順序を制御することも可能です。この順序指定を利用して、`mutation_ordering.json` で提供されているデフォルトの順序を上書きすることができます。例:

```json
{ // ファイル全体が一つのオブジェクトです
  "tile_info": [ // tile_info は必須項目です
    {
      "height": 32,
      "width": 32,
      "iso": true, //  オプション。アイソメトリック形式であることを示します。既定値は false。
      "pixelscale": 2 //  オプション。タイルセットをリサイズするための倍率を設定します。既定値は 1。
    }
  ],
  "tiles-new": [ // tiles-new はタイルシートの配列です
    { //   または、単一の "tiles" 配列でも可能です
      "file": "tiles.png", // グリッド状にスプライトが並んだ画像ファイル名
      "tiles": [ // タイルごとの定義を格納する配列
        {
          "id": "10mm", // ID:ゲーム内の要素とスプライトを紐付けます
          "fg": 1, //   接頭辞がない場合は主にアイテムを示します
          "bg": 632, // fg(前景)と bg(背景)は画像内のスプライト番号です
          "rotates": false
        },
        {
          "id": "t_wall", // "t_" は地形(terrain)を意味します
          "fg": [2918, 2919, 2918, 2919], // 数値が2つまたは4つの場合は、回転済みのスプライト指定です
          "bg": 633,
          "rotates": true,
          "multitile": true,
          "additional_tiles": [ // 接続・合成されたバージョンのスプライト
            { //   またはバリエーション。詳細は後述。
              "id": "center",
              "fg": [2919, 2918, 2919, 2918]
            },
            {
              "id": "corner",
              "fg": [2924, 2922, 2922, 2923]
            },
            {
              "id": "end_piece",
              "fg": [2918, 2919, 2918, 2919]
            },
            {
              "id": "t_connection",
              "fg": [2919, 2918, 2919, 2918]
            },
            {
              "id": "unconnected",
              "fg": 2235
            }
          ]
        },
        {
          "id": "vp_atomic_lamp", // "vp_" 車両パーツ
          "fg": 3019,
          "bg": 632,
          "rotates": false,
          "multitile": true,
          "additional_tiles": [
            {
              "id": "broken", // バリアントスプライト
              "fg": 3021
            }
          ]
        },
        {
          "id": "t_dirt",
          "rotates": false,
          "fg": [
            { "weight": 50, "sprite": 640 }, // 重み付きランダム・バリエーション
            { "weight": 1, "sprite": 3620 },
            { "weight": 1, "sprite": 3621 },
            { "weight": 1, "sprite": 3622 }
          ]
        },
        {
          "id": [
            "overlay_mutation_GOURMAND", // 変異用オーバーレイ
            "overlay_mutation_male_GOURMAND", // 特定の性別用
            "overlay_mutation_active_GOURMAND" // 発動中の変異用
          ],
          "fg": 4040
        }
      ]
    },
    { // tiles-new 内の2番目のエントリ
      "file": "moretiles.png", // 別のスプライトシート
      "tiles": [
        {
          "id": ["xxx", "yyy"], // 2つのIDを一度に定義
          "fg": 1,
          "bg": 234
        }
      ]
    }
  ],
  "overlay_ordering": [
    {
      "id": "WINGS_BAT", //変異名。文字列、または文字列の配列で指定。
      "order": 1000 // 範囲は 0 - 9999。9999が最前面(一番上)に描画される。
    },
    {
      "id": ["PLANTSKIN", "BARK"], // 変異の名前。単一の文字列、または文字列の配列のいずれかで記述します。
      "order": 3500 // (指定された)順序(order)は、配列内のすべての項目に適用されます。
    },
    {
      "id": "bio_armor_torso", // 義体(CBM)の表示順序も同様に制御される。
      "order": 500
    }
  ]
}
```

## 投射物のスプライト

特定の命名規則を使うことで、投射物（弾丸と投擲アイテム）にカスタムスプライトを定義できます。

> [!NOTE]
> 正しい向きで表示するには、スプライトを上向き（0度）にしてください。

### 弾丸（銃から発射）

`animation_bullet_{ammo_type}` を使用します。`{ammo_type}` は弾薬のアイテムIDです。

```json
{ "id": "animation_bullet_9mm", "fg": 123, "rotates": true }
{ "id": "animation_bullet_556", "fg": 124, "rotates": true }
{ "id": "animation_bullet_762", "fg": 125, "rotates": true }
```

システムは弾薬の `looks_like` チェーンをたどります。`animation_bullet_556` が存在せず、弾薬 `556` に `looks_like: "223"` が指定されている場合、`animation_bullet_223` があれば自動的に使用します。

### 投擲アイテム

`animation_bullet_{item_type}` を使用します。`{item_type}` は投擲アイテムのIDです。

```json
{ "id": "animation_bullet_javelin", "fg": 126, "rotates": true }
{ "id": "animation_bullet_throwing_axe", "fg": 127, "rotates": true }
{ "id": "animation_bullet_throwing_knife", "fg": 128, "rotates": true }
```

投擲アイテムについても、アイテムの `looks_like` チェーンをたどります。

### フォールバック動作

カスタム投射物スプライトが見つからない場合は、次のようにフォールバックします。

1. **投擲アイテム**: そのアイテム自体のスプライト（例: `javelin`）
2. **弾丸**: `animation_bullet_normal_0deg`

### 回転

- ジャベリンや槍のように `FLY_STRAIGHT` フラグを持つアイテムは、飛行中も向きを維持します。
- 斧やナイフなど、それ以外の投擲アイテムは飛行中に回転します。
- タイル定義で `"rotates": true` を設定すると、方向別スプライトが有効になります。

## 状態モディファイア

状態モディファイアは、状態ごとの別のアートを用意せずに、ゲーム状態（しゃがみ、ノックダウンなど）に応じてキャラクターのスプライトを動的に調整します。モディファイア画像でピクセルの移動を制御する UV マッピングを使用します。

### UV マッピングの仕組み

UV モディファイア画像の各ピクセルは赤（X）と緑（Y）チャンネルで変位を表します。描画時には `(x, y)` のピクセルを直接描く代わりに、同じ位置のモディファイアを読んで元のスプライトからサンプルする位置を決めます。これにより、スプライトの一部を縮めたり伸ばしたり移動したりできます。

### オフセットモードと正規化モード

**オフセットモード**（`"use_offset": true`、デフォルト）では、赤/緑の値が中立値 `(127, 127)` からの変位を表します。127 は移動なし、0 は -127 ピクセル、255 は +128 ピクセルです。変更しない場所には灰色 `(127,127)` を塗ります。複数のモディファイアの変位は加算されます。

**正規化モード**（`"use_offset": false`）では、赤/緑の値がタイルサイズで正規化された絶対 UV 座標です。`(0,0)` は左下、`(255,255)` は右上をサンプルします。複雑な再マッピングには正確ですが直感的ではありません。UVを回転すると結果も回転するため、素早く変更しやすい方式です。モディファイアは互いに再サンプリングして連鎖し、計算コストがわずかに高くなります。

### JSON 構造

タイル設定の `"state-modifiers"` 配列に状態モディファイアを定義します。

```json
"state-modifiers": [
  {
    "id": "movement_mode",
    "override": false,
    "use_offset": true,
    "tiles": [
      { "id": "walk", "fg": null },
      { "id": "crouch", "fg": 100 },
      { "id": "run", "fg": 101 }
    ]
  },
  {
    "id": "downed",
    "override": true,
    "use_offset": true,
    "tiles": [
      { "id": "normal", "fg": null },
      { "id": "downed", "fg": 102 }
    ]
  }
]
```

### フィールド

| フィールド   | 型     | 説明                                                                     |
| ------------ | ------ | ------------------------------------------------------------------------ |
| `id`         | string | モディファイアグループ ID。対応するグループと一致する必要があります。    |
| `override`   | bool   | `true` で状態が有効なとき、優先度の低いグループをスキップします。        |
| `use_offset` | bool   | オフセットモードは `true`、正規化モードは `false`。デフォルトは `true`。 |
| `tiles`      | array  | グループの状態とスプライトの対応。                                       |
| `whitelist`  | array  | 任意。指定した接頭辞に一致するオーバーレイだけに適用。                   |
| `blacklist`  | array  | 任意。指定した接頭辞に一致するオーバーレイには適用しない。               |

`tiles` の各項目には、グループ内の状態 ID `id`、UV モディファイアのスプライトインデックス `fg`（`null` は変更なし）、任意の `offset`（`{"x": n, "y": n}`）があります。

### 対応するモディファイアグループ

| グループ ID     | 状態                                       | 説明                                      |
| --------------- | ------------------------------------------ | ----------------------------------------- |
| `movement_mode` | `walk`, `run`, `crouch`                    | キャラクターの移動姿勢                    |
| `downed`        | `normal`, `downed`                         | ノックダウン状態かどうか                  |
| `lying_down`    | `normal`, `lying`                          | 横たわっているかどうか                    |
| `activity`      | `none`, activity ID                        | 現在の活動（例: `ACT_CRAFT`、`ACT_READ`） |
| `body_size`     | `tiny`, `small`, `medium`, `large`, `huge` | 変異で変化した体の大きさ                  |

### 優先度と上書き

モディファイアグループは配列順（インデックス0が最高優先度）で処理されます。`"override": true` のグループで `fg` が null でない有効なモディファイアがある場合、優先度の低いグループはすべてスキップされます。たとえば、ノックダウン状態で移動に基づく変更を完全に置き換えられます。

### オーバーレイのフィルタ

グループごとの `whitelist` と `blacklist` で適用するオーバーレイを制御します。オーバーレイは接頭辞で一致し、`wielded_` は `wielded_katana` に一致します。グループでいずれかのフィルタを指定すると、グローバルフィルタを上書きします。よく使う接頭辞は `wielded_`、`worn_`、`mutation_`、`effect_`、`bionic_` です。

```json
{
  "id": "movement_mode",
  "blacklist": ["wielded_"],
  "tiles": [...]
}
```

同じIDに異なるフィルタを持つ複数のグループを置くことで、オーバーレイの種類ごとに異なるUVモディファイアを使えます。その場合、**フィルタは相互排他的でなければならず**、各オーバーレイがIDごとに最大1グループだけに一致する必要があります。フィルタが重なると重複描画が発生します。

```json
{
  "id": "movement_mode",
  "blacklist": ["wielded_"],
  "tiles": [...]
},
{
  "id": "movement_mode",
  "whitelist": ["wielded_"],
  "tiles": [...]
}
```

**基本スプライトの動作:** 基本キャラクタースプライト（肌、目、髪など）はオーバーレイではなく、接頭辞もありません。そのため接頭辞に一致できず、`whitelist` を持つグループは基本スプライトに適用されません。`blacklist` だけを持つグループ（またはフィルタのないグループ）は基本スプライトに通常どおり適用されます。基本スプライトと特定のオーバーレイに異なるモディファイアを適用するには、基本スプライト用のblacklistグループとオーバーレイ用のwhitelistグループを使用してください。

### UV モディファイアスプライトの作成

3. 緑チャンネルで縦移動を指定します（127未満は上、127超は下）。

### スプライトサイズ

タイルセットを定義するとき、`sprite_width` と `sprite_height` に加えて `sprite_offset_x` と `sprite_offset_y` を指定します。UVでは、これらが影響する範囲を定義し、範囲外のピクセルは変わりません。すべて同じ解像度なら特筆する必要はありませんが、オーバーレイには異なるオフセットやサイズも指定できます。この機能はピクセルのスケールが一貫していることを前提としますが、それ以外はサイズの異なるスプライトにも対応します。

武器やステータス表示のようにアバターの外側へ伸びるオーバーレイを扱うため、状態モディファイアは64x64、オフセット `(-16,-16)` で作成することを推奨します。理論上は状態モディファイアのメモリ使用量を減らすこともできます。たとえば表情を新しいモディファイアグループとして実装する場合、非常に小さなUVで顔の領域だけに限定できます。その場合、丸め誤差を避けるためオフセットモードを使うとよいでしょう。

### スプライト境界

元のスプライト境界の外へ移動したピクセルも扱えますが、描画上の制限があります。タイルは上から下へ行単位で描画されるため、歪んだスプライトが下の行へ伸びると、その部分は次の行の地形で上書きされます。上、左、右へ伸びるスプライトは正しく描画されます。これはタイルの描画順序に由来する根本的な制限です。

### パフォーマンス

状態モディファイアは描画時に処理され、一意な状態の組み合わせごとにキャッシュされます。性能が問題になる場合は、グラフィック設定の `State Modifiers` トグルで無効にできます。

## 色付け

タイルセットは色付けと色付けペアに対応します。

### 色付けペア

色付けペアは、1つの種類で別のタイルの色付けを制御します。たとえば `hair_color` で `hair_style` を制御できます。

```json
"tint_pairs": [
  { "source_type": "hair_color", "target_type": "hair_style", "override": true },
  { "source_type": "hair_color", "target_type": "facial_hair", "override": true }
],
"tints": [
  { "id": "hair_blond", "fg": "#91631f", "contrast": 1.1, "blend_mode": "multiply" },
  { "id": "hair_white", "fg": "#ffffff", "blend_mode": "multiply" }
],
"tiles-new": [
```

`override` のデフォルトは false で、レガシーなタイル指定を迂回させます。これはメインタイルセットからエントリを削除できない `mod_tileset` で特に役立ちます。`source_type` はオーバーレイの種類に応じて `target_type` を制御します。現在は突然変異だけに作用するため、入力に `mutation_type` を使えます。また、`target_type` をタグに一致させることもでき、髪の色に応じて毛皮を色付けするといった処理が可能です。

### 色付け

色付けを使うと、単純な色の違いごとに別スプライトを作らずにタイルの色を変更できます。色付けエントリの `id` には、タイルまたは色付けペアのソースを指定できます。例:

```json
"tint_pairs": [
"tints": [
  { "id": "eye_pink", "fg": "#ff00bb", "saturation": 1.5 },
  { "id": "eye_black", "fg": "c_black", "blend_mode": "multiply" },
  { "id": "eye_white", "fg": { "color": "#ffffff", "saturation": 0.0, "brightness": 1.2 } }
],
"tiles-new": [
```

色付けは柔軟で、前景と背景を別々に指定できます。色入力、または色とモディファイアを含むエントリのどちらかを選ぶ必要があり、両方の形式を併用できません。また、前景と背景の両方に適用するモディファイアとエントリ形式も併用できません。モディファイアは `saturation`、`brightness`、`contrast` です。これらも主に `mod_tileset` で役立ちますが、用途はそれに限りません。`blend_mode` には次を指定できます。

- `tint`（デフォルト）
- `overlay`
- `softlight`
- `hardlight`
- `multiply`
- `additive`
- `subtract`
- `normal`
- `screen`
- `divide`

参考資料:
https://en.wikipedia.org/wiki/Blend_modes

特に `tint` はこの機能専用のモードです。黒や白でも結果のタイル色を完全に変えながら適度なコントラストを保つため、塗装したような効果に向いています。`normal` は、色付け側のアルファを使うと効果の周囲に不自然な四角い縁が生じるため、その時点のタイルのアルファを使用します。

色には16進数コードまたは curses 色名を使います。IDから curses 色を取得するフォールバックがありますが、依存しないでください。色付けは現在、突然変異、アイテム、バイオニック、効果に適用できます。IDまたはタグで色付けできますが、効果フラグには対応していません。
