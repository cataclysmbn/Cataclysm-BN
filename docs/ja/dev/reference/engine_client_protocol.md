外部クライアントは `cataclysm-bn-tiles --client=mcp` の stdio 上で、改行区切りの JSON-RPC 2.0 によりゲームをプレイします。値は [Draft 2020-12 スキーマ](../../../schema/engine-client/0.2.schema.json)で定義され、以下の例はすべて[例ファイル](../../../schema/engine-client/0.2.examples/)でスキーマに照らして検証されています。従来の MCP ツール(`bn.observe`、`bn.press` など)は別の面であり変更されません。クライアントが `bn.hello` を呼ぶと、これらのツールは入力を拒否します。

## セッション

```text
-> {"jsonrpc":"2.0","id":1,"method":"bn.hello","params":{"versions":["0.2"],"client":{"name":"my-client","version":"1"},"schema":"sha256:0123456789abcdef"}}
<- {"jsonrpc":"2.0","id":1,"result":{"version":"0.2","epoch":"epoch:e7f3","engine":{"build":"...","mods":["bn"],"display":{"tiles":true,"tileset":"UNDEAD_PEOPLE_BASE"}},"limits":{"frame_bytes":1048576,"cells_per_part":512,"cells_per_query":4096,"screen_queue":8},"schema":"sha256:0123456789abcdef","locale":"en","engine_locale":"en","role":"controller"}}
-> {"jsonrpc":"2.0","id":2,"method":"bn.subscribe","params":{}}
<- {"jsonrpc":"2.0","id":2,"result":{"at":{"epoch":"epoch:e7f3","sequence":"40","revision":"31"},"interaction":{...},"entities":[],"parts":1}}
<- {"jsonrpc":"2.0","method":"bn.snapshot.part","params":{"epoch":"epoch:e7f3","at":{...},"index":0,"last":true,"cells":[...]}}
-> {"jsonrpc":"2.0","id":3,"method":"bn.command.submit","params":{"epoch":"epoch:e7f3","expect":{"revision":"31","boundary_id":"boundary:90","schema_id":null},"operation":{"kind":"action","action_id":"RIGHT"}}}
<- {"jsonrpc":"2.0","id":3,"result":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"received"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"validated"}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"executing"}}
<- {"jsonrpc":"2.0","method":"bn.events","params":{"epoch":"epoch:e7f3","events":[{"sequence":"41","revision":"32","type":"interaction.changed","command":"c:5","changes":{...}}]}}
<- {"jsonrpc":"2.0","method":"bn.command","params":{"epoch":"epoch:e7f3","command_id":"c:5","stage":"completed","at":{"epoch":"epoch:e7f3","sequence":"41","revision":"32"}}}
```

`parts` 個のスナップショットパートを集めてから、`bn.events` を順に適用します。欠落(gap)、epoch の不一致、`bn.resync` があれば `bn.subscribe` を再度呼びます。新しいスナップショットは状態のみを復元し、`lost_after` 以降の一時的なイベントは失われたものとして扱われ、再送されません。 エンジンはイベント履歴を保持しません。`bn.unsubscribe` の後や遅れた後に戻る方法は `bn.subscribe` だけで、そのスナップショット(再送ではない)が最後に見た `(epoch, sequence)` に取って代わります。`bn.resync` が止めるのはイベントだけで、スナップショットに含まれない `bn.command` のステージは届き続けます。ステージはその `at` より新しいスナップショットの後に届くこともあります。ステージがプッシュされるのは `bn.subscribe` から `bn.unsubscribe` または `bn.hello` までで、その間以外のコマンドの結果は `bn.command.result` で読みます。古い `epoch` を指定したリクエストはすべて `stale_epoch` と `action: "subscribe"` で失敗します。

| `bn.viewport`            | `cols`, `rows`                                             | なし                                                                                             |
| `bn.interrupt`           | なし                                                       | なし                                                                                             |
| `bn.hold`                | `epoch`, `screen_id`, `affordance_id`                      | なし                                                                                             |
| `bn.release`             | なし                                                       | なし                                                                                             |
| `bn.subscribe`           | なし                                                       | スナップショットヘッダー。続いてパートとイベントが届く                                           |
| `bn.unsubscribe`         | なし                                                       | なし                                                                                             |
| `bn.interaction.choices` | `epoch`, `boundary_id`, `offset`, `limit`                  | `boundary_id`, `total`, `choices` (読み取り専用)                                                 |
| `bn.world.describe`      | `epoch`, `boundary_id`, `pos`                              | `lines`(読み取り専用)                                                                            |
| `bn.world.cells`         | `epoch`, `min`, `max`                                      | `at`, `cells`, `forgotten` (読み取り専用)                                                        |
| `bn.overmap.cells`       | `epoch`, `min`, `max`                                      | `overmap` オーバーマップ 1 階層のマス、カーソルとは無関係 (読み取り専用)                         |

| `bn.credit`              | `frames`                                                   | 付与後の保有 `credits`                                                                           |

エンジンからの通知は `bn.snapshot.part`、`bn.events`、`bn.command`、`bn.resync`、`bn.loading`、`bn.progress` です。`bn.loading` と `bn.progress` 以外は、購読中のクライアントへ入力境界ごとに送られます。`bn.progress`(`{epoch}`)はハートビートで、待機などの行動が入力境界に到達せずに続いている間、`bn.hello` を済ませたクライアントへ 2 秒ごとに送られます。通信が途絶えたなら、エンジンは動いていません。ワールドの読み込み中は `bn.loading` が同じ役割を果たします。

エラーはコード `1000` と `error.data = {kind, action?, at?}` を使い、`action` が次の対応(`hello`、`subscribe`、`retry`)を示します。

## hello とスタック

エンジンはすべてのトランスポートで `"0.2"` だけを提供する。`"0.2"` を列挙しない hello は `negotiation_failed`、`action: "hello"` で失敗する。hello は次を含める必要がある。

- `schema`: `sha256:` と、[`0.2.schema.json`](../../../schema/engine-client/0.2.schema.json) の生バイトの SHA-256 の先頭 16 桁の 16 進数。ハッシュが異なると `negotiation_failed`、`action: "hello"`、`error.data.schema = {engine, client}` で失敗する。エンジンは CMake の構成時にスキーマファイルからハッシュを得る。
- 任意の `locale` と `capabilities`（`tiles`、`tint_ids`、`viewport`、`delivery`。個別メンバーとして送っても受け付けるが両方の形式は併用できない）。結果には `schema`、`locale`（接続のテキストの言語）、`engine_locale`、`role` が加わる。エンジンが接続ごとにローカライズするまで、`locale` はエンジンの言語である。

すべてのインタラクション境界（スナップショットのヘッダーとイベント）は `interaction` と並んで `stack` を持つ。スタックは開いている画面を外側から並べたもので、最後の画面だけが affordance を持つ。`component_id` 付きの `bn.interaction.choices` は最上位画面のその一覧（`rows`、`total`）を読む。

`bn.command.submit` は `operation: {kind: "invoke", affordance_id, args?}` を受け取る。`expect` は affordance の `expect` の範囲に従う。

- `screen`: `{screen_id}`。その画面が最上位の間だけ有効で、そうでなければ `stale_screen` で拒否される。エンジンはコマンドの実行中、この種の送信を最大 8 件(hello 結果の `limits.screen_queue`)待たせ、順番が来たときに個別に検証する。キーを押し続けても動き続け、閉じたポップアップ宛てのキーは拒否される。
- `boundary`: `{boundary_id, revision}`。従来どおり。コマンドの実行中は `command_busy` で失敗する。

affordance に合わない形式は `invalid_arguments` である。

## 押し続けるキー

マップの一歩には `holdable` が付きます。クライアントはキーが下がったときに `bn.hold` を一度、上がったときに `bn.release` を送り、キーリピートには invoke を送りません。hold が有効でマップが最前面の画面で入力待ちの間、エンジンは入力プロンプトごとにネイティブキーをもう一度押したかのようにその操作を一歩ずつゲームへ渡し、一歩の前にクライアントが送済みのリクエストを先に読みます。タップは先に離されても一歩を保証します。ポップアップなど他の画面が上に来る、一歩でアバターのマスもターンも変わらない、新しい `bn.hello`、切断のいずれかで hold は終わります。`bn.hold` は活動中は `not_ready`、最前面でない画面は `stale_screen`、存在しない・hold できない affordance は `unknown_affordance`/`invalid_arguments` で失敗します。画面スコープの invoke はこれまでどおりキューに積まれます(リストで矢印キーを押し続ける場合)。

## 配信クレジット

`bn.hello` の `delivery = {credits, max_hz?}`(`credits` は 1〜256、任意の `max_hz` は 1〜240)で有効にします。結果には `delivery = {credits, held_frames, held_bytes, max_hz?}` が付き、`max_hz` を要求した場合はそのまま返されます。`delivery` を送らない場合、以下は適用されず、プッシュされるフレームは従来どおり入力境界と自動移動のステップで即座に書き込まれます。

- プッシュされる `bn.events` と `bn.command` のフレームは 1 クレジットを消費します。残りがなければエンジンはフレームを順序どおり保持し、`bn.credit {frames}` で追加されたときに書き込みます(結果は付与後の保有クレジットで上限 256。保持されたフレームはレスポンスの後に続きます)。スナップショットの部分、`bn.resync`、`bn.loading`、`bn.progress` はクレジットを消費しません。
- エンジンが 1 つのクライアントのために保持するのは最大 `held_frames` フレーム・`held_bytes` バイトです。どちらかを超えると保持中の `bn.events` を破棄し、理由 `backpressure` の `bn.resync`(`lost_after` は書き込んだ最新の sequence)を送り、クライアントが `bn.subscribe` を呼ぶまでイベントのプッシュを止めます。そのスナップショットが破棄分を置き換えます。保持中の `bn.command` フレームは残り、クレジットが支払われ次第 `bn.resync` の後に届きます。`bn.subscribe` も保持中のイベントだけを破棄するため、コマンドの終わりが失われることはありません。保持の上限を超えるほどステージを未払いのまま残したクライアントだけが、その最も古いものを失います。
- クレジットを持つクライアントは、実行中の行動(待機、製作など)の間もコマンドの完了より前にフレームを受け取ります。ワールドのキャプチャは 1 ターンよりはるかに高価なため、エンジンは毎ターンではなく、発行に要する時間が行動の時間の 5 分の 1 になる間隔でのみ発行し、`max_hz` があれば実時間で 1/`max_hz` 秒に 1 回までという制限も加え、より疎な方に従います。フレームは直前のフレーム以降の変更を担い、状態の変更はまとめられ、すべてのメッセージと演出の事実は順序どおりに含まれ、行動が終わる境界が残りを担います。`bn.command` の `completed` は引き続き入力境界で送られます。ストリームはクライアントを待ちません。クレジットを付与しなくなったクライアントがエンジンに強いるのは保持上限までで、ゲーム、その RNG、セーブは、すべてを読むクライアントや存在しないクライアントの場合と同一です。
- クレジットがアクティビティを待たせることはありません。stdout はコントローラーとしてソケットと同じく扱われる(`ソケットと観戦者` を参照)ため、クレジット済みのフレームは待たずに書き込まれるバッファに入り、stdout が満杯でもエンジンは stdin を読み続けます。アクティビティの配信より遅く読むクライアントはクレジットが尽き、上記のとおり再同期されます。16 MiB を超えて読まないクライアントはソケットと同じく切断されます。stdio には次のコントローラーがないため、エンジンはプレイ中のゲームを保存して終了します。Windows の stdio はこの扱いではありません。書き込みはパイプが受け取って初めて戻るため、クレジットを渡した分を読まないクライアントをアクティビティは待ちます。

## フレームと失敗

- フレームは 1 行の JSON 値 1 つで、どちらの向きも `limits.frame_bytes` を超えません。フレームは単一の書き込み主体が丸ごと書くため混ざらず、エンジンは一度に 1 フレームだけを読み、それ以上は溜めません。
- JSON でない行には `-32700`、形の誤った JSON には `-32600`、未知の `bn.` メソッドには `-32601`、不正な params には `-32602` で答えます。読み取れる `id` がなければ `id` は `null` で、通知には答えません。このようなフレームはゲームも保留中のフレームも変えず、アクティビティの実行中でも接続は維持されます。
- 最大長を超えるフレームや stdin の終了で途切れたフレームには答えられません。エンジンはそれ以上読まず、理由を stderr に書いて終了コード 1 で終了します(ソケットではその接続だけが終わります)。
- アクティビティの実行中、リクエストには答えますが何も開始しません。`bn.command.submit` は次の入力境界まで `not_ready` で失敗し、`bn.interrupt` はアクティビティが受け付ける唯一の制御で、`bn.viewport`、`bn.subscribe`、`bn.credit` は配信される内容だけを変えます。コマンドはアクティビティが終わる境界まで開いたままです。`bn.hello` を再送すると配信を再交渉し、保留中のフレームを捨てて購読を解除するため、ストリームは次の `bn.subscribe` からやり直します。
- 終了時(stdin の終了、ゲームの終了)、エンジンはクレジットで支払える保留フレームを順に書き込み、残りを捨てます。未完了コマンドの `interrupted` 段階もこれに含まれます。`SIGTERM` と `SIGINT` は stderr にシグナル名を書いてからエンジンを即座に終了させます。読むのをやめて自分側を閉じたクライアントは、失敗した書き込みを通じてエンジンを終了させます。

## ソケットと観戦者

`--client=mcp --listen <path>` は、stdio の代わりに同じプロトコルをローカルのストリームソケット(Unix ドメインソケット。Windows 10 以降では `AF_UNIX`)で提供します。オプションがなければ何も変わりません。エンジンはユーザーだけが読めるファイルを作り、応答のない古いファイルは置き換え、使用中のパスは拒否します。フレームは同じ行で、制限も同じです。同時に処理する接続は最大 8 で、それ以上は直ちに閉じます。ワールドの読み込み中にも接続でき、`bn.loading` を受け取ります。

- **役割。** 最初の接続と、コントローラーがいないときに張られた接続がコントローラーで、ゲームに命令できるのはコントローラーだけです。他の接続は観戦者で、それぞれ独自の `bn.hello`、クレジット、保持フレーム(256 フレーム、1 MiB)、購読を持ちます。観戦者はコントローラーが読めるすべて(コントローラーのコマンドの段階とイベントを含む)を読めますが、`bn.command.submit`、`bn.interrupt`、`bn.viewport`、レガシーの `bn.press` と `bn.interact` は `read_only` で失敗し、観戦者の `bn.hello` はコントローラーのビューポートとタイル設定に触れません。接続中に役割は変わらず、操作したい観戦者はコントローラーが去った後に接続し直します。
- **ブロックしない。** 出力は接続ごとのバッファに待たずに書き込まれ、16 MiB を超えて送れなくなった接続は、それ以前にクレジットがストリームを止めていなければ閉じられます。ゲームは stdio と同じくコントローラーの入力だけを待ち、その間に観戦者を処理するため、読むのが遅い、あるいは全く読まない観戦者がゲームやコントローラーを遅らせることはありません。クレジットのためにアクティビティがソケットを待つこともありません。
- **切断。** 接続を閉じるとその接続のために保持していたものはすべて解放され、再接続のために残すものはありません。戻ったクライアントは `bn.hello` と `bn.subscribe` を送り、そのスナップショットから続けます。これは `bn.resync` の後と同じです。JSON でないフレームには上記のとおり答えて接続は維持され、制限を超えたフレームや切断で途切れたフレームはその接続だけを終わらせます(stdio ではエンジンが終了します)。
- **コントローラーが去るとき。** 開いていたコマンドは `interrupted` になります。実行中のアクティビティは最後まで続き、その後ゲームはキーを押していないプレイヤーのように入力境界で接続を待ち、次の接続がコントローラーになります。観戦者は接続されたまま、ゲームの現在位置を知らされます。ソケットが閉じてもエンジンは終了せず、ゲーム自身の終了か `SIGTERM`、`SIGINT` で終了します。

## 単一の時計

- `epoch` はプロセス開始時とワールド入れ替え時に変わり、読み取りでは変わりません。
- `sequence` は公開されたイベントの数です(10進文字列、連続、`"1"` から開始)。`revision` は状態を変えるイベントの数です。`at = {epoch, sequence, revision}` は「sequence までのすべてのイベントを含む」ことを意味します。
- コマンドは `expect = {revision, boundary_id, schema_id}` を持ちます。古い値は拒否されるため、クライアントは見ていない画面に対して操作しません。`schema_id` は、その境界にインタラクションがないときに限り `null` です。

## コマンド

`operation.kind` は `choose`、`fill`、`set_count`、`set_target`、`cancel`(意味ベースのメニュー)、`action`(移動キーなど登録済みの行動)、`travel`(マップのクリック)、または `tile_action`(マップのマスに対する行動、後述)のいずれかです。

```json
{ "kind": "choose", "choice_id": "tab:new_game" }
{ "kind": "set_target", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
{ "kind": "action", "action_id": "RIGHT" }
{ "kind": "travel", "pos": { "dim": "", "x": 9, "y": 4, "z": 0 } }
```

すべての境界アクションは、アクティブな入力コンテキストがそのアクションに割り当てた単一キーボードキーの可搬名(`ESC`、`SPACE`、`RETURN`、`UP`、`>` など)を `keys` に列挙します。`action` はアクションを id で実行し、キーのないアクション(割り当てのない `open_options` など)も実行できます。押されたキーで動作するクライアントは、キー設定ファイルから推測せず、`keys` にそのキーを含むアクションを探してください。

`travel` は、インタラクションのない境界で、画面内の絶対マップマスに対する Tiles と curses の左クリックです。最初のクリックはエンジン自身のルートを `route` として公開し、同じマスをもう一度クリックするとネイティブの自動移動が始まります。その後アバターは 1 歩ずつ歩き、各歩でそのコマンドに紐づく通常のイベントが公開され、エンジンが止まる場所(到着、モンスターの視界入りなど)で止まります。歩行が終わって再び入力を待つとコマンドは `completed` になります。他のコマンドや別のマスのクリックは計画を置き換えるか消します。クライアントがルートを自分で計算することはありません。

クリックや雑用がマスとアイテムに何をするかも、エンジンが決めます。アバターの隣にある、開けられる閉じたドアへの左 `travel` は、ルートのクリックではなくそのドアへの移動(ネイティブの移動がドアを開ける)になります。`pickup` と `drop` は `{ "kind": "pickup" | "drop", "item_id", "count" }` を取ります。`item_id` は `avatar.ground`(pickup)または `avatar.inventory`(drop)の行の `id`、`count` はその行から取る量をネイティブの単位(釘のようなチャージ式アイテムはチャージ数、それ以外はアイテムの個数)で表し、エンジンはメニューで印を付けて確定したときと同じネイティブの拾う・落とす行動を開始します。行 ID はそのスタックが同じである間は変わらず、行がなくなったか `count` に足りない場合、コマンドは `validation_failed` で拒否されます。失敗したコマンドは、ローカライズされた理由を `error_text`(コマンド結果と `bn.command`)または `message`(JSON-RPC エラーの `data`)で伝えます。エンジンが知っている場合は `error` より具体的です(マップウィンドウ外への移動、スタックを超える個数など)。ターゲットのインタラクション(`context` が `TARGET`)は `target.distance`(`distance_metric` による `source` から `current` までの距離。垂直方向を含む)を持ち、画面が射程と準備状態を報告する場合は `target.status_text`(ローカライズされた射程と状態の行)も持ちます。どのキーでも進み、キーが割り当てられていない画面(キー待ちのポップアップ、コンピューター端末のプロンプト)は、選ぶべき選択肢を `interaction.any_key_choice_id` で示します。

`context` は同じマスへの右クリック(SEC_SELECT)です。ネイティブでは隣のマスを調べる、隣のドアを閉じる、足元のアイテムを拾う、見えているモンスターを撃つ、あるいは計画中のルートをまず取り消します。`bn.world.describe` はターミナルウィンドウ内のマスにホバーしたときにネイティブのマウスビューが表示するテキストを返します(範囲外は `validation_failed`)。何も選択も計画もしません。`bn.world.cells` は 1 つの階層の範囲(`min` と `max` を含み、`dim` と `z` が同じで最大 `limits.cells_per_query` マス)でアバターが知っている内容を返します。セルはスナップショットが持つものと同一で、`forgotten` は範囲内のロード済み領域(coverage)で何も分かっていないマスです。反転した範囲や複数階層にまたがる範囲は `validation_failed`、大きすぎる範囲は `resource_limit`、別の `epoch` は `stale_epoch` です。メニューでのホイール 1 ステップは登録済みアクション `SCROLL_UP` または `SCROLL_DOWN` で、エンジンがネイティブのカーソルを 3 行動かします。

`tile_action` は、`bn.world.describe` がマスに対して列挙する `actions` の一つを `action_id` と `pos` で指定し、そのマスでネイティブのアクションが行うことを行います。一覧には今できることだけが、メニューの順に、ネイティブの `label` とプレイヤーの `keys`(`attack`、`talk`、`travel` にはなし)とともに入ります。`attack`(アバターの隣にいる、味方でない見えている生き物)、`fire`(見えているモンスター、遠距離武器を装備中)、`talk`(見えているキャラクター)、`open`・`close`・`pickup`・`examine`(アバターのマスとその周囲8マスで、ネイティブのアクションが行えるもの)、`travel`(アバターが知っているマス。ルートの計画と歩行開始を1つのコマンドで行う)、`look`(常に。そのマスでルック表示を開く)です。そのマスが今列挙していないアクションは `validation_failed` です。クライアントはこの一覧をマスの右クリックメニューとして表示します。

マップ画面は `shortcuts`、つまりショートカットバーのボタンも持ちます。これはデータ(ゲームの JSON の `client_shortcut`: `id`、`action`、`icon`、`glyph`、`order`。MOD は新しい id でボタンを追加し、同じ id で置き換えます)で、各ボタンはマップの入力コンテキストの登録済みアクションを指します。エンジンはそのコンテキストの `label` と `keys`、データの `icon`(不透明なスプライト id)と `glyph`(専用の絵がないときに描くもの)、マップが最前面でそのアクションを受け付ける間 `enabled` を付けて公開します。コンテキストが名前を持たないアクションのボタンは含まれません。クリックは `affordance_id` が指すアフォーダンスの `invoke` です。画面のアフォーダンスは `confirm`・`cancel` のほか、`role` として `navigate`(カーソル・ページ・タブ・スクロール。クライアントはキー、ホイール、クリックで既に扱えます)と `help`(キー割り当てメニュー)を持つことがあります。

ステージは `received`、`validated`、`executing`、`completed`、または `rejected`、または `interrupted` で、`interrupted` の `error` が理由を示します(ワールドが入れ替わると `stale_epoch`、ゲームが入力を拒否すると `validation_failed`、それ以外は `not_ready`)。`completed` は入力が再び待たれていることを意味します。待機などの行動は、終わるか、ゲームが何かを尋ねる(ポップアップや中断)まで先に実行されます。その `at` はその境界の終点です。そのため、入力が開くプロンプト(テキスト欄、数量)は、それを運ぶイベントが先に届くので(`bn.resync` の後は、続くスナップショットが運びます) `completed` の到着時には状態に含まれています。そのときプロンプトが無ければ、プロンプトは開かれなかったということです。同時に実行できるコマンドは 1 つです(`command_busy`)。 待機などの行動の実行中もリクエストには応答します。`bn.interrupt` はネイティブの中断キーを押し、行動は Tiles と同様に中止するか尋ね、その質問が次の境界になります。行動中でなければ `not_ready` で失敗します。

## 読み込み画面

ワールドの読み込み中はゲームスレッドが処理中で入力境界に到達しないため、`bn.hello` を済ませたクライアントには、ネイティブの読み込み画面の各ステップで `bn.loading` が送られます(購読の有無は問いません)。進行状況はネイティブクライアントが表示する画面と同じです。`title` は現在のコンテキスト(例: "Loading files")、`entries` はその一覧、`index` は処理中の項目(それ以前は完了)、`image` はネイティブクライアントと同じ方法で選ばれた読み込み画像です。`image.path` はゲームのベースパスからの相対パスで、ファイル名に作者が含まれない場合 `author` は省略されます。読み込み画面が終わると `done` が一度だけ送られ、その後に通常どおり `bn.resync` や `bn.events` が続きます。`epoch` はそのステップを送った時点の epoch です。

```text
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","title":"Loading files","entries":["Terrain","Items"],"index":1,"image":{"path":"data/json/loading/Ada_dawn.webp","author":"Ada"}}}
<- {"jsonrpc":"2.0","method":"bn.loading","params":{"epoch":"epoch:e7f3","done":true}}
```

## 値

- `pos = {dim, x, y, z}` は絶対マップマスで、`dim` はゲームのディメンション、プライマリは `""` です。リアリティバブル座標はワイヤ上に現れません。
- `look = {kind, id, glyph, color}` はゲームデータ由来の見た目を持つため、テキストクライアントにタイルセットは不要です。自動壁の地形はアバターが知っている接続に応じた線文字を持ち、記憶されたマスは `memory.terrain` の上に `memory.overlay`（家具、罠、乗り物部品）を保持します。
- `look` は `name`、つまりネイティブの look が表示する翻訳済みのプレイヤー向けの名前（`t_floor` は "wooden floor"）を持つため、テキストや音声のクライアントは ID を読む必要がありません。クリーチャーにはエンティティの `name` を使います。
- タイルクライアントは同じ `look` をゲームのタイルセットで描画します。エンジンだけが知り得る情報（データとネイティブの選択ロジックを持つのはエンジンのため）を公開し、クライアントは再実装しません。`tile`（`id` と異なるスプライト ID。`corpse_<monster>`、`player_male`、`vp_<part>`）、`looks_like`（データのフォールバック連鎖、近い順）、`subtile` と `rotation`（アバターが知っている隣接マスからネイティブの選択が計算したマルチタイルキーと 90 度回転数。接続ロジックは一箇所のみ）、`stack`（山の表示アイテム）、`attitude` と `aware`（モンスターと NPC。ネイティブ表示は重ねて印を付ける）、`tint`（乗り物部品の塗装。タイルセットがスプライトに混ぜる）、`reviving`（蘇る死体があるマス）、`facing`（生物）、マスの `light`（ネイティブの `lit_level`：0 暗い、1 低い、2 明るいのみ、3 照明あり、4 明るい）、`environment.season`、アバターの `look`、キャラクターの `overlays`（装備・手持ちアイテム・ミューテーション・バイオニクスを、ネイティブの順に試すスプライト ID を `tile` と `looks_like` に並べた種別 `overlay` の `look` として）です。ファイル、重み付きバリアント、レイヤー、暗転はタイルセットが定めるものでクライアントが担当します。描画順は地形、家具、罠、フィールド、アイテム、乗り物部品、生物で、`fields` と `items` の最後の要素がネイティブ表示で描かれるものです。`light` は視界内のマスだけを対象とします。ゲームの暗い・明るいのみ（0 と 2）はアバターから見えないマスなので、クライアントは通常表示のないマスすべてに hidden 照明スプライトを敷き、`lowlight_dark` や `lowlight_light` の情報は送りません。記憶されたマスは暗く、`light` が 1 のマスは陰影付きで描かれ、スプライトのない ID は `glyph` にフォールバックします。
- 変異のオーバーレイは `mutation`（変異の `id`、`types`、`flags`）を、アバターやエンティティは `traits`（変異の種類ごとの変異 ID）を持ちます。タイルセットの `tints` と `tint_pairs` がこれをキーにして髪、肌、目に色を付けます。環境は `mod_tilesets` として、タイルセットにスプライトを追加するゲームデータのファイルをネイティブの読み込み順に、`base` フォルダ、ファイル内の `index`、`compatibility` に挙げたタイルセットとともに並べます。 セルは、その上の車両の貨物パーツに物が入っているとき `cargo` を持ち、ネイティブ画面はそのパーツを強調します。 装備または手に持つアイテム、バイオニクス、効果のオーバーレイは `tint_keys` を持ちます。タイルセットの `tints` がキーにする ID で、ネイティブ画面が試す順（フラグ、次に ID）です。 hello は `tint_ids` でタイルセットが持つティントの ID を挙げられます。すると地形、家具、モンスター、車両パーツ、アイテムの look はその中に当てはまる `tint_keys`（フラグ、次に ID）を持ち、ティント変数を持つアイテム、地形、家具は `tint_vars`（タイルセットのティントに重ねる色、ブレンド、補正）を持ちます。フィールドの look はネイティブ画面が塗るフィールド種別のティントを `tint` に持ちます。フィールドの種別がその下のアイテムを隠すとき(煙、火、蜘蛛の巣)、フィールドの項目は `hides_items` を持ちます。それが表示中のフィールドである間、ネイティブのタイル画面はアイテムもその強調も描きません。
- アバターの階で見えていて、ネイティブのタイル画面が透かして見るマス(空中、および樹冠、ガラスの屋根、下りスロープなど床のない地形)は `below` を持ちます。`below` はネイティブのタイル画面がそこに描くマスが何階下かを示します。床のある最初のマス、または何かを覚えている最初のマスが、見えている、覚えている、または車両であればそのマス、そうでなければ下りる途中で見えた何かのある最も低いマスです。そのマスはそれ自体として公開されます。透かして見るマスはその上にあるもの(フィールドなど)を保ち、何もない空中はそれ以外を持たず、透かして見えるものがない何もない空中は公開しません。透かして見るのは見えているマスだけです。
- `interaction` はネイティブのメニューやダイアログです。`columns` の各項目は、安定した翻訳されない名前 `key`(英語の見出しを小文字にして単語を `_` でつないだもの。例 `spell_level`、所持品のセルは `cell0`、`cell1`、…)と翻訳された見出し `label` を持ち、クライアントは `key` だけで列を探します。列は値のネイティブ色名 `color` を持つことがあります。選択肢は `favorite`(お気に入りの呪文)、`color`、`key_color`(行テキストと `hotkey` の色名)、`markup`(ネイティブの色タグ付きの名前)、ネイティブのリストが選択記号を表示する所では `mark`(`glyph` は `+`、`#`、`-`、と `color`)、入れ子の斜線を描く所では `parent_id` と `nest_color` も持ちます。`choices` は最大 200 行ですがサイズにより少なくなることがあるため、残りは `bn.interaction.choices` を `offset = choices.length` から読みます。全体の行数は `choice_total` です。`compat.focus` と `compat.panes` は 1:1 移植のためにネイティブのリスト状態を保持します。クライアントは無視して構いません。高度なインベントリ管理のペインには `sort`(ネイティブの並べ替え名)と `totals`(ネイティブのペインヘッダー: `weight`、`volume`、容量のある区画では `weight_max`/`volume_max`、および `weight_unit`、`volume_unit`、`over_weight`、`over_volume`。ネイティブが表示しない最大値は空)も含まれます。メインメニューはネイティブと同じタブ構成です。各タブは `pane_id` を持たない選択肢(`tab:new_game`、`tab:load` など。選択中のタブは `selected`)で、その後に選択中のタブの項目だけが、そのタブの `pane_id` 付きで続きます(`new_game:tutorial`、`settings:options`、`load:<world>`)。別のタブを選ぶと、そのタブの項目を持つ新しい interaction が公開されます。ID は位置にも言語にも依存しません。クラフトメニュー(`context` が `CRAFTING`)も同じタブ構成です。カテゴリタブ(`tab:CC_ELECTRONIC`)、選択中カテゴリのサブタブ(`subtab:CSC_ELECTRONIC_TOOLS`、検索中は無し)、レシピ(`recipe:<hash>`)の順で、後の 2 つはカテゴリを `pane_id` に持ちます。タブまたはサブタブを選ぶとそのグループが一覧され、レシピを選ぶとクラフトし、レシピへの `set_count` は一括クラフトに入ります。各レシピはネイティブの詳細テキスト(スキル、時間、道具、材料)を色タグなしで `description` に持ちます。建設メニュー(`context` が `CONSTRUCTION`、キー `*`)も同じ構成です。カテゴリタブ(`tab:<category id>`、検索中は `tab:FILTER` のみ)に続いて、建設グループごとに `color`、`key_color`、`markup` と、複数選択の選択画面では `mark` が型付きの項目で、`category_mode` はカテゴリ選択中にオンです。拾得の行はネイティブのリストが表示するキーを `hotkey` に持ち、1文字の枠を超えるとバッククォートと2文字になり、それも超えると持ちません。拾得の行の `markup` はネイティブのリストが表示する行そのもの(スタック数、`ITEM_SYMBOLS` の記号、自分のものでないアイテムの前の `<color_light_red>!</color>`)で、`label` はそのままです。拾得ペインの `area_id` は `PICKUP_POSITION` オプション(`left`、`right`、`overlapping`、`cursor`)で、`totals` の `over_weight`/`over_volume` はネイティブのヘッダーが赤で表示する場合に立ちます。 高度な持ち物管理(advanced inventory)の interaction は `areas` も運びます。ネイティブのヘッダーと同じ配置のエリア選択で、各エリアに、有効なペインをそのエリアに向ける `action_id`、翻訳済みの `label`(ペインは `label` が自身の `area_label` と等しいエリアにいる)、`key`(プレイヤーがそのアクションに割り当てたキー、未割り当てなら空。割り当てを変えるとクライアントの表示も変わる)、`x` と `y`(選択部の左上からの文字セル数)、`available`(そのエリアが今存在する: 車両を掴んでいる、またはそのマスに車両がある、その階層が存在する)があります。操作ボタンの名前は登録済みアクションの `name` です。choice は、その行が実行する登録済みアクションを示す `action_id` を持つことがあります。ゲーム内メインメニューの行が持つので、Options 行は言語を問わず `open_options` です。拾う一覧の `message` は色タグ付きのネイティブヘッダーで(容量を超える予測重量・体積は `<color_c_red>` で囲まれる)、フィルターが 2 行目に続きます。
- ワールドはアバターが知っているものです。`cells`(`remembered`、`visible`、`sensed`)、`entities`、`avatar`(能力値、所持品 `inventory`、足元の `ground`)、`environment`、読み込み済みの `coverage`、`view`、保留中の `route`(計画がなければ空または省略)で構成されます。`view` はアバターのいる階層でネイティブの地形ウィンドウが映すマス `{min, max}` です(アバターに追従します)。`travel` クリックはこの内側だけ受理され、外側は `validation_failed` で拒否されます。
- `avatar.inventory` は手に持つアイテム、装備中のアイテム、持ち運ぶスタックの順に並び、各要素は `{look, name, count?, slot, durability?}` で、`slot` は `wielded`、`worn`、`carried` のいずれかです。`avatar.ground` はアバター自身のマスにあるスタックを `slot` なしの同じ形で並べます。`count` は行が持つ量をネイティブの単位(チャージ式アイテムはチャージ数、それ以外はアイテムの個数)で表し、その行の `pickup` や `drop` が取れる最大量です。`name` はネイティブの一覧と同じ表示名で、色マークアップを含みません。`name` がネイティブの状態マーカーで始まるとき、`durability` がそのマーカーを `{symbol, color}` で示し、クライアントはその色で描けます。どちらの配列も空のときは省略されます。 各行には `label` もあり、ネイティブのリストの言い回しそのままの行です。スタックの表示名に個数と状態マーカーを色マークアップで付け、続けて装備状態 (`(wielded)`、`(worn)`) をプレイヤーの言語で付けます。
- キャラクター画面はテキストではなくネイティブの値と色を公開します。`PLAYER_INFO`(`@`)は 6 つのタブ(`stats`、`encumbrance`、`skills`、`traits`、`bionics`、`effects`)を `pane_id` のない choice として、続けて各タブの行をそのタブの `pane_id` で並べます。列の `color` は値のネイティブ色名で、特性とバイオニクスの行では行の `color` が名前の色です。能力値の行の値は `current` 列です。速度の内訳は `pane_id` が `speed` の行で、選択不可、`color` 付きの `value` 列を持ちます。このバージョンのシートに習熟タブはありません。`BIONICS`(`p`)は `active` と `passive` のタブを `panes`(`role` は `current` か `inactive`)に示し、現在のタブの行だけを並べます。タブの切り替えは `NEXT_TAB` と `PREV_TAB` です。バイオニクスの行はショートカットを `hotkey` に、行の `color` と、`Power`(起動・トリガー・維持コスト)、`State`(`On`、`Off`、`Passive`、`Incapacitated`)、`Fuel`(`name: stored/capacity`)の列を持ち、`REASSIGN`、`TOGGLE_EXAMINE`、`TOGGLE_SAFE_FUEL`、`TOGGLE_SPRITE`、`TOGGLE_AUTO_START`、`SORT` は登録アクションのままです。`MUTATIONS`(`[`)は行を `passive` と `active` のペインに、`action:` 行を `actions` に置きます。行は `Kind`、`Key`、`State`、`Sprite`、`Innate`、`Cost`、`Cooldown` の列と行の `color` を持ち、選ぶとネイティブどおり有効化または無効化されます。
- オーバーマップ(`m`、アクション `map`)は `context` が `OVERMAP` の `target` 種別の interaction です。`overmap` はネイティブのウィンドウを描かれたまま運びます。`cols`、`rows`、`cells[行][列] = [グリフ, 前景, 背景]`(curses の色インデックス 0〜15: 0 黒、1 赤、2 緑、3 茶、4 青、5 マゼンタ、6 シアン、7 明るい灰、8〜15 は各色の明るい形)、左上のセルのマスを示す `origin`、`player`、サイドバーの文字列 `legend`、表示範囲内の `notes` です。ウィンドウはカーソル `target.current` を中心にし、`target.unit` は `"omt"` で、この interaction のすべての位置はマップのマスではなく絶対オーバーマップ地形マスです。`pos` 付きの `set_target` でカーソルが動き(エンジンの範囲内の任意のマス、階層は -10〜10)、`cancel` で画面を閉じ、ネイティブのオーバーマップ操作(移動の `CHOOSE_DESTINATION`、`CREATE_NOTE`、`LEVEL_UP`/`LEVEL_DOWN`、`ZOOM_IN`、各種切り替えなど)はその境界の登録アクションです。クライアントは点滅させられないため、オーバーレイ(プレイヤー、メモ、経路)は常時表示されます。`path` は計画された移動経路です。`bn.hello` で `"tiles": true` を伝えたクライアントには `tiles` も届きます。セルごとの `[tile, rotation, subtile]`(ネイティブのタイル表示が選ぶ `overmap_terrain` のタイル ID、90 度回転数、マルチタイルキー)と、各タイル ID の `looks_like` フォールバックです。ほかのクライアントには送られません。セッション中にタイルと ASCII を切り替えるクライアントは、実行中のコマンドがないときに新しい `tiles` の値で `bn.hello` をもう一度送り(実行中なら `command_busy`)、続けて現在のサイズで `bn.viewport` を送ります。これでエンジンは開いている画面を、ID 付きまたは ID なしで再発行します。 `cursor_description` は、ネイティブのサイドバーがカーソルのマスについて述べる翻訳済みの文で、ウィンドウの枠やマスのグリフを含みません。`cursor_here`(カーソルがプレイヤーのマスにあるときの `You are here.`)、`cursor_note`(`Note:` の後に、ネイティブのウィンドウがカーソルのマスのメモについて隅に表示するテキストを続けたもの。例 `Note: cache`)、`route_text`(`path` の長さ。例 `Route of 2 squares.`)はエンジンが作る翻訳済みの行で、当てはまらないときはありません。
- 車両ウィンドウ(`^`、`context` が `VEH_INTERACT`)は `vehicle` オブジェクトを持つ `choices` インタラクションです。カーソルのパーツを囲むグリッドの `cells`(カーソルからの画面セル相対 `dx`、`dy`、`glyph`、ゲームの `color` 名)、カーソルのマスにある `parts`(内容物付きの `name`、層ごとの `open`/`close` 記号、`health`、`broken`)、ネイティブの `stats` 行(空行は空きスロット)、車両座標系の `cursor`、`blocked`、`owner`、`owned` を含みます。`mode` は `main`、作業リスト(`install`、`repair`、`remove`、`mend`、`refill`)、または `select`(吸い出し、乗員など)です。メイン画面の選択肢はネイティブのアクション(`action:INSTALL`、`action:REPAIR` など)で、`enabled` と、拒否時はネイティブのメッセージと同じ `denial` を持ち、カーソル移動(`action:UP` など)も含みます。作業リストの選択肢は候補パーツ `part:<index>` で、ネイティブのカーソル位置に `highlighted` が付きます。インストールのリストには `tab:<index>` の選択肢と `vehicle.tabs` もあります。`vehicle.detail` は強調中のパーツのプレビューで、`time`、パーツの `stats`、`requirements`(`kind` は `skill`、`component`、`tool`、`extra`。component と tool の行は代替品を OR でつなぎ、`met` を持つ)、`can_do` を含みます。強調中のパーツへの `choose` はネイティブの作業を開始し、別のパーツへの `choose` は強調を移すだけなので、クライアントは先に要件を表示できます。要件が未達の間、強調中の行は `enabled: false` と `denial` を持ちます。`cancel` は一つ前に戻ります。 `vehicle.verb` は翻訳済みの作業動詞(`Install`、`Repair` など)で、メイン画面にはありません。`detail.groups` は要件の見出しを表示順に並べ(`kind`、翻訳済みの `heading`、その種別の要件が無いときに表示する `NONE` などの `empty_text`。空ならその場合はグループを省く)、`detail.time_heading` は `time` の見出しです。
- コンピュータ端末(任意キー待ちでは `context` が `COMPUTER_TERMINAL`、問い合わせでは `YESNOQUIT`)は `choices` インタラクションで、`title` がコンピュータ名、`message` がネイティブウィンドウに表示される端末テキスト(行区切りは `\n`、色タグはそのまま)です。任意キー待ちの選択肢は `continue` のみ、問い合わせは `yes`、`no`、`quit` です。`choose` は対応するキーと同じ応答になり、`cancel` はプロンプトを終了します(問い合わせでは quit)。端末のルートメニューは通常のオプション一覧です。拡張説明(`context` が `EXTENDED_DESCRIPTION`)は、現在の対象の説明を `message` に、選択肢 `describe:creature`、`describe:furniture`、`describe:terrain` を持ち、現在の対象が `selected` です。`choose` で対象を切り替え、`cancel` で閉じます。
- ソフトウェアゲーム(スネーク、マインスイーパー、倉庫番、Lights on、robotfindskitten。`context`は`SNAKE`、`MINESWEEPER`、`SOKOBAN`、`LIGHTSON`、`IUSE_SOFTWARE_KITTEN`)は選択肢を持たない`custom` interactionで、`title`はゲーム名、`canvas`は描画されたゲームウィンドウです。`rows`はウィンドウの行ごとの`[text, foreground, background]`のrunの配列(色はオーバーマップと同じcursesの色番号0-15で、行末の空白セルは省略)、`cols`は幅です。ゲームのキーはboundaryの登録済みアクション(`UP`、`FLAG`、`CONFIRM`、`QUIT`など)で、アクションのないキーは生キー`text`コマンドです。`canvas`は`schema_id`に含まれないため、再描画でコマンドがstaleになることはありません。時間で進むゲーム(スネーク)には`refresh_ms`があり、ネイティブの入力待ちの長さを表します。その間にコマンドが来なければエンジン自身が待ちを終えてゲームを進め、再描画された`canvas`を通常の`interaction.changed`イベントとして公開するので、クライアントは受け取ったものを描くだけです。更新と重なったコマンドは`stale_boundary`で拒否されることがあり、新しい`boundary_id`で再送してください。robotfindskitten は終了アニメーションを `refresh_ms` 1000 のフレームとして公開し、そのフレーム以外のすべての状態は選択肢 `acknowledge`(description が `ANY_INPUT`)を持ちます。これを選ぶとアクションのないキーになり、フィールドは無効コマンドの行で応えます。
- ゾーンマネージャー(`context` が `ZONES_MANAGER`)は 3 つのペインを持つ `choices` インタラクションです。`zones`(ゾーンごとに `zone:<n>` 行、有効なら `selected`、`Type`、`Distance`、`Direction`、`Vehicle` の列)、`options`(強調中ゾーンのオプション行、選択不可、`Value` 列)、`actions`(ネイティブの `hotkey` と `Key` 列を持つ `action:<ID>` 行。ゾーンが 2 つ未満での移動のようにネイティブのキーが何もしない場合は `enabled` が false で、`SHOW_ALL_ZONES`、`TOGGLE_ZONE_OVERLAY`、`debug_submap_grid` はオンの間 `selected`)です。ゾーン行への `choose` はネイティブのカーソルを動かします。ゾーンの範囲を選ぶ段階(追加、位置の編集、位置の移動)は見回しの `target` インタラクションで、`message` は `Select first point.`、`Select second point.`、`Moving zone.`、`target.status` は `zone_first`、`zone_second`、`zone_move`(それ以外は `look`)です。`target.description` はネイティブの見回しウィンドウがカーソルのマスについて表示するテキストを 60 桁で折り返したもので、翻訳済みの 1 行が 1 項目です。カーソルは登録済みの方向アクションで動き、`CONFIRM` でマスを確定します。カーソルは `set_target`(読み込み済みマップの任意のマス)でも動きます。マップエディタ(`context` が `EDITMAP`)は `status` が `editmap` の `target` インタラクションです。`target.cursor` が編集中のマスで、`set_target` で読み込み済みマップの任意のマスへ動かせます。`tile` ペインはそのマスにあるもの(`tile:terrain`、`tile:furniture`、`tile:field:<id>`、`tile:trap`、`tile:creature` または `tile:vehicle`、`tile:items`。名前は `description`、ID と数値は `columns`)を、`actions` ペインは `hotkey` 付きの編集アクション(`EDIT_TERRAIN`、`EDIT_FURNITURE`、`EDIT_TRAPS`、`EDIT_FIELDS`、`EDIT_ITEMS`、`EDIT_MONSTER`、`EDIT_OVERMAP`、マップ全体を表示している間 `selected` の `EDITMAP_SHOW_ALL`、`LEVEL_UP`、`LEVEL_DOWN`)を並べます。編集メニューは通常の一覧で、`cancel` でエディタを閉じます。形状選択(`context` が `EDITMAP_SHAPE`)とマップ生成の対象移動(`context` が `EDITMAP_RETARGET`)は、`status` が `editmap_shape_resize`、`editmap_shape_move`、`editmap_retarget` の同形の `target` インタラクションで、`set_target` がカーソル(移動中は選択範囲も)を動かし、`actions` ペインにネイティブのアクション(`RESIZE`、`SWAP`、`EDITMAP_MOVE`、`START`、`EDITMAP_SHOW_ALL`、`CONFIRM`)を並べます。
- 設定画面はネイティブのものです。`settings:options`、`settings:keybindings`、`settings:autopickup`、`settings:safemode`、`settings:distractions`、`settings:colors` から開きます(オプションとキー割り当てはゲーム中も開けます)。`editor` を持つ行は直接設定できます。`fill` の `field_id` に行の `choice_id`、`value` にエディタの形式の値、`submit: true` を指定します。`editor.type` は `bool`(`true`/`false`)、`select`(`values[].id` のいずれか)、`integer`/`float`(`minimum`〜`maximum`)、`text`(`max_length` 以下)で、ネイティブメニューが受け付けない値はエンジンが拒否します。行への `choose` はネイティブの Enter と同じです。オプション: タブ行 `page:<id>` の後に、選択中のページの `option:<NAME>` と `group:<id>` の行が続きます。`cancel` で抜けるとネイティブの「変更を保存しますか?」が出て、保存すると適用され書き込まれます。キー割り当て: `mode:add_local`、`mode:add_global`、`mode:remove`(ネイティブが提供する場合は `mode:execute`)が次の `action:<ID>` 行の動作を決め、フィールドが名前で絞り込み、新しいキーの入力は `key` 型のフィールドで、キー割り当てファイルと同じ綴り(`z`、`=`、`F9`、`CTRL+A`)のキー名を受け取ります。自動拾いとセーフモード: タブ行 `page:<n>`、列行 `column:<n>`、`rule:<n>` 行。ルール操作(追加・削除・移動など)は画面の登録済みアクションです。注意散漫: `bool` エディタ付きの `distraction:<name>` 行(true で中断)。色: `column:<n>` と `color:<name>` 行。色を選ぶとネイティブの色リストが開きます。
- ワールドはアバターが知っているものです。`cells`(`remembered`、`visible`、`sensed`)、`entities`、`avatar`(能力値と所持品 `inventory`)、`environment`、読み込み済みの `coverage`、`view`、保留中の `route`(計画がなければ空または省略)で構成されます。`view` はアバターのいる階層でネイティブの地形ウィンドウが映すマス `{min, max}` です(アバターに追従します)。`travel` クリックはこの内側だけ受理され、外側は `validation_failed` で拒否されます。
- `avatar.sidebar` は同じ getter から取ったネイティブのクラシックサイドバーの値と、そのパネルが表示するラベルです。配置と描画はクライアントが行います。文字列の値は `{label, text, color}` で、`label` は翻訳されたパネルのラベル(パネルが表示しない場合は無し)、`color` は色に意味がある場合のネイティブ色名です。メンバーは `limbs`(`id`、`label` と状態色、`hp`、`hp_max`、体力の `color`、`broken`)、`pain`、`hunger`、`thirst`、`fatigue`、`temperature`、`power`、`location`、`weather`(地下ではラベル無し)、`focus`(`label`、`value`)、`morale`(`level`、ネイティブの `face`)、`stamina`(`label`、`current`、`max`、`color`)、`speed`(`label`、`value`、`color`)、`movement`(`counter`、`mode` は `walk`、`run`、`crouch`、`prone`、翻訳された1文字の `mode_text`)、`safe_mode`(`label`、`enabled`、`color`)、`time`(`season`、`day_label`、`day`、`clock`: 時計の時刻、なければおおよその時間帯、地下ではネイティブの時刻不明の文言)、任意の `ambient_temperature`(温度計がある場合のみ)、`weapon`、任意の `style`(武術スタイル)です。手足の体力とスタミナはバーではなく数値で、クライアントが自分の形で描きます。文字列はエンジンの表示言語で、それ以外の値は言語中立です。`stats` の項目はネイティブの `color` を持つことがあり、4つの能力値はサイドバーの `short_label` も持ちます。
- 地形ウィンドウはネイティブのウィンドウサイズ変更と同じ方法で決まります。`bn.hello` の `viewport = {cols, rows}`(マップのマス 1〜512)、または後の `bn.viewport` は、端末をそのマス数にサイドパネルを足した大きさへ変え、エンジンがアバター周辺をその分だけ映すようにします。ネイティブの最小端末サイズが引き続き適用されるため、実際の `view` が正です。何も送らなければ既定の端末が使われます。
- すべてのイベントは汎用の `changes` ブロックを持ち、`coverage`、`view`、`cells`、`forgotten`、`entities`、`gone` の順に適用した後、`avatar`、`environment`、`route`、`interaction` を置き換えます。
- バイト数を減らすため、セルレイヤーの `look` はレイヤーが既に示している `kind` を省略し（`terrain`、`furniture`、`trap`、`field`、`item`、`vehicle_part`。`memory.terrain` は `terrain`、`memory.overlay` は自身の値を保持）、`subtile` が `center`（形を持つレイヤーの既定値）のとき省略し、すべての `look` は `rotation` が 0 のとき省略します。イベントの `interaction` は `actions` が直前の境界と同じとき省略します。クライアントは自分の値を保持し、空のリストはそれを置き換え、スナップショットは常に一覧を含みます。
- イベントの `avatar` は、直前の avatar と同じで空でないメンバーを省略し、`keep` に名前を挙げます ("look"、"overlays"、"traits"、"stats"、"inventory"、"sidebar"、"ground")。クライアントは自分の値を保持し、それ以外で無いメンバーは空です。スナップショットの avatar は常に完全です。
- `message.logged` はネイティブのメッセージログです。`data = {id, text, kind, color, count}` で、1 行ごとに 1 イベントがログの順に、原因となったコマンドに紐づいて送られます。`text` は色タグと「x N」を除いた翻訳済みの行、`kind` はネイティブの種別(`good`、`bad`、`mixed`、`warning`、`info`、`neutral`、`debug`)、`color` はその種別のネイティブの色名です。最後の行が繰り返されると、同じ `id` が高い `count` で再度送られ、その行を置き換えます。状態は変えず(`revision` は進みません)、他の一時イベントと同様 `bn.resync` をまたぐと失われます。ただしログ自体は失われません。`bn.subscribe` が最新 100 行を `messages`(古い行から、`data` と同じ形、空なら省略)として返すので、ロードや resync の後に購読するクライアントも、ネイティブのクライアントが表示するログから始められます。以後の `message.logged` イベントをこの一覧に適用すると(繰り返しは同じ `id` の行を置き換え、100 行を超えると最も古い行が外れます)、新しく購読して得られる一覧と一致します。ネイティブのログがクールダウンで隠すメッセージは送られません。 `label` はネイティブのログが表示するそのままの行で、`count` が2以上なら `text` の後に翻訳済みの繰り返し接尾辞 (`x 2`) が付きます。
- `projectile.moved`、`explosion.started`、`explosion.blast`、`explosion.ended`、`combat_text.shown` はネイティブのアニメーション事実です。ゲームがアニメーションを始める箇所で公開されるため、どのクライアントもレンダラーなしで同じ事実を得ます。状態は変えず、原因のコマンドに紐づき、そのコマンドの状態イベントより前に届きます。`display.duration_ms` はネイティブのアニメーションがその事実を保持する時間です(1 ステップあたり `ANIMATION_DELAY` オプション)。`projectile.moved` は `path`(描画順のマス。弾が飛ぶ間はイベントごとに 1 マス)と、グリフとカスタムスプライト ID を持つ種別 `projectile` の `look` を持ちます。`explosion.started` は `at`、`radius`、`color` と、ネイティブのタイルが使うタイル ID `tile` を持ちます。描画するかどうかはクライアントが決めるため、`ANIMATIONS` オプションはこれらを抑止しません(クライアントはゲームを変えません)。戦闘テキストだけは `ANIMATION_SCT` が必要です。`explosion.blast` は地形で形が変わる爆発の 1 リング分の `cells` を並べます。`combat_text.shown` は `at` に出る 1〜2 色の `segments` の浮遊テキストで、ネイティブと同じく 1 アニメーションステップごとに `scroll`(単位ステップ)だけ動きます。`kind` が `hp` のものはクリーチャーの HP 表示で、その横に留まります。
- 投げられたアイテムはゲームイベントとしても公開され、アニメーションのオプションでは止まりません。どれもアバターに見えるものだけが公開されます。`item.activated`(`at`、`look`、導火線の残りターン数 `turns`)は導火線に火がついたときと、燃えている間の毎ターンに出ます。`item.thrown`(`projectile`、`look`、`by`、`from`、`to`)が飛行の始まりで、その `projectile.moved` イベントは同じ `projectile` を持ち、`item.landed`(`at`、`look`、攻撃が放った場合は `projectile`)が終わりです。投げられた弾や撃たれた弾は `projectile.hit`(`at`、アバターに見えるクリーチャーに当たった場合は `entity`。障害物なら無し)にも同じ `projectile` を持ち、これは `projectile.moved` の後、それが起こした `entity.damaged` や地形の変化の前に来ます。爆発は `explosion.started`、論理時間ステップごとの `explosion.blast` または `explosion.shrapnel` のリングとそのステップが起こしたこと、そして `explosion.ended` です。起こしたこととは、クリーチャーが受けた攻撃ごとの `entity.damaged`(`id`、`amount`、キャラクターなら `part`)、ステップで変わったマスの `terrain.changed` と `furniture.changed`(`at`、`from` と `to` の look)、追加または除去されたフィールドごとの `field.changed`(`at`、`field`、変化後の `intensity`。消えたら 0)です。`entity.damaged` はクリーチャーが受けるすべてのダメージ(直接加えられたものを含む)で出ます。地形・家具・フィールドの変化は爆発に限らず、ゲームが起こすたびに公開されます。アバターに見えるマスを変えるすべての呼び出し(ドアを壊す、家具を置く、フィールドを足す・除く)は共有のマップ境界で、フィールドターン(延焼、ガスの拡散、フィールドの減衰。スキップしたターンも含む)はアバターの階で見えるフィールドの前後を比べて、違うマスごとに 1 件の `field.changed` として公開されます。長い待機のあとでも、そのマスは 1 回だけ伝えられます。
- `sound.heard`(`text`、`volume`、`marker`、`logged`)は、ネイティブの聴覚ルール(周囲の騒音に対する音量、聴覚保護、睡眠、難聴)を通ってアバターに届いた音です。`text` はネイティブのメッセージが挙げる説明、`volume` はアバターに聞こえるデシベル、`marker` はネイティブのゲームが音を示すマスです。マーカーは音源ではなく、その近くでアバターから見えないマスで、アバターが音源にいるか音源が見えるときは省かれるため、隠れた音源は漏れません。音のログ行はネイティブのメッセージルールとクールダウンに従いますが、`sound.heard` は足音などログが省く音も含め、聞こえたすべての音について公開されます。`logged` は、その音がメッセージログにも行を持つとき `true` で、両方を表示するクライアントが同じ音を一度だけ挙げられます。 アバター自身の叫びは、そのアクションが自分で行 (`You yell ...`) を記録するため logged として扱います。
- `entity.moved`(`id`、`to`、`from`、`mode`)と `entity.gone`(`id`、`reason`)により、クライアントはスナップショットが開示するモンスターと NPC を、再同期なしでアクションの間じゅう追えます。`entity.moved` はアバターに見えるクリーチャーの移動ごとに、移動先のマスで公開されます。移動元のマスがアバターに見えていなければ `from` は省かれ、`mode` は隣のマスへの一歩なら `walk`、それより長い移動(押される、テレポート)なら `propelled` です。アバター自身の移動は状態の差分に含まれます。`entity.gone` は、クライアントが知っていたクリーチャーがもう開示されないことを示し、`reason` は `lost_sight`(視界から出た、またはアバターや視点が動いた)、`died`、`removed`(ゲームから消えた)です。視界から歩き出たクリーチャーはその場で `gone` になり、それ以外は境界の公開時に見つかります。混んだターンでは `entity.moved`、`terrain.changed`、`furniture.changed`、`field.changed` の最初の 256 件だけが公開されます(視界から歩き出たクリーチャーの `gone` も数えます)。境界の `cells.seen` 変更セットは常に最終状態を持つため、イベントは順序とタイミングを加えるだけで、状態を置き換えることはありません。

イベントは `interaction.changed`、`coverage.moved`、`turn.passed`、`cells.seen`、`message.logged` と上記のアニメーション事実で、今後スキーマに挙げた残りの演出タイプが加わります。0.2 の公開前に追加したイベントタイプは 0.2 に含まれ、公開後は新しいイベントタイプに新しい正確なバージョンが必要です。
